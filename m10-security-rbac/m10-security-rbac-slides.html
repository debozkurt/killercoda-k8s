Admission acts on requests that create, modify, delete, or connect to an object. It never sees reads.

401, 403, and system:anonymous

Invalid credential

Authentication fails. The API server returns 401 Unauthorized.

No credential

The API server treats the request as system:anonymous. Authorization then refuses it with a 403.

The API server enables anonymous access by default.

Valid credential, no rule

Authentication succeeds. Authorization finds no matching rule and returns a 403 that names the identity.

A 401 points at the credential. A 403 points at the identity the API server resolved, so read that identity first.

The RBAC refusal is a five-field sentence

The API server writes one line. This slide splits it by field.

deployments.apps is forbidden: User "system:serviceaccount:provisioning:release-auditor" # identity cannot list # verb resource "deployments" # resource in API group "apps" # API group in the namespace "provisioning" # scope

A cluster-scoped request ends at the cluster scope instead. A subresource prints as "pods/log".

Each field maps to one object

FieldIn the messageWhere the fix lives
IdentityUser "system:serviceaccount:…"The Pod's serviceAccountName, or a binding's subject
Verbcannot listThe rule's verbs
Resourceresource "deployments" or "pods/log"The rule's resources, subresource included
API groupin API group "apps"The rule's apiGroups; "" is the core group
Scopein the namespace "…" or at the cluster scopeThe kind of binding

A rule is API groups × resources × verbs

rules: - apiGroups: ["apps"] resources: ["deployments"] verbs: ["get", "list", "watch"]
HTTP requestVerb
GET one named objectget
GET a collectionlist
GET with ?watch=truewatch
  • A request matches only when all three lists contain its values.
  • RBAC matches exact strings. get is not list, and pods is not pods/log.
  • Permissions are purely additive. No rule denies, so a refusal always means no rule matched.

Core group: matches no request

deployments [] [] [get list watch]

No suffix means apiGroups: [""]. The core group has no deployments resource.

The apps group

deployments.apps [] [] [get list watch]

The suffix names the group. This rule matches a list of Deployments.

kubectl api-resources | grep -w deployments deployments deploy apps/v1 true Deployment

Scope is a property of the binding

BindingRole it referencesGrants
RoleBindingRoleInside the RoleBinding's own namespace
RoleBindingClusterRoleInside the RoleBinding's own namespace. The standard way to reuse view
ClusterRoleBindingClusterRoleAcross all namespaces, and cluster-scoped resources

nodes, namespaces, and persistentvolumes live in no namespace. The API server accepts a Role that lists nodes, and that Role grants nothing. The refusal ends at the cluster scope.

Prove the decision with kubectl auth can-i

--as requires impersonation rights, which cluster-admin has.

kubectl auth can-i list deployments -n provisioning \ --as=system:serviceaccount:provisioning:release-auditor no kubectl auth can-i --list -n provisioning \ --as=system:serviceaccount:provisioning:release-auditor Resources Non-Resource URLs Resource Names Verbs deployments [] [] [get list watch]
  • The first form answers one request with yes or no. The second prints every rule the identity holds.
  • Reproduce the 403 as a no, then change one object until it reads yes.

A holder of edit can run Pods as any ServiceAccount in the namespace, and so can act as any of them.

Grants that are wider than they read

Workload creation

The right to create Pods, or a Deployment that creates them, reaches every Secret in the namespace. The Pod mounts the Secret and reads it.

The Pod can also run as any ServiceAccount there.

escalate, bind, impersonate

RBAC normally refuses a Role with permissions the creator lacks. escalate and bind remove that check.

impersonate lets the caller act as another identity.

nodes/proxy

A get reaches the kubelet API, which can execute commands in every Pod on the node.

That access bypasses audit logging and admission control.

When the identity is default,
fix the Pod

Grant the permission to default

The 403 clears. Every Pod in the namespace that omits serviceAccountName inherits the grant.

Set the Pod's ServiceAccount

The Pod runs as the account the RoleBinding already grants. Nothing else changes.

kubectl set serviceaccount \ deployment route-watcher \ route-watcher -n call-routing

The identity field separates two faults. The intended account means the permission is wrong. default means the Pod is wrong.

The securityContext fields

FieldEffect
runAsNonRoot: trueThe kubelet refuses to start a container whose user is UID 0
runAsUser: 1000Runs the process as this UID, overriding the image's user
allowPrivilegeEscalation: falseSets no_new_privs, so a child process cannot gain privileges
capabilities.drop: ["ALL"]Removes every Linux capability
seccompProfile.type: RuntimeDefaultApplies the container runtime's default syscall filter

Set them at Pod level for all containers, or per container. By default a container runs as root and keeps the runtime's default capabilities.

Three Pod Security Standards, cumulative

LevelForbids
PrivilegedNothing. Unrestricted
BaselinePrivileged containers, host namespaces, hostPath volumes, host ports, added capabilities outside a default set
RestrictedEverything Baseline forbids, plus:
  • no runAsNonRoot: true, or UID 0 in runAsUser
  • privilege escalation
  • any capability except NET_BIND_SERVICE after drop: ["ALL"]
  • a seccomp profile other than RuntimeDefault or Localhost
  • volume types outside a short list

A namespace with no label takes the cluster default. That default is privileged unless the cluster admission configuration sets another level.

  • runAsNonRoot checks the user. It never sets it. With no runAsUser, the kubelet reads the user from the image.
  • Fix with a non-root runAsUser, or an image with a numeric non-root USER. A named USER fails the same check.

Turn on enforce in two passes

Find the violators firstSet warn and audit, or run a server-side dry run. It prints a warning for each existing Pod that would fail.
Fix each workloadAdd the securityContext fields, including a non-root runAsUser where the image runs as root.
Set enforceRunning Pods keep running. Enforcement checks only creation, so each Pod is checked at its next replacement.
kubectl label --dry-run=server --overwrite ns payments \ pod-security.kubernetes.io/enforce=restricted

RBAC and Pod Security: key rules

  • Read the refusal before you change anything. Its wording names the stage that refused.
  • The RBAC refusal names identity, verb, resource, API group, and scope. Prove it with auth can-i and change the one object that does not match.
  • RBAC only adds. A request is denied because no rule matches its exact strings in its scope.
  • A Pod's identity is its ServiceAccount. An empty serviceAccountName means default, so fix the Pod.
  • enforce leaves a Deployment with zero Pods. A compliant spec can still fail at the kubelet when the image runs as root.
