RBAC & Pod Security

The two questions every request to the API server must pass — who are you and what may you do — plus the admission gate that decides whether a Pod's security posture is allowed at all.

Security failures don't crash — they deny. The whole signal is one string from the API server, and it names the gate that said no.

What you'll walk away with

  • Trace a request through the API server's three gates — authentication, authorization, admission — and tell which one a Forbidden came from
  • Read RBAC: a Role as a set of rules (apiGroups × resources × verbs), a binding tying a subject to a role, and the additive, deny-by-default evaluation
  • Reproduce and prove any authorization decision with kubectl auth can-i instead of guessing
  • Understand a ServiceAccount as a Pod's API identity, and why the default SA is bound to nothing
  • Set a container's securityContext and enforce the Pod Security Standards per namespace
  • Work the Forbidden differential — one phrase in the message tells a missing verb from the wrong identity from the wrong scope

Security failures don't crash;
they deny

A Pod that can't reach the API doesn't OOM or sit Pending. Its app logs one line — Forbidden — and stalls.

Every reflex from the workload modules — logs, --previous, restart — returns nothing useful. The app was never wrong.

A request is authorized if some rule reachable from the caller matches its apiGroup, its resource, and its verb.

One rule, three lists ANDed

# "" is the core group rules: - apiGroups: [""] resources: ["endpoints"] verbs: ["get", "list", "watch"]

Miss any one list and no rule matches — so it's denied.

Additive, deny-by-default,
and it matches strings

You can only grant, never deny

A subject's permissions are the union of every binding that reaches it. There is no deny rule to hunt for.

"Why can't it?" is always "no rule allows it" — never "something blocked it."

Strings, not intent

endpoints and endpoint, get and list, group "" and "apps" are different keys.

A near-miss is a silent denial. There is nothing to unblock — only a rule to make match.

Don't argue with the error. Make some rule, reachable from the right subject, match all three strings in the right scope.

Two scopes, and the boundary bites

Namespaced — Role + RoleBinding

Grants its rules only within its own namespace. A Role can only usefully grant namespaced resources.

Cluster — ClusterRole + ClusterRoleBinding

Grants across every namespace — and is the only kind that can grant a cluster-scoped resource: nodes, namespaces, persistentvolumes.

Put nodes in a namespaced Role and bind it with a RoleBinding: RBAC accepts the YAML and grants nothing. Nodes live outside every namespace, so the request is denied at the cluster scope — and that word, scope, is the whole tell.

Reproduce any decision
with auth can-i

It asks the API server the exact question the authorizer answers — so you prove the decision instead of guessing.

# yes / no — reproduce one denial as an impersonated identity kubectl auth can-i list endpoints -n media \ --as=system:serviceaccount:media:endpoint-watcher # the full matrix — everything that subject actually holds kubectl auth can-i --list \ --as=system:serviceaccount:media:endpoint-watcher -n media

The first move on any Forbidden: reproduce it as a yes/no, then widen with --list. --as impersonates any identity (you need impersonation rights, which cluster-admin has).

A Pod's identity is its ServiceAccount

SA identity
…:<ns>:<name>

Every Pod runs as exactly one SA — the one named, or default if unset — and authenticates as system:serviceaccount:<ns>:<name>. That string is the subject your bindings must name.

The default SA is the trap: auto-created in every namespace and bound to nothing. A Pod with no serviceAccountName runs as it — and gets denied even when the Role you wrote is sitting right there, correct, granting the SA the Pod never adopted.

securityContext: what the Pod may be

Authorization governs what a Pod's process may ask the API. This governs the process's own security posture — set per Pod or per container.

FieldWhat it does
runAsNonRoot: truethe kubelet refuses to start a container whose image would run as UID 0
runAsUser: 1000pins the UID — needed with runAsNonRoot when the image defaults to root
allowPrivilegeEscalation: falseno child process can gain more privileges than its parent
capabilities: {drop: [ALL]}start from zero Linux capabilities, add back only what's needed

Three Pod Security Standards

Privileged

Unrestricted. The default when a namespace carries no label.

Baseline

Blocks the known-dangerous: no privileged containers, no host namespaces, no hostPath. Minimal friction.

Restricted

Everything Baseline blocks, plus the hardened fields:

  • runAsNonRoot
  • allowPrivilegeEscalation: false
  • capabilities: drop [ALL]
  • a seccompProfile

Restricted requires exactly the securityContext fields from the previous slide — the Standard is those knobs, named and enforced.

PodSecurity admission enforces a Standard
per namespace, by label

kubectl label ns payments \ pod-security.kubernetes.io/enforce=restricted \ pod-security.kubernetes.io/warn=restricted
enforcerejects a non-compliant Pod at admission
auditrecords it in the audit log
warnreturns a warning to the client, but admits it

The three modes are independent, so the safe rollout is warn/audit first — learn what would break — then enforce.

A rejected Deployment
has no Pods at all

Because enforce runs at admission, the rejection lands on the object that tries to create the Pod. For a Deployment, that's the ReplicaSet — no Pod is ever created.

So a Deployment can sit at 0/3 ready with nothing to describe — not even a Pending Pod. The reason is an event on the controller.

Where the reason lives

kubectl get pods -n payments No resources found. kubectl describe rs -n payments Error creating: … violates PodSecurity "restricted:latest"

Look at the ReplicaSet or the namespace events, not get pods.

What to carry forward

  • Every request passes three gates in order — authn, authz, admission — and a Forbidden names which one. Read the gate before you touch the app.
  • RBAC is additive, deny-by-default, and matches strings. A near-miss is a silent denial — there's nothing to unblock, only a rule to make match.
  • A Pod's identity is its ServiceAccount; unset means default, bound to nothing. The subject in a Forbidden says whether the permission is wrong or the caller isn't who you meant.
  • Scope is a hard boundary. Cluster-scoped resources need a ClusterRole through a ClusterRoleBinding; a namespaced binding for them parses fine and grants nothing.
  • PodSecurity enforce rejects at creation, so a rejected Deployment has zero Pods and the reason lives on the ReplicaSet. restricted needs non-root, no privilege escalation, dropped capabilities, and a seccomp profile.
