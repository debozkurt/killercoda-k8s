Helm:
render, record, apply

A chart plus values renders into manifests. Helm applies them and records the result as a numbered revision of a release.

Each failure lands in one stage. Helm keeps its own record of each stage, so read that record as well as the cluster.

Helm keeps an override key
that no template reads

$ helm get values voicemail USER-SUPPLIED VALUES: replicas: 3 $ helm get values voicemail -a COMPUTED VALUES: replicaCount: 1 replicas: 3
$ helm get manifest voicemail \ | grep 'replicas:' replicas: 1
  • Helm does not check an override against the keys the templates read.
  • -a shows the unused key next to the real one; the manifest shows the result.
  • A values.schema.json with additionalProperties: false turns an unknown key into an error.

The chart on disk can change after an install. The stored manifest is what the cluster is supposed to run.

A render error stops the install;
nothing reaches the cluster

$ helm install voicemail /root/voicemail --set replicaCount=2 Error: INSTALLATION FAILED: execution error at (voicemail/templates/deployment.yaml:25:24): voicemail: .Values.config.sipRealm is required
  • required stops the render when its value is empty or missing.
  • Helm renders before it creates the release record: no release, no object, no event.
  • helm template reproduces the same error offline.

The release record lives in Secrets

$ kubectl get secret -n app-services -l owner=helm --show-labels sh.helm.release.v1.voicemail.v1 ...status=superseded,version=1 sh.helm.release.v1.voicemail.v2 ...status=superseded,version=2 sh.helm.release.v1.voicemail.v3 ...status=deployed,version=3
  • One Secret per revision, in the release namespace by default.
  • Every install, upgrade and rollback adds one revision.
  • helm upgrade keeps 10 revisions by default (--history-max).

deployed means the apply succeeded,
not that the Pods are healthy

Default upgrade

Helm 4 defaults to --wait=hookOnly. It waits for hooks only and records deployed once the apply succeeds.

e.g. a missing image tag: READY 2/2, UP-TO-DATE 1, one Pod in ImagePullBackOff.

Graded upgrade

--wait alone uses the watcher strategy, up to --timeout (default 5m). After a timeout, Helm marks the revision failed.

--rollback-on-failure (Helm 3: --atomic) also returns to the last successful revision.

A rollback writes a new revision

$ helm rollback voicemail 1 $ helm history voicemail REVISION STATUS DESCRIPTION 1 superseded Install complete 2 superseded Upgrade complete 3 deployed Rollback to 1
  • Helm re-applies revision 1's manifest as revision 3. Revision 2 stays in the history.
  • Recover a Helm-managed workload through Helm, so the record and the cluster agree.

The record is also a lock

$ helm upgrade voicemail /root/voicemail --reuse-values ... Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress $ helm history voicemail 1 deployed Install complete 2 pending-upgrade Preparing upgrade
  • Helm writes the revision as pending before it applies, and changes it when the operation ends.
  • If CI kills the process during --wait, the pending status stays forever.
  • helm rollback does not check the lock. Its new deployed revision clears it.

Do not delete revision Secrets by hand. A wrong delete removes the record of the revision that runs now.

Helm adopts an existing object
only when its metadata names the release

Error: INSTALLATION FAILED: ... Service "voicemail" in namespace "app-services" exists and cannot be imported into the current release: invalid ownership metadata
labelapp.kubernetes.io/managed-by: Helm
annotationsmeta.helm.sh/release-name, meta.helm.sh/release-namespace
  • helm template succeeds: this is an apply-stage failure.
  • The error names one object at a time.

Three ways past an ownership conflict

Adopt

Write the label and both annotations, then install. The object keeps its UID and ClusterIP.

--take-ownership

First confirm that no other release owns the object. Then Helm skips the check.

Delete and recreate

Callers lose the object for a moment. A Service comes back with a new ClusterIP.

Another manager owns the field;
Helm 4 refuses to overwrite it

$ kubectl scale deployment voicemail --replicas=4 $ helm upgrade voicemail /root/voicemail --reuse-values Error: UPGRADE FAILED: ... conflict with "kubectl" with subresource "scale" using apps/v1: .spec.replicas
  • Helm 4 installs with server-side apply, as the field manager helm.
  • The upgrade, and also a rollback, fails and changes nothing.
  • When the chart is right, --force-conflicts takes the field back. When the hand edit is right, move it into the values.

A release that Helm 3 created keeps client-side apply. Its three-way merge overwrites the same drift with no message.

Recap

  • Helm renders, records a revision, then applies to the API server. Find the stage first.
  • A template reads specific key paths. Compare helm get values -a with helm get manifest.
  • The release record is history and a lock. helm rollback writes a new revision and clears a stale pending status.
  • deployed describes the Helm operation, not the workload.
  • Helm owns objects through metadata and, in Helm 4, through field managers. Change a Helm-managed object through its values.
