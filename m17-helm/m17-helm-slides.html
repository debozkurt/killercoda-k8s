Helm Fundamentals

The Kubernetes package manager. A chart plus values renders into manifests; Helm applies them and records the result as a release you can upgrade and roll back.

What runs in the cluster is the render's output, and Helm keeps its own record of that output. Debugging Helm means reading its state — values, manifest, history — not just the cluster's.

What you'll walk away with

  • Read a chart on disk — Chart.yaml, values.yaml, templates/ — and know which keys the templates actually consume
  • Trace a value from your --set/-f input through the render to the live object with helm template and helm get manifest
  • Reason about values precedence, and why Helm silently keeps override keys it never reads
  • Use the release model — revisions, helm history, helm status, helm rollback — to recover from a bad upgrade
  • Read past a green helm status to the Pods that Helm never waited on
  • Decide when Helm is the right tool and when Kustomize fits better

The pipeline has three stages — merge, render, apply — and every failure this module covers lives in exactly one of them.

Three ways Helm bites, one per stage

None of them looks like a normal Kubernetes problem. Each fails at a different point in the pipeline and leaves a different signature.

Value carried but inert

An override sits at a key the chart never reads. It renders the default anyway — no error.

Helm keeps three views
the plain cluster can't give you

Because Helm records its own inputs and outputs, you compare these three against the live objects — and the discrepancy names the stage that failed.

helm get values

The inputs — the values that fed the render. Add -a for the effective merge, defaults included.

helm get manifest

The rendered output Helm actually applied, read back from stored release state — the authoritative answer, not the chart on disk.

helm history

The timeline of revisions. Every install, upgrade, and rollback is a numbered entry with a status.

A chart is inputs and templates

values.yaml holds the defaults; templates/ holds manifests with holes. helm install merges your overrides over the defaults, evaluates the templates, and applies the result.

  • A template reads specific key paths — it pulls the ones it names and ignores every other key in your values
  • Templates are Go text/template plus the Sprig functions, so values have types and a missing key renders as <no value>, not an error

templates/deployment.yaml

# the template names the key it reads spec: replicas: {{ .Values.replicaCount }} # ... image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"

helm template renders offline;
required fails before the cluster

helm template runs merge + render locally and prints the manifests without touching the cluster — the most useful command in the kit. It answers "what would these values produce?" and reproduces render errors offline.

# see what the values render to — no cluster needed helm template voicemail ./chart -f prod-values.yaml # a required value that is missing aborts the render, client-side Error: execution error: sipRealm is required

A required failure happens before anything is applied — there is no Pod, no event, nothing for the normal get → describe → events loop to find. The error text and helm template are the entire diagnosis.

lowest to highest

Repeated -f files layer left to right; the rightmost wins a conflict. --set beats every file.

It is a deep merge, not a replace: a file that sets image.tag leaves image.repository at the chart default.

Helm does not validate your overrides

Set the wrong key — a typo, or replicas when the chart reads replicaCount — and Helm keeps your key in the release values and renders the default anyway. No warning.

# what you ASKED for — shows your (wrong) key, misleading alone helm get values voicemail # what actually TOOK — effective merge, defaults included helm get values voicemail -a # what RENDERED and applied — the ground truth helm get manifest voicemail

The wrong-key signature

Your key appears in get values, sits beside the real key in get values -a, and never reaches get manifest.

A chart shipping values.schema.json turns this whole class of bug into an install-time validation error instead of a silent no-op.

A release is a revision history
stored in the cluster

Every install, upgrade, and rollback writes a new revision and keeps the old ones. The state lives in the cluster, so any operator with access sees the same history — Helm holds no local state.

release namespace
revision 1install
revision 2upgrade
revision 3rollback
each stored as a Secret — sh.helm.release.v1.<release>.v<n>

helm status is the current snapshot — which revision is live, deployed or failed.

helm history is the timeline — and every bad upgrade has a prior good revision to return to.

helm status: deployed means
"applied", not "healthy"

By default helm upgrade returns as soon as the apply succeeds — it does not wait for Pods to become ready. Helm grades the manifest, not the rollout.

Read past a green status to kubectl get pods / kubectl rollout status. --wait makes the upgrade block on readiness; --atomic adds --wait and auto-rolls-back on failure — at the cost of deploy latency and the watch RBAC it needs.

helm rollback rolls forward,
and recovery goes through Helm

revision 1the last good release
revision 2the bad upgrade — stays in history
revision 3rollback re-applies rev 1's manifests

A new revision, not a rewind

helm rollback <release> 1 re-applies an old revision's manifests as revision 3. The broken revision is kept in the timeline.

Recover through Helm, not kubectl rollout undo. Undoing at the Deployment fixes the live object but leaves the release pointing at the break — the next helm upgrade or reconcile re-applies it.

Helm vs Kustomize:
both solve one config, many environments

Helm

Templated and packaged: manifests with {{ }} holes, parameterized with values, versioned with dependencies and rollback as a unit.

trackingrevisions, history, rollback
fitsthird-party apps, install-and-forget

Kustomize

Template-free: real manifests as a base plus patches that override fields; kubectl apply -k builds the result.

trackingnone — the cluster is the state
fitsyour own manifests, small per-env deltas

Reach for Helm when you consume someone else's packaged app or want release/rollback semantics; reach for Kustomize when you own the manifests and the per-environment difference is a handful of patches. They also compose.

What to carry forward

  • Helm is render plus bookkeeping. Chart + values → manifests → an applied, versioned release. Every failure lives in one of those stages.
  • Templates read named key paths; Helm doesn't validate overrides. A wrong-key value is kept but inert — get values -a versus get manifest exposes it.
  • A release is a numbered revision history in the cluster. status is now, history is the timeline, rollback rolls forward to an old revision.
  • deployed means "manifest applied," not "workload healthy." Read past it to the Pods; use --wait/--atomic to grade readiness.
  • Recover Helm-managed workloads through Helm. A kubectl edit drifts the object from the release record, and the next reconcile undoes your fix.
