CRDs & Operators

The API server ships with a fixed vocabulary — Pods, Deployments, Services. This is how every capability above the built-ins is delivered, and how it quietly fails.

A CRD adds a word to the API server's vocabulary; an operator is the program that makes the word mean something.

A CRD adds a noun;
an operator is the verb

CustomResourceDefinition

Register a type and the API server stores, validates, versions, and serves it. kubectl and RBAC treat instances like any built-in.

Operator

A controller paired with that CRD — a loop that watches instances and makes each one mean a running, correctly-sized workload.

A noun with no verb is inert: a custom resource on its own changes nothing, just as a Deployment object would with no Deployment controller running. An operator is a CRD plus a controller.

One turn of the reconcile loop

Read each resource's spec, create or update the child to match, write what you observed into status — then repeat. The whole child tree hangs off the CR by an ownerReference.

A CRD registers a type
with the API server

Applying a CRD gives the API server a new endpoint and a new served type. The CRD declares that type's identity and scope; the name is mechanical, always <plural>.<group>.

Registration isn't instant. The Established condition flips True once the type will serve. Before that, kubectl get <kind> fails with "the server doesn't have a resource type" — the same error as a typo.

First question when a custom type "doesn't exist": is the CRD installed, and Established?

The schema is real,
API-server-enforced validation

A structural OpenAPI schema in the CRD constrains every field — type, enum, required, min/max. The API server checks each resource at admission, exactly as it checks a built-in. A resource that violates it is rejected and never stored.

Accepted

tier: gold — in the enum.
replicas: 3 — an integer, 1–5.

Passes admission, gets stored, the operator sees it.

Rejected at admission

tier: platinum — not in the enum.
replicas missing — a required field.

The error names the offending field; the resource is never stored.

"My custom resource won't apply" is almost always a schema mismatch, read straight from the rejection. kubectl explain <kind>.spec reads the same schema back.

One type,
several served versions

Each version flags whether it's served — the API accepts it — and exactly one is storage, the form written to etcd. Every object is persisted in the storage version and converted on read to whatever version the client asked for.

Serving more than one version lets consumers migrate on their own schedule.

PER VERSION

servedAPI accepts this version — can be several
storageexactly one — the form etcd persists

Version skew. If the operator watches a version that is no longer served, its watch returns nothing — it reconciles nothing, and every resource sits untouched. It looks identical to an operator asleep. The tell is in the CRD: compare its served versions to the apiVersion the operator is built for. Upgrade operator and CRD in lockstep.

The loop reasons about the current difference, not a stream of events. A dropped notification, a restart, or an API blip all self-heal on the next pass — delete a child it manages and the next pass recreates it.

This is why an unblocked operator recovers on its own, no restart needed.

You own spec;
the controller owns status

.spec — desired state

What you declare — the tier, the replica count. Your apply writes here.

.status — observed state

What the controller writes back — phase, ready replicas — through a separate status subresource.

The subresource splits the two halves at the API: a normal apply of spec can't touch status, and the controller's status write can't touch spec. Neither clobbers the other — that split is the contract every operator follows.

Read operator state
from three surfaces at once

The CR's .status

Conditions and phase — what the operator claims is true.

The child resources

The Deployments and Pods it created — what actually exists.

The operator's logs

What it tried, and what stopped it.

Agreement across all three means healthy. A gap between them localizes the fault — status claiming Ready with no child Pods points somewhere very different from a status stuck Provisioning.

Each child names its owner by kind, name, and uid — the uid pins it to this resource, not something that merely shares the name; controller: true marks the single managing owner. Delete the owner and the garbage collector deletes every object whose ownerReferences names it, following each link down the tree.

Read the reference the other way and it's a debugging map: from a child find its parent, from a resource enumerate everything it spawned. Never hand-delete an operator's children.

The failure is
the absence of the link

Missing ownerRef

A child created by hand, or by an older operator, carries no thread. Delete its logical parent and the collector has nothing to follow — the child becomes a silent orphan, running on for something gone. Nothing errors.

Stale uid

A reference to an owner uid that no longer exists marks the child for deletion. A recreated parent gets a new uid, so old children point at a ghost and get collected out from under it.

Finalizer left behind

A finalizer blocks hard deletion until its controller cleans up and removes the key. A finalizer whose controller is gone wedges the object in Terminating indefinitely.

You spot an orphan by comparing a suspect child's ownerReferences to a properly-managed sibling's, and by noticing children whose named owner no longer exists.

What to carry out

  • A CRD adds a type; an operator gives it meaning. The CRD registers a first-class, schema-validated, RBAC-governed resource; the controller is a level-triggered loop that makes instances of it do something.
  • The schema is API-server-enforced. A resource that violates it is rejected at admission and never stored — "it won't apply" is a schema mismatch you read from the error.
  • A Running Pod is not a progressing loop. When resources sit un-advanced, read .status, children, and logs — and check: down, forbidden, or watching an unserved version.
  • Owner references are the thread cascading deletion follows. Missing one orphans a child; a stale one deletes it early; a finalizer can wedge deletion in Terminating.
  • Operators fail quietly. The failure is a resource that never appeared, never progressed, or never left — you catch it by verifying each link held, not by waiting for something to go red.
