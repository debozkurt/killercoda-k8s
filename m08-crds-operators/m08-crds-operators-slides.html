CRDs and operators:
new types and the loops behind them

An operator fails without a crash, so check that each link held.

The schema validates at admission
and prunes unknown fields

Invalid value: rejected

The API server checks every object against the structural schema before it stores the object.

kubectl apply -f vega.yaml spec.tier: Unsupported value: "platinum": supported values: "gold", "silver", "bronze"

Unknown field: pruned

The docs: "the unknown field is pruned (removed) before being persisted."

  • No error appears.
  • A misspelled optional field has no effect.
  • Compare the stored object with the manifest.

kubectl explain reads the same schema, so it shows what a valid object looks like.

  • A client pinned to v1 gets an error on every list call.
  • The docs: clients on the old version "may begin reporting errors." Serve the old version again, then migrate the client.
  • Upgrade an operator and its CRD together.

The docs: operators are "software extensions to Kubernetes that make use of custom resources to manage applications and their components."

  • Step 3: the operator writes the observed state back into the tenant's .status.
  • The CRD adds the type. Without a controller, creating an object changes no cluster state.

The loop is level-triggered.
Read three places together

Each pass compares desired and observed state and closes the gap. A deleted child returns on the next pass.

The .status

What the operator claims. Phase and ready count.

The children

What exists. Deployments, ReplicaSets, Pods.

The logs

What the operator tried, and what stopped it.

When all three agree, the operator is healthy. A gap shows where the fault is.

Stuck reconciliation has three causes

The operator Pod is Running in all three. Pod status says the program is alive, not that the loop progresses.

CauseSignatureFirst command
Controller downLast-written .status never updates. No Pod, or crash loop.get pods, get deployment
Controller forbiddenProvisioning, no children, Forbidden in the logs.auth can-i --as= returns no
Version not servedBlank .status, no children, list error in the logs.describe crd: Served:

One command separates forbidden
from an unserved version

kubectl auth can-i create deployments -n media \ --as=system:serviceaccount:platform:tenant-operator no forbidden: add the missing verb to the role kubectl auth can-i list mediatenants.polyphone.example \ --as=system:serviceaccount:platform:tenant-operator yes allowed: read the logs and the CRD versions
  • The operator runs as a ServiceAccount, the identity a Pod uses to call the API.
  • If the role lacks a verb, every attempt returns 403.
  • If the answers are yes, RBAC is not the cause. The logs name the version.

ReplicaSetowned by the Deployment

  • The uid pins the reference to one object. A new object that reuses the name does not match.
  • controller: true marks the single managing owner.
  • The docs: "Cross-namespace owner references are disallowed by design."
  • Read it upward to find the parent of any child.

The garbage collector deletes children
when the owner goes

Background default

The owner goes first. The garbage collector removes the children afterwards.

--cascade=foreground

The garbage collector removes the children that block deletion before the owner.

--cascade=orphan

The children stay. The garbage collector removes their owner references.

Delete the custom resource, not its children. The tree goes with it.

A child without an owner reference
becomes a silent orphan

kubectl get deployment orion-media -n media -o yaml metadata: ownerReferences: - kind: MediaTenant name: orion controller: true kubectl get deployment vega-media -n media -o yaml metadata: (no ownerReferences)
  • Delete the logical parent and the garbage collector has nothing to follow. The child runs on, and no error appears.
  • Find orphans by comparing a suspect child with a managed sibling.
  • The reverse case: a reference to a deleted owner's uid. The dependent "is subject to deletion once all owners are verified absent".

A finalizer holds an object until cleanup finishes

You delete the objectthe finalizer key is in metadata.finalizers
The API server sets deletionTimestampit keeps the object and returns 202 Accepted
The controller runs its cleanupfor example, it deregisters an external resource
The controller removes its keythe list in metadata.finalizers is empty
The API server deletes the objectcascading deletion of the children follows
  • Owner references handle the cascade. Finalizers handle cleanup that must finish first.
  • The object reads Terminating while it waits.
  • Its children keep running, because the cascade starts only when the owner is gone.

A delete that hangs points at a missing controller

kubectl describe mediatenant vega -n media Metadata: Deletion Timestamp: 2026-10-30T12:00:00Z Finalizers: polyphone.example/media-cleanup kubectl get deployment tenant-operator -n platform NAME READY tenant-operator 0/0

Restore the controller

It runs its cleanup and removes its own key.

Patch the key by hand

The object disappears at once. The cleanup is skipped, so an external resource can leak.

Deleting a CRD deletes its custom resources

The docs: "When you delete a CustomResourceDefinition, the server will uninstall the RESTful API endpoint and delete all custom objects stored in it."

  • Every tenant of that type disappears with the CRD.
  • A chart uninstall that removes the chart's CRDs has the same effect.
  • Back up the custom resources first.
  • Uninstall in order: delete the custom resources, wait for the finalizers to clear, then remove the controller and the CRD.

CRDs and operators: key rules

  • A CRD adds a type. An operator is a custom controller plus its CRD, and the loop is level-triggered.
  • A schema rejects invalid objects and prunes unknown fields without an error.
  • Pod status is not reconciliation status. Read .status, the children, and the logs.
  • The garbage collector follows owner references. A missing reference leaves an orphan.
  • A finalizer holds an object until its controller cleans up. Restore the controller before you patch the key.
