Policy &
Ingress

Two controls that shape the traffic the Service layer leaves wide open — NetworkPolicy for east-west segmentation, Ingress for the north-south HTTP front door — and the failure signatures each adds.

Both fail quietly, in ways the top-line objects don't show. A policy drop hangs to a timeout; an Ingress with no controller routes nothing. The client's error names the class; the policies and rules name the spot.

What you'll walk away with

  • NetworkPolicy's switch — a Pod is default-allow until a policy selects it, then default-deny for that direction; every later policy only adds
  • Reading a policy — podSelector (who it governs), policyTypes (directions), and the from/to peers and ports
  • Peer semantics — podSelector is namespace-local, namespaceSelector reaches across, and the two in one element are an AND
  • The egress-breaks-DNS trap — and that enforcement is the CNI's job, not the API server's
  • Ingress — an L7 router that's inert until a controller claims it by IngressClass
  • Two new failure branches — a silent timeout (policy drop) and 404/503 (Ingress)

Two axes of traffic:
east-west and north-south

The two controls are independent. A request from the internet becomes east-west Pod traffic the moment the controller forwards it.

A NetworkPolicy can block the second hop even when the Ingress is perfect — the two are enforced separately.

A policy is a whitelist that
switches on when it selects a Pod

Before any policy selects a Pod, everything is allowed. The instant one does — even a policy that allows a single source — that Pod is default-deny for the covered direction.

Read a policy the way
you read a Service

  • podSelector — which Pods it governs; empty {} is every Pod in the namespace
  • policyTypes — the directions it controls: Ingress, Egress, or both
  • rules — the allowed peers under from/to and the ports they gate

A direction named with no matching rules means "deny all that way." That is the canonical baseline.

A default-deny for ingress

# selects every Pod, names a direction, # lists no rules -> denies all ingress kind: NetworkPolicy spec: podSelector: {} # every Pod policyTypes: [Ingress] # ...no rules

Default-deny is the baseline;
allows only ever add

Default-deny

A policy that selects Pods and names a direction with no rules. The baseline you then open specific holes in.

Additive-allow

Multiple policies on one Pod are unioned — a connection is allowed if any of them allows it. Nothing subtracts; there is no deny rule.

Isolation comes from the absence of an allow, never from a deny. You can write "allow X" and "allow Z" — never "allow X but not Y."

On a plugin that doesn't implement policy (e.g. plain Flannel), your default-deny is a stored object that changes nothing — a false sense of security only a real connectivity test exposes. Confirm CNI support before you trust isolation.

Three kinds of peer

A peer is the other end of an allowed connection. Mixing them up is the most common way a policy that looks right still drops traffic.

podSelector

Pods in the policy's own namespace matching these labels. Does not reach across namespaces.

scopenamespace-local

namespaceSelector

Pods in any namespace whose labels match. Every namespace carries kubernetes.io/metadata.name as a handle.

scopecross-namespace

ipBlock

A CIDR range, for traffic whose source isn't a Pod — external clients, node IPs, a VPN range.

scopenon-Pod IPs

One list element is AND;
two elements are OR

# namespace handle is the auto-label # kubernetes.io/metadata.name: <namespace> # AND -- one element, both selectors must match from: - namespaceSelector: { matchLabels: { ..name: app-services } } podSelector: { matchLabels: { app: sip-app } } # OR -- two elements, a union (either matches) from: - namespaceSelector: { matchLabels: { ..name: app-services } } - podSelector: { matchLabels: { app: sip-app } }

The classic silent bug: allowing a Pod from another namespace with a bare podSelector. It matches nothing — a bare podSelector never leaves the policy's namespace. Cross-namespace allow always needs a namespaceSelector.

Lock down egress and you
block the Pod's own DNS

DNS is egress too. A Pod resolving a name sends a packet to CoreDNS on port 53; an egress policy that doesn't allow it makes every lookup time out.

# every egress lockdown needs this companion allow egress: - to: - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } } ports: - { protocol: UDP, port: 53 } - { protocol: TCP, port: 53 }

The symptom looks like "DNS is broken" in kube-system when the block is a policy in your own namespace. Reach for ingress isolation first — lower blast radius; add egress only once you've enumerated what the workload calls, DNS included.

An Ingress is inert
until a controller claims it

A Service is acted on by kube-proxy, which every cluster runs. An Ingress needs an Ingress controller — an ordinary workload someone installs, and many clusters don't have one.

The link is the IngressClass — ingressClassName selects which controller claims the object. Set none and, unless a controller is marked default, nobody claims it. No ADDRESS in get ingress means no controller took ownership.

404 — no rule matched

The request reached the controller but no rule matched its host or path — wrong host, wrong pathType, a typo in path.

503 — backend broken

A rule matched, but the backend Service is missing, has no Ready endpoints, or the rule's port doesn't match one the Service exposes.

Reading 503 vs 404 tells you which half to inspect. An Ingress inherits every Service failure mode — the rule is only as good as the Service and port it names.

What to carry forward

  • A NetworkPolicy is a whitelist that switches on the instant it selects a Pod. No policy = default-allow; the first to select a Pod makes it default-deny for that direction. Isolation is the absence of an allow, never a deny.
  • Policies are additive and CNI-enforced. Unioned across policies; nothing subtracts. A policy on a non-enforcing CNI is a stored no-op — verify support before trusting isolation.
  • Cross-namespace allow needs a namespaceSelector. A bare podSelector is namespace-local; the two in one element are an AND. And egress lockdown must allow kube-dns:53, or every lookup times out.
  • An Ingress is inert without a controller. It's an L7 routing spec a controller claims by IngressClass; no ADDRESS = nobody claimed it. It's only as good as the backend Service and port it names.
  • The differential now has six branches. NXDOMAIN · empty-endpoints · connection refused · timeout (policy drop) · 503 (Ingress backend) · 404 (no rule matched).
