Networking II:
NetworkPolicy and Ingress

Two controls shape traffic that a Service leaves open. Each fails in a quiet way that the top-level objects do not show.

NetworkPolicy splits the flat pod network into lanes. Ingress routes outside HTTP to Services.

The default pod network is flat

Without a policy

Any pod can open a connection to any other pod in any namespace.

riskone compromised pod reaches the database directly
auditno object proves who may reach what

With NetworkPolicy

A namespaced list of allowed traffic. The network plugin enforces it.

trafficpod to pod, at L3 and L4
scopeone namespace; allow rules only

A pod is isolated one direction at a time

The word Ingress with a capital I names the routing object. Lowercase ingress names the direction.

  • A policy isolates a pod for ingress when it selects the pod and lists Ingress in policyTypes. Egress works the same way.
  • A direction that no policy selects stays open.
  • A policy that lists only Ingress leaves egress open.

A default-deny has no rules;
policies only add

kind: NetworkPolicy metadata: name: default-deny-ingress spec: podSelector: {} policyTypes: [Ingress]
  • An empty podSelector selects every pod in the namespace.
  • The policy lists no allowed source, so every pod is isolated for ingress.
  • Policies on one pod combine as a union. Order does not matter.
  • No deny rule exists. Isolation comes from the absence of an allow.

The node is always allowed

An ingress-isolated pod still accepts connections from its own node. Kubelet probes come from the node, so a deny-all policy does not fail readiness.

Policy sees L4 only

Policy covers TCP, UDP and SCTP. For other protocols, such as ICMP, the behavior depends on the network plugin.

The network plugin enforces policy;
a drop is a silent timeout

No enforcing plugin

The API server stores the policy. Nothing acts on it. A default-deny changes nothing.

testone allowed call and one denied call

Enforcing plugin

Most plugins discard the packet. No reset returns, so the client waits for a timeout.

signaturetimeout with DNS, endpoints and pods healthy

A new pod can start for a moment before the plugin applies its policy. Applications must tolerate that window.

One list entry means AND;
two entries mean OR

AND: sip-app pods that are also in app-services

from: - namespaceSelector: matchLabels: {...} podSelector: matchLabels: {app: sip-app}

OR: any pod in that namespace, plus sip-app pods here

from: - namespaceSelector: matchLabels: {...} - podSelector: matchLabels: {app: sip-app}

When in doubt, run kubectl describe on the policy. It shows how Kubernetes read the list.

A cross-namespace allow needs
a namespaceSelector

podSelector alone

Selects pods in the policy's own namespace. It never crosses a namespace.

Selects all pods in the namespaces whose labels match.

Selects a CIDR range. Use it for cluster-external addresses, not for pod IPs.

A bare podSelector that names a pod in another namespace allows nothing, and no error appears.

With ingress-nginx, an unclaimed Ingress shows no ADDRESS. Other controllers report status in their own way.

Read the status code to name the half that broke

CodeMeaningInspect
404No rule matched the host and paththe rule's host, path and pathType

These are ingress-nginx behaviors. Other controllers can differ. A direct call to the Service tells you whether the backend is at fault.

pathType decides how a path matches

pathTypeMatches

A rule with Exact and path / matches only /. A request for /index.html gets a 404 while the backend would serve it.

Recap

  • A policy is a whitelist that switches on when it selects a pod for a direction. No deny rule exists.
  • Policies add up, and both ends must allow. The pod's own node is always allowed.
  • Peers are exact. A cross-namespace allow needs a namespaceSelector.
  • Egress isolation needs a DNS allow. Names fail while IP calls work.
  • An Ingress is inert without a claiming controller. 404 means no rule matched. 503 means the backend failed.

Production thinking

  • A review locks a namespace to "only its own pods, plus DNS". Half the workloads fail in a minute. What did the egress half break first, and what is the smallest allow that restores a working, isolated namespace?
  • Every namespace has tidy policies, and someone says traffic is segmented. Which test shows the policies are enforced, and which cluster property would make all of them a no-op?
  • A shared Ingress returns 503 for about 30 seconds after each deploy, then recovers. Which interaction of rolling updates, readiness and endpoints causes it?
