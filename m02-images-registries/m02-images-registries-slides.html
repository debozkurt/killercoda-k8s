What an image actually is

Before a Pod can name one, it helps to know what's inside.

TermWhat it is
imageA read-only bundle of filesystem layers plus a config, addressable by content. What a container is started from.
layerOne set of filesystem changes (a diff). Layers stack to form the root filesystem; each is read-only and content-addressed, so it can be shared and cached across images.
configThe image's metadata — entrypoint, default command, env, working dir. The "how to run it" half of the image.
manifestThe registry document listing an image's layers and config by digest. A manifest list (image index) maps platforms — amd64/arm64 — to per-platform manifests.
containerA running process started from an image: its read-only layers plus a thin writable layer on top.

How layers stack into a container

An image is built in layers; the runtime stacks them — like a protocol stack — and adds a writable layer on top.

writable container layerread-write · per container
Image · read-only
app codelayer · sha256:…
runtime & dependencieslayer · sha256:…
base OS — libc, /bin, /liblayer · sha256:…
+ config: entrypoint · cmd · env · workdir

Image = layers + config

Read-only and content-addressed — each layer has its own digest. Identical layers are shared and cached across images.

Container = image + a writable layer

The runtime union-mounts the read-only layers and adds one thin writable layer on top (copy-on-write). Many containers share the same read-only layers.

Because layers are immutable, a pull fetches only the ones the node doesn't already have — the rest come from cache.

Tags move; digests don't

:1.4.2 — a tag

A mutable, human-friendly name. The registry resolves it to a digest, and that digest is what actually gets pulled.

Push new bytes under the same tag and it repoints — later pulls get different content. :latest moves constantly.

@sha256:… — a digest

The SHA-256 of the image's manifest — an immutable content address that names exactly those bytes, forever.

Change the content and the digest changes. There's nothing to repoint, and no lookup that can drift.

Production pins by digest: every node, every restart, every region runs byte-identical code. The cost — a wrong digest fails closed with manifest unknown, the safety feature working, not a bug.

Before pulling, this decides whether the kubelet should — and whether it trusts the node's cached image.

If you don't set it

Kubernetes picks the default from the reference:

  • a :latest tag, or no tag, defaults to Always
  • any other tag, or a digest, defaults to IfNotPresent

A moving tag gets re-checked every time; a pinned reference can trust the cache, since the cache can't be wrong about immutable content.

ErrImageNeverPull

Never, on an image the node has never cached — the kubelet refuses to pull, so the Pod stalls before it starts.

That makes it distinct from ImagePullBackOff: no pull was even attempted. The read is "wouldn't pull" versus "couldn't pull".

An imagePullSecret authenticates the pull

Public images pull anonymously. A private registry demands credentials — an anonymous pull gets 401 Unauthorized.

# a Secret of type kubernetes.io/dockerconfigjson kubectl create secret docker-registry regcred \ --docker-server=<registry-host> \ --docker-username=<user> --docker-password=<pass> -n <ns>

Then reference it — spec.imagePullSecrets, or attach it to the Pod's ServiceAccount.

Namespaced and host-matched. A secret in one namespace does nothing for a Pod in another, and --docker-server must match the image's registry host exactly.

Silent until a pull happens. Running Pods hold cached images; the page comes when something restarts and re-authenticates. Blast radius — everything that restarts.

The kubelet hits these in order — policy, reachability, auth, resolution. The first gate that fails is the one in your events.

The container never ran, so there are no logs. The signal is the event message, not kubectl logs.

ImagePullBackOff is just "tried, failed, backing off" — the reason is in the events, never in that status word.

# the status only tells you it's wedged kubectl get pod <pod> -n <ns> NAME READY STATUS RESTARTS app-0 0/1 ImagePullBackOff 0 # the reason is one line down here kubectl describe pod <pod> -n <ns> # → Events Failed to pull image "…": 401 Unauthorized

Same instinct as any stuck workload: get → describe → read the event. Never "just restart" an ImagePullBackOff before reading the message.

Signing / scanning

Produce trust info keyed by the digest. Neither blocks anything on its own.

Admission

The enforcement point — rejects unsigned or unscanned images before a pull. A separate concern.

Mirrors / caches

Live in the runtime (hosts.toml), not the Pod spec. The image string is unchanged.

Diagnostic tell: a pull that differs node-to-node with an identical spec points at runtime config, not the Pod.

What to carry forward

  • A reference is registry/repository:tag@digest. Tags are mutable pointers; digests are immutable content addresses — pin by digest for "the exact same bytes everywhere".
  • imagePullPolicy decides whether to pull: Always re-checks, IfNotPresent/Never trust the cache. Default: Always for :latest, IfNotPresent otherwise.
  • Private registries need an imagePullSecret — namespaced, host-matched, and silent until a Pod restarts.
  • The differential: ErrImageNeverPull = policy · no such host = unreachable · 401 = auth · manifest unknown = bad reference.
  • The status says stuck; the event says why — read it first. Signing, scanning, and mirrors live around the pull, enforced elsewhere.
