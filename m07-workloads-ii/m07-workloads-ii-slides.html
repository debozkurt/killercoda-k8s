Workloads II
StatefulSets & DaemonSets

The two workload controllers a Deployment can't replace — one gives each Pod a durable name, its own disk, and a strict startup order; the other pins one Pod to every node.

Both trade the Deployment's interchangeable-replica model for a stronger guarantee — and both fail in ways a Deployment never does. Both fail quietly, with the Pods still up.

What you'll walk away with

  • StatefulSet — stable ordinal identity, a per-Pod DNS record, and per-Pod storage: the three guarantees a Deployment deliberately withholds
  • The governing headless Service — why a StatefulSet depends on it, and the NXDOMAIN failure when it's missing
  • OrderedReady — the ordered lifecycle, and how one un-ready Pod stalls every ordinal behind it
  • DaemonSet — one Pod per eligible node, where eligibility is set by selectors/affinity and taint tolerations
  • desiredNumberScheduled — reading it as a coverage check when an agent silently skips a node
  • Reaching for the right one — most workloads stay Deployments; these are the specific exceptions

Right for a stateless tier; wrong for a store, a broker, or a registrar cache — where a specific member owns specific data and peers address it by name. Two controllers answer that need.

A StatefulSet pins three things
a Deployment leaves loose

Identity

Pods are named by ordinal — <name>-0 through <name>-(N-1) — not a random hash.

durablekill <name>-0, its replacement is also <name>-0

Network

A headless Service publishes a per-Pod DNS record that follows the ordinal.

resolves<pod>.<svc>.<ns>.svc.cluster.local

Storage

A volumeClaimTemplate stamps one PVC per ordinal; it re-binds to that ordinal every time.

stickyreschedule and it re-mounts its data

Having a PVC does not mean you need a StatefulSet. Reach for one only when the workload needs one of these three — otherwise a Deployment is simpler and rolls out faster.

Ownership creates; identity attaches

The controller creates each Pod (solid) — delete one and it returns with the same name. The headless Service and per-ordinal PVC attach identity that tracks the ordinal, not the Pod instance.

Under the default OrderedReady policy the controller also enforces order — Pod-1 is not created until Pod-0 is Ready.

Stable network identity is the Service's job —
and the Service is yours to create

The controller does not create the governing Service. You do — and it must be headless (clusterIP: None).

Headless Service present

Cluster DNS publishes a per-Pod A record. pod-0.svc.ns resolves to ordinal 0, so peers discover each other specifically rather than through a shared VIP.

Missing, misnamed, or a ClusterIP

The Pods still start and run — but the per-Pod DNS records never appear, so every peer lookup returns NXDOMAIN and the cluster can't form.

The Pods look healthy; the membership is broken. You catch this by resolving a name, not by waiting for a crash.

OrderedReady: Pod-0 gates the whole set

The controller creates <name>-0, waits for it to be Running and Ready, then creates <name>-1, and so on. Scale-down runs in reverse.

Create Pod-0wait until Running and Ready
Create Pod-1only after Pod-0 is Ready
Pod-0 never Readythe gate never opens — Pod-1 and Pod-2 are never created
# the whole set stalls behind one Pod kubectl get statefulset NAME READY 0/3 kubectl get pods NAME READY STATUS sts-0 0/1 Running # sts-1 and sts-2 do not exist

One Pod and two absences — not three crashing Pods. Fix Pod-0's readiness and the rest unblock. podManagementPolicy: Parallel removes this gate while keeping stable names and storage.

Updates run in order too

The same reverse-ordinal discipline governs rollouts when the Pod template changes.

RollingUpdate default

Replaces Pods in reverse ordinal order, one at a time, waiting for each to go Ready before the next.

partition

Only ordinals >= the value update; lower ones stay on the old revision — a canary you widen by lowering the number.

OnDelete

Opts out of automation. The controller applies the new template to a Pod only when you delete that Pod by hand.

A StatefulSet does everything in order — a feature you exploit for staged rollouts and a constraint you respect when one wedges.

A DaemonSet belongs to the node,
not to a replica count

You don't set replicas. The controller watches the node list and keeps exactly one Pod on every node that qualifies — the node set is the count.

The only question a DaemonSet asks is which nodes count. Used for node-local agents: log shippers, CNI/CSI plugins, node exporters, edge proxies.

Eligibility decides coverage;
DESIRED reports it

For each node the controller applies the scheduler's rules: the Pod's nodeSelector/affinity must match the node's labels, and the Pod must tolerate the node's taints.

kubectl get daemonset NAME DESIRED CURRENT READY AVAILABLE agent 2 2 2 2

DESIRED counts the eligible nodes — those the Pod can actually land on — not the number of nodes in the cluster.

When DESIRED and your node count disagree, coverage is the story. A node the Pod can't tolerate is not a candidate, so it isn't counted.

A missing toleration
silently drops a node

There's no Pending Pod to trip over. An untolerated node simply isn't a candidate, so no Pod is ever created for it and nothing goes red.

# a 2-node cluster; the agent lacks the control-plane toleration kubectl get daemonset node-agent NAME DESIRED CURRENT READY node-agent 1 1 1 # one node, not two — no error

The controller auto-adds tolerations for transient node-condition taints (not-ready, unreachable, memory/disk/PID pressure) — but not the control-plane taint; you add that yourself. When DESIRED is below your node count, compare the Pod's tolerations against the missing node's taints.

What to carry forward

  • A StatefulSet nails down what a Deployment leaves loose — ordinal names, a per-Pod DNS record, and a per-Pod PVC, all sticky to the ordinal. Use one only when the workload needs one of the three.
  • Stable network identity is the headless Service's job, and the Service is yours to create. Miss it and the Pods run while every per-Pod name returns NXDOMAIN.
  • OrderedReady means Pod-0 gates the whole set. READY 0/N with only Pod-0 present is one un-ready Pod blocking every ordinal behind it — a Deployment never fails this way.
  • A DaemonSet guarantees one Pod per eligible node. desiredNumberScheduled counts only reachable nodes, so it's your coverage check — read tolerations against the missing node's taints.
  • These controllers fail quietly — no crash, no Pending. You catch the failure by verifying the guarantee, not by waiting for something to go red.
