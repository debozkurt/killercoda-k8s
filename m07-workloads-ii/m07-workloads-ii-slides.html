StatefulSets and DaemonSets:
Pods with an identity or a node

Check that the guarantee held, because these controllers fail without a red status.

Focus: ordinal names, per-Pod DNS, claims, ordered rollout, and one Pod per eligible node.

Objectives

  • State the three guarantees a StatefulSet adds to a Deployment.
  • Trace the headless Service that serves per-Pod DNS names.
  • Explain why one un-Ready Pod stalls an OrderedReady set, and why a template fix does not repair it.
  • Contain a bad update with reverse-ordinal order and partition.
  • Read DESIRED on a DaemonSet as a coverage check.

Each controller guarantees something different

A Deployment treats its Pods as interchangeable. Two kinds of workload need more.

ControllerGuaranteePod namesQuiet failure
DeploymentA number of Pods, anywhererandom suffixnot applicable
StatefulSetNamed Pods, each with its own claim, created in order<name>-<ordinal>no DNS record; a stalled rollout
DaemonSetOne Pod per eligible node<name>-<random>a node with no Pod

Use a Deployment unless the workload needs a stable name, per-replica storage, ordered rollout, or a Pod on each node.

RollingUpdate replaces Pods
from the highest ordinal down

kubectl get pods -l app=session-store -L controller-revision-hash NAME READY STATUS HASH session-store-0 1/1 Running 6d4f9 session-store-1 1/1 Running 6d4f9 session-store-2 0/1 ImagePullBackOff 75b8c
  • The controller replaces ordinal 2 first. If it never goes Ready, the update stops.
  • Ordinals 0 and 1 keep the old revision and keep serving.
  • partition limits the update to ordinals at or above it. Lower ordinals "will be recreated at the previous version."
  • With partition: 2 on three replicas, only ordinal 2 updates. Lower the partition to widen the canary.

A template fix does not replace an un-Ready Pod

You correct the templateThe spec changes.
The controller checks each Pod it createdEvery Pod must be Running and Ready.
One Pod is un-Ready, so the controller stopsIt never reaches its update step.
You delete that PodThe Pod ran the bad template.
The controller recreates itThe new Pod uses the corrected template.

The docs: "it's possible to get into a broken state that requires manual intervention to repair."

  • The rule covers a creation stall and a halted update.
  • The docs scope it to OrderedReady.
  • Repair in two steps: correct or revert the template, then delete the Pod.

DESIRED counts eligible nodes

kubectl get daemonset -A NAMESPACE NAME DESIRED CURRENT READY edge sbc-edge 2 2 2 edge rtp-probe 1 1 1 media disk-exporter 0 0 0
  • DESIRED against the nodes the agent belongs on checks coverage.
  • DESIRED against READY checks Pod health. A shortfall there is a Pod problem.

The correct DESIRED is not always the node count. An agent for fast-disk nodes should match the number of fast-disk nodes.

Coverage gap, cause one:
a taint the Pod does not tolerate

kubectl describe nodes | grep -E '^Name:|^Taints:' Name: control-plane Taints: node-role.kubernetes.io/ control-plane:NoSchedule Name: worker Taints: none

The control-plane node is eligible only with an explicit toleration. Without it, DESIRED is one short.

The controller adds these tolerations to every DaemonSet Pod:

The control-plane taint is not in the list. Add that toleration yourself.

StatefulSets and DaemonSets: key rules

  • A StatefulSet ties a name, a DNS record, and a claim to each ordinal. You create the headless Service.
  • Under OrderedReady, an un-Ready Pod blocks the controller, including its repair of that Pod. Correct the template, then delete the Pod.
  • Reverse-ordinal order and partition limit a bad update to the highest ordinals.
  • A DaemonSet creates one Pod per eligible node. DESIRED is the coverage check.
  • Running is not identity, and a rollout of zero Pods is not coverage. Verify that the guarantee held.
