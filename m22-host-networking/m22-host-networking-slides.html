Host networking
& multi-NIC

The four deliberate ways a Pod steps off the default pod network to reach the node's own interfaces and ports — and the convenience each one trades away.

A Pod is on the pod network unless it opts out. Every escape hatch un-hides the node in one specific way, and gives up one specific piece of platform convenience to do it.

What you'll walk away with

  • The four overrides to the default pod network — hostNetwork, hostPort, a second NIC via Multus, and NodePort exposure — and what each un-hides
  • Why a hostNetwork Pod's IP is the node IP, and why it loses cluster DNS without ClusterFirstWithHostNet
  • How hostPort maps one node port through portmap, and why that port becomes a scheduling resource
  • How Multus attaches a second interface from a namespaced NetworkAttachmentDefinition — and the namespace trap that hangs it
  • How externalTrafficPolicy trades the client's source IP against reachability on a NodePort

Every Pod answers one question:
whose network am I on?

The default answer is "my own." Host networking is four narrow overrides — read each branch as a trade, not a feature.

The default: one interface,
wired by a CNI plugin

When the kubelet starts a Pod it calls a CNI plugin to build its network namespace: an IP from the pod range, a single eth0, every Pod reachable without NAT. The node's own interfaces are invisible to it.

CNI is a chain, not one plugin — the kubelet runs the default plugin for eth0, then more links do narrower jobs. That chain is what makes the escape hatches possible.

Core Kubernetes

hostNetwork (a Pod-spec field) and NodePort (a Service type) — no plugin needed.

Extra links in the chain

hostPort via the portmap plugin, and a second NIC via Multus — CNI plugins doing jobs the default one doesn't.

hostNetwork: true — the Pod
shares the node's stack

The bluntest override: the Pod gets no network namespace of its own — it shares the node's. A process that binds a port inside the container is binding it on the node, reachable at the node's address with no Service in front.

e.g. a high-throughput RTP relay uses it for the kernel's UDP path straight to the wire — no overlay encapsulation, no extra hop.

hostNetwork silently drops
cluster DNS

dnsPolicy defaults to ClusterFirst — and ClusterFirst is ignored on the host network.

Default dnsPolicy

The kubelet hands the Pod the node's /etc/resolv.conf. It knows nothing about svc.cluster.local, so no in-cluster Service resolves by name.

The Pod is Running; only Service DNS is broken — while every other Pod resolves fine.

ClusterFirstWithHostNet

"ClusterFirst, and yes I know I'm on the host network." One field points the resolver back at CoreDNS.

The rule to carry: any hostNetwork Pod that talks to cluster Services needs ClusterFirstWithHostNet. Check dnsPolicy before you suspect CoreDNS.

hostPort publishes one node port
through portmap

The surgical version of the same idea. A container port declares hostPort: 5060, and portmap writes a node DNAT rule — while the Pod keeps its normal pod-network IP. One port published; nothing else changes.

node :5060

portmap DNAT→
container :5060
Pod keeps its pod IP

A hostPort is a node-level resource, tracked like CPU or memory. One Pod per node per port — a second stays Pending with didn't have free ports; a DaemonSet using one is capped at one Pod per node.

Multus attaches a second interface
from a NAD

A media plane sometimes wants two interfaces — eth0 on the pod network for control, and a dedicated second interface for media on its own L2. Multus is a meta-CNI: it runs the default plugin, then attaches the extras.

Pod
eth0pod network · control
net1macvlan · media L2
Multus runs the default plugin for eth0, then attaches net1 from a NetworkAttachmentDefinition

A NAD is a namespaced custom resource whose spec.config is a plain CNI JSON block.

A Pod requests one by annotation k8s.v1.cni.cncf.io/networks. Multus itself moves no packets — it delegates to macvlan or ipvlan.

A bare NAD name resolves
in the Pod's own namespace

The same trap as cross-namespace DNS — a NAD is a namespaced object.

Bare name, wrong namespace

A Pod in edge asks for bare rtp-macvlan, but the NAD lives in media. Multus can't find it, sandbox creation fails.

resultstuck ContainerCreating — never Running

externalTrafficPolicy trades
source IP against reachability

A NodePort opens a fixed port on every node; the policy decides what a node does when the backing Pod is elsewhere.

Cluster default

reachevery node — forwards cluster-wide
no local podSNAT + extra hop to a Pod elsewhere
source IPhidden — the Pod sees the node's IP

Local

reachonly nodes with a local endpoint
no local podsilently drops the traffic
source IPpreserved — nothing SNATs it

Local with a single-replica backend is a per-node blackhole — while get svc and the EndpointSlice look healthy. Keep an endpoint on every node (a DaemonSet or topology spread), or switch to Cluster.

What to carry forward

  • A Pod is on the default pod network unless it deliberately steps off — four narrow overrides, each trading one convenience. Diagnose by asking which convenience did this hatch give up.
  • hostNetwork makes the Pod IP the node IP and takes cluster DNS with it — needs ClusterFirstWithHostNet, or it's Running but blind to svc.cluster.local.
  • hostPort publishes one node port via portmap and spends a node scheduling slot — one Pod per node per port.
  • Multus adds interfaces from a namespaced NAD by annotation — a bare name resolves in the Pod's namespace; wrong namespace hangs it in ContainerCreating.
  • A NodePort's externalTrafficPolicy is a source-IP-vs-reachability choice — Local plus a single-node backend is a per-node blackhole behind a healthy-looking Service.
