Resilience & Autoscaling

How Kubernetes keeps a service available while the world changes underneath it — demand rising and falling, versions shipping, nodes draining — and the ways each control quietly stops protecting you.

Availability isn't a property a service has; it's one Kubernetes actively maintains against a stream of change. Each control is quiet when healthy and quiet when broken — the skill is reading its state directly, not waiting for the downstream page.

What you'll walk away with

  • Three kinds of change — demand, version, disruption — each with one control, and each with a failure that stays silent until that change arrives
  • Reading an HPA — how it turns a metric into a replica count, why CPU is measured as a percentage of the request, and why a missing request leaves it at <unknown>
  • The four autoscalers — HPA (count), VPA (size), Cluster Autoscaler / Karpenter (nodes), KEDA (events) — which axis each one moves
  • Rolling updates and rollback — maxSurge / maxUnavailable, the two-ReplicaSet handoff, and why a bad release stalls instead of crashing
  • PodDisruptionBudgets — allowed disruptions, the eviction API, and the budget that blocks a drain forever
  • Graceful shutdown — endpoints out, preStop, SIGTERM, grace, SIGKILL — and how the three controls compose into lossless change

Three kinds of change;
one control absorbs each

Resilience is Kubernetes absorbing change so the service doesn't feel it. Demand, version, and disruption each hit a running fleet, and each has one control that keeps availability flat while it happens.

Each control has a signature failure that stays silent until its change arrives — a broken HPA looks fine until the surge, a bad budget until the drain, a stuck rollout until you notice the new version never landed. Read the control's own state.

The HPA is a control loop
that moves the replica dial

About every 15 seconds it reads a metric for the target workload, computes a desired replica count, clamps it to the configured bounds, and sets the Deployment's count.

The HPA doesn't create Pods — it moves the same replica dial you'd move by hand, and the change rolls out through the ordinary ReplicaSet machinery: desiredReplicas = ceil(currentReplicas × currentMetric ÷ target).

Utilization is usage ÷ request;
no request, no denominator

The HPA doesn't scale on raw CPU — it scales on utilization, usage expressed as a percentage of the container's request. metrics-server supplies the numerator; the request is the denominator.

Request set

Live usage divided by the request gives a percentage. The HPA compares it to the target and moves the count.

readsTARGETS shows e.g. 42%/50%
statusScalingActive=True

No request on the target

The arithmetic has no denominator. The HPA can't compute utilization, so it freezes at the current count — the metrics pipeline can be perfectly healthy.

readsTARGETS <unknown>/50%
statusScalingActive=False, FailedGetResourceMetric

This is the single most common reason an HPA silently doesn't scale, and it's entirely on the target side — the same request the scheduler reserves is the autoscaler's definition of 100%.

Four autoscalers,
four different axes

The HPA scales replicas, but that's only one axis. Reaching for the wrong one wastes an incident; the axes are orthogonal.

HPA — more replicas

Keeps a per-Pod metric near target by changing the count. The default for stateless request-serving workloads. Needs a request for resource metrics.

VPA — bigger replicas

Right-sizes the requests and limits from observed usage rather than multiplying Pods. For workloads you can't shard — a single big or stateful process.

Cluster Autoscaler / Karpenter — more nodes

Adds nodes when Pods are Pending for lack of room; drains idle ones. Scales the cluster, and pairs with the HPA.

KEDA — scale on events

Scales on external signals — queue depth, stream lag, cron — and can scale to zero when idle. Manages an HPA under the hood.

Don't run VPA and HPA on the same resource (both on CPU) — they fight, one growing Pods while the other multiplies them.

An old Pod is never retired until a new one is Ready — the invariant that lets the update proceed without dropping capacity.

A bad release stalls;
it does not take the service down

Because a Pod is never retired until its replacement is Ready, a broken new version — an image that won't pull, a crash, a readiness probe that never passes — can't roll forward. The old ReplicaSet keeps serving; the rollout hangs partway.

The stall

After progressDeadlineSeconds of no progress, the Deployment reports Progressing=False with ProgressDeadlineExceeded — a report, not an action. Kubernetes does not auto-roll-back.

The recovery

kubectl rollout undo re-applies the previous revision and rolls forward to it — a rollback is just a rolling update aimed at an older revision. Fix the release out of the hot path.

# the rollout blocks, then reports the stall — not a rollback kubectl rollout status deploy/<name> Waiting for rollout to finish: 1 old replicas are pending termination... error: deployment exceeded its progress deadline

A PDB paces voluntary disruption;
allowed disruptions is the number

A PodDisruptionBudget constrains only voluntary disruption — a drain, an upgrade, a scale-down — declaring how many replicas must stay up. The eviction API enforces it; kubectl drain evicts, it doesn't delete.

Room to move

2 healthy replicas, minAvailable: 1 → allowed disruptions is 1. Drain evicts one, waits for a fresh Pod elsewhere, then evicts the next.

minAvailable = replica count

Allowed disruptions is permanently 0. No eviction is ever permitted; the drain blocks forever — a budget that protects nothing because it protects everything.

# the whole story is one column kubectl get pdb NAME MIN AVAILABLE ALLOWED DISRUPTIONS AGE web 3 0 5m # drain will hang

Allowed disruptions = currentHealthy − desiredHealthy, floored at 0 — how many Pods the budget will let go right now.

What a PodDisruptionBudget
does and does not protect

A PDB is narrower than most people assume, and the gaps are where it bites.

Guards the eviction API

kubectl drain and the Cluster Autoscaler evict, so they respect it. A plain kubectl delete pod does not go through eviction — it deletes regardless.

Does not touch rolling updates

A rollout is bounded by maxUnavailable, not the PDB — separate systems. A rollout can briefly take more down than an eviction would allow.

Can't help involuntary loss

A crashed node takes its Pods with it; there's no eviction to check. For that you need enough replicas and spread to survive the loss.

Can starve maintenance

Because eviction strictly honors it, an over-tight budget turns a routine drain into an indefinite hang. A blocked drain is more often a bad PDB than a bad node.

Rule of thumb: express the budget as maxUnavailable when an HPA moves the replica count — a fixed minAvailable silently drifts between "block everything" and "protect nothing" as replicas scale.

The grace period is a budget

It's the app's window to finish cleanly. Long enough for the longest in-flight request to drain.

Where it drops traffic

Too short, or an app that ignores SIGTERM, and in-flight work is cut off mid-request.

What to carry forward

  • Resilience answers three kinds of change — demand, version, disruption — each with one control and a failure that's silent until that change arrives. Read the control's own state; don't wait for the downstream page.
  • An HPA scales on utilization = usage ÷ request. No request, no denominator — it reads <unknown> and freezes. The family splits by axis: count, size, nodes, events.
  • A rolling update fails safe: a bad release stalls, it doesn't crash the service. ProgressDeadlineExceeded flags the stall but never rolls back; rollout undo is the recovery.
  • A PDB paces voluntary disruption via the eviction API — allowed disruptions = currentHealthy − desiredHealthy. Set minAvailable at the replica count and it's 0, blocking maintenance. It does nothing for rollouts or involuntary loss.
  • Graceful shutdown makes each termination lossless — endpoints out, preStop, SIGTERM, grace, SIGKILL. The three controls compose; one misconfigured piece turns routine change into dropped traffic.
