Resilience and autoscaling:
capacity, versions, and disruption

Each control is quiet when healthy and quiet when broken. Read its own status.

Objectives

  • Name the three kinds of change and the control for each.
  • Read an HPA: the formula, utilization as usage divided by the request, and the path from desired count to running Pod.
  • Compute the bounds of a rolling update and read a stalled one.
  • Compute allowed disruptions and name each cause of a zero.
  • Trace graceful shutdown and find a Pod that ignores SIGTERM.

The Deployment scales a new ReplicaSet up and the old one down. Each template change is a revision.

A bad release stalls;
rollout undo recovers it

kubectl get deployment portal-web READY UP-TO-DATE AVAILABLE 2/2 1 2 kubectl describe deployment portal-web Progressing False ProgressDeadlineExceeded kubectl rollout undo deployment/portal-web kubectl rollout status deployment/portal-web successfully rolled out
  • ProgressDeadlineExceeded is a report. Kubernetes takes no action on a stalled Deployment.
  • With a larger fleet, the controller first retires up to maxUnavailable old Pods, so capacity dips before the stall.
  • rollout undo restores the Pod template only. A replica count set by an HPA stays.

A PodDisruptionBudget allows
current minus desired

kubectl describe pdb route-engine Min available: 1 Status: Allowed disruptions: 1 Current: 2 Desired: 1 Total: 2 allowed disruptions = current − desired (floored at 0)
  • Current counts healthy Pods. A healthy Pod is a Ready Pod.
  • Desired is minAvailable, or total − maxUnavailable. Percentages round up.
  • The budget limits voluntary disruption only. The eviction API enforces it.

A process with no SIGTERM handler
spends the whole grace period

kubectl delete pod announce-player-7d9f --wait=false kubectl describe pod announce-player-7d9f Status: Terminating (lasts 41s) Termination Grace Period: 45s kubectl delete pod announce-player-7d9f real 0m45.2s compare: a handled SIGTERM exits in 1-2 s
  • PID 1 receives SIGTERM only if it installed a handler. A shell wrapper that does not forward the signal has the same effect.
  • Each rollout step, each drain, and each delete waits the full period, then ends in SIGKILL (exit code 137).
  • Read the symptom as a duration. A shorter grace period caps the cost and does not cure the cause.

The three controls compose

Rolling update

Terminates Pods in batches, bounded by maxUnavailable.

PodDisruptionBudget

Caps how many Pods a drain removes at once.

Graceful shutdown

Decides whether each termination drops traffic.

One mistake in any control turns the same routine operation into dropped traffic or a hung maintenance window.

Resilience and autoscaling: key rules

  • Three kinds of change have three controls. Each fails silently until its change arrives, so read the control's own status.
  • An HPA scales on usage divided by the request. A desired count is not a running count.
  • A rolling update keeps replicas minus maxUnavailable Pods available, so a bad release stalls. Kubernetes never rolls back by itself.
  • Allowed disruptions is current minus desired. A zero comes from the floor, from unhealthy replicas, from the unhealthy-Pod policy, or from overlapping budgets.
  • Graceful shutdown is one grace period that starts at deletion. An app with no SIGTERM handler spends all of it.
