Secrets at scale:
reading the pipeline one link at a time

A plaintext Secret cannot live in Git, so at scale a controller produces each Secret from a source of truth. The failure surface moves out of the Pod and into that pipeline.

A Secret manifest is base64;
etcd stores Secrets unencrypted

In Git

A Secret manifest stores each value in base64, and base64 -d reverses it.

"Base64 encoding is not an encryption method, it provides no additional confidentiality over plain text."

Every clone holds the credential. A later rotation does not remove the old value from the Git history.

In etcd

"Kubernetes Secrets are, by default, stored unencrypted in the API server's underlying data store (etcd)."

Base64 is only the API's JSON encoding. In etcd the value is raw bytes inside a protobuf record.

Anyone who reads etcd, or an etcd snapshot, reads every credential.

Encryption at rest:
the API server encrypts before it writes

  • The API server reads an EncryptionConfiguration from --encryption-provider-config.
  • The first provider in the list encrypts new writes. Every listed provider can decrypt reads.
  • The identity provider means no encryption. A kms provider keeps the key in an external key management service.
  • Existing Secrets stay unencrypted until something rewrites them.
# rewrite every Secret through the API server kubectl get secrets --all-namespaces -o json | kubectl replace -f -

No provider configured

An etcd read shows the Secret's keys and values in clear text.

Provider configured

The stored value starts with k8s:enc:, and the rest is ciphertext.

Three delivery patterns

Each pattern keeps the plaintext value out of Git. A component in the cluster produces what the consumer reads.

Sync-from-store

The value lives in an external manager. A controller copies it into a Kubernetes Secret and refreshes it.

With the default Periodic refresh policy, ESO repeats the read every refreshInterval.

ESO reverts hand edits

A user edits the derived SecretThe edit changes the data hash that ESO records in an annotation.
ESO sees the changeESO also watches the derived Secret.

The Orphan creation policy turns this protection off.

To change a derived Secret, change the store value or the ExternalSecret.

Three links, three blast radii

LinkWhat breaksWhat fails
ReferenceA remoteRef names a key that the store does not haveThat one ExternalSecret
Store readThe store's credential or RBAC grant is goneEvery ExternalSecret that uses the store
Target writeThe controller cannot create or update Secrets in one namespaceEvery ExternalSecret in that namespace

The pattern of failures is the first clue. In all three cases the derived Secret is absent or stale, and the cause is upstream of the consumer.

Each SecretStore has its own identity

  • The SecretStore does not authenticate as the ESO controller. It uses the identity that you give it: a Vault role, a cloud workload identity, or a ServiceAccount.
  • With the Kubernetes provider, the reconciler checks read access with SelfSubjectRulesReview. When that fails, it falls back to SelfSubjectAccessReview.
  • If the check fails, the store's Ready condition goes False with the reason ValidationFailed.
kubectl get secretstore -A # read the shared store first kubectl auth can-i get secrets -n <backend-namespace> \ --as=system:serviceaccount:<ns>:<sa>

auth can-i sends a SelfSubjectAccessReview for one verb. Add --list to send the SelfSubjectRulesReview that ESO tries first.

ESO fails closed;
the outage starts at reschedule

The store credential expiresEvery sync against that store fails. A missing key produces no Secret, never a partial one.
Existing Secrets keep their last good valueRunning Pods keep working. No Pod reports an error.
A Pod restarts or a new Pod schedulesIt finds a Secret that never refreshed, or a new namespace finds no Secret at all.

Alert on the store's Ready condition and on the age of the last sync, not on Pod failures. Forty failing ExternalSecret objects that name one store are one incident.

Key renewal is not credential rotation

Sealing key renewal

The controller renews its sealing key every 30 days by default. It keeps the old keys, so old SealedSecret objects still decrypt.

Credential rotation

The credential values inside each SealedSecret stay the same. The README calls renewal "not a substitute for periodical rotation of your actual secret values."

Back up the sealing keys. A rebuilt cluster with new keys cannot decrypt anything in the repository.

SOPS encrypts the values;
Flux decrypts at apply time

  • SOPS encrypts the values in a YAML or JSON file and leaves the keys readable.
  • A diff shows which keys changed, never their values.
  • The encryption key comes from age, PGP, or a cloud KMS.
  • The Flux kustomize-controller decrypts when the Kustomization sets a decryption provider.
kind: Kustomization spec: decryption: provider: sops secretRef: name: <private-key-secret>

The key is absent, or is not a recipient of the file

The Kustomization reports Ready=False with the decryption error. The kustomize-controller applies no Secret.

Both encrypt-and-commit tools fail closed on a coupling: Sealed Secrets on scope, SOPS on the key. A broken coupling produces no Secret, never a wrong one.

Close the rotation gap by construction

Checksum annotation

A hash of the Secret on the Pod template works only when the deploy tool renders the Secret.

ESO writes the derived Secret later, outside the renderer, so the hash never changes.

Watcher controller

A controller watches the Secret and restarts its consumers when the Secret changes.

Directory mount and reload

Mount the whole directory, not a subPath. The application reloads the file when it changes.

During rotation, keep the old credential valid in the store until every consumer runs on the new one.

Secrets at scale: key rules

  • A Secret manifest is base64, and etcd stores Secrets unencrypted by default. At scale a controller produces each Secret, and encryption at rest protects the result on disk.
  • A derived Secret's failure story is in the producing object. Read its .status before the consumer's logs, and change the source, not the Secret.
  • The pattern of failures locates the link: one object means the reference, one store means the store, one namespace means the write grant.
  • Encrypt-and-commit fails closed on a coupling: Sealed Secrets on scope, SOPS on the decryption key.
  • Rotation has two steps: the pipeline updates the Secret, and the consumer adopts it. When the status is green, read what the process holds.
