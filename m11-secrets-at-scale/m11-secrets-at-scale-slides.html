Secrets at Scale

Why a plaintext Secret can't live in Git, and the two patterns that fix it — sync a secret in from an external store, or commit it encrypted and decrypt it in-cluster.

Both patterns turn a Secret into something a controller materializes — which moves the failure surface out of the Pod and into the pipeline that feeds it.

What you'll walk away with

  • Explain why a Secret is unsafe to commit — base64 is encoding, not encryption — and name the two GitOps-safe patterns: sync-from-store and encrypt-and-commit
  • Read the materialization pipeline — external source → controller → Secret → consumer Pod — and locate which link broke
  • Map the External Secrets Operator model onto that pipeline, and read an ExternalSecret's .status the way you'd read a Pod's
  • Recognize the encrypt-and-commit tools — Sealed Secrets and SOPS — and the coupling that breaks each
  • Work the differential: no Secret because the store is down, vs. the key is missing, vs. a Secret that synced fine but the consumer runs on a stale value after rotation

base64 is encoding, not encryption;
a plaintext Secret can't live in Git

A Secret stores its values base64-encoded, and base64 -d reverses that in one command. Commit the manifest and the credential is in the repository's history permanently — readable by everyone with clone access and every CI that checked it out.

Rotating the leaked value doesn't help; the old one is still in the history, and often still valid somewhere.

The wall every team hits at GitOps

The declarative model wants everything in Git. A Secret is the one thing that can't go there in the clear.

encodingreversible by anyone — base64 -d
historya git log is forever

Two ways out,
and every tool here is one of them

Sync-from-store

Don't put the secret in Git at all. Keep it in a purpose-built manager and let a controller pull it into the cluster, refreshed.

source of truththe external manager
toolsESO, Vault, cloud managers

Encrypt-and-commit

Put the secret in Git, but encrypted with a key the repo doesn't hold, and decrypt it inside the cluster.

source of truthGit, in a safe form
toolsSealed Secrets, SOPS

Both make the committed artifact safe: it names or encrypts the secret — it never holds it in the clear.

At scale, a Secret is the output of a pipeline,
not a leaf you write

The real secret lives outside the cluster — or encrypted in Git — and a controller turns that source into the Secret a Pod actually consumes.

The Secret is derived,
and the failure surface moved upstream

Two things follow. The Secret is derived — editing it by hand is pointless, because the controller reconciles it back to the source on the next pass. You change the source, not the Secret.

And a consumer stuck on a missing credential now has three new causes before you reach the Pod.

Three upstream causes before the Pod

sourcethe store was unreachable
referencethe key it named was wrong
accessthe controller wasn't allowed to read

Start at the object that was supposed to produce the Secret, and read its .status — not the Pod's logs.

Sync-from-store: a store says where,
an ExternalSecret says what

The External Secrets Operator splits the job. A SecretStore names the provider and how to authenticate. An ExternalSecret declares which remote keys to pull and which Secret to write.

The ExternalSecret is the GitOps-safe artifact: it names prod/database/password, it doesn't contain it — so it commits cleanly.

kind: ExternalSecret spec: secretStoreRef: name: polyphone-vault # where + how to auth target: name: db-credentials # the Secret ESO creates data: - secretKey: DB_PASSWORD remoteRef: key: prod/database # path in the store property: password # field within it

Read the producing object's .status,
not the consumer's logs

# healthy — the target exists and matches kubectl get externalsecret -n provisioning NAME READY STATUS db-credentials True SecretSynced # broken — it can't pull db-credentials False SecretSyncedError

The status names the failing step

An ExternalSecret carries a Ready condition. The reason tells you which link went dark.

store downprovider unreachable / unauthenticated
key missingthe remoteRef named nothing
transforma property or template failed

kubectl describe shows the provider's actual error.

A store is a shared dependency;
one broken identity downs them all

A SecretStore authenticates as an identity you give it, and that identity has to be allowed to read the backend. If the RBAC isn't there, the store's own Ready goes False — and every ExternalSecret under it fails at once.

A fan-out of errors that all name one store is one problem, not twenty. Go store-first.

kubectl auth can-i get secrets \ -n backend-ns --as=system:serviceaccount:...

Blast radius of one missing RoleBinding

The store they all lean on is down, so every sync under it goes dark together.

storeValidationFailed — not ready
sync Adb-credentials — StoreNotReady
sync Bpartner-api — StoreNotReady

The controller holds a private key and publishes the matching public key. kubeseal encrypts the values with the public key into a SealedSecret that only this cluster's controller can decrypt. Even someone holding the YAML can't read it — then the controller decrypts each into an ordinary Secret.

Strict scope, by default:
bound to one namespace and name

Same namespace and name

The controller recomputes the binding from the object's current namespace and name, it matches what was sealed, and it decrypts.

Moved or renamed

The binding no longer matches, so the controller refuses. No Secret is produced — the derived object never appears at all.

Strict scope is deliberate: it stops someone who can create objects in a namespace from copying your SealedSecret there to have the controller decrypt it for them. The signal is the controller log and the SealedSecret's own status.

SOPS encrypts values, not keys;
both patterns fail closed

Sealed Secrets — coupling: scope

Encrypts a whole Secret with the controller's public key. Breaks when the object's namespace or name changes.

SOPS — coupling: key

Encrypts the values in a YAML/JSON file — keys stay readable, so a diff shows which keys changed, never their values. A GitOps engine decrypts it at apply time with a key held in the cluster.

Both fail closed: a broken link — wrong scope, missing decryption key — produces no Secret, never a wrong-but-plausible one.

The floor under every pattern:
encryption at rest

Every pattern ends the same way — a Secret, base64 in etcd. That base64 is not encryption, so a stolen etcd snapshot or backup is every credential in the cluster, in the clear.

An EncryptionConfiguration on the API server encrypts Secret values before they hit etcd, ideally with an external KMS holding the key.

What to carry forward

  • base64 is not encryption, so a plaintext Secret can't live in Git. A controller materializes it one of two ways — sync-from-store or encrypt-and-commit; the committed artifact names or encrypts the secret, never holds it in the clear.
  • The Secret is a derived object, and the failure surface moved upstream. A missing Secret has causes before the Pod — source, reference, access. Read the producing object's .status, not the consumer's logs.
  • A store is a shared dependency. When its identity loses access, every ExternalSecret under it fails together — one problem, diagnosed store-first and confirmed with auth can-i --as=.
  • Encrypt-and-commit fails closed on a coupling — Sealed Secrets on scope, SOPS on the decryption key. Move or rename a SealedSecret and it stops decrypting: no Secret, not a wrong one.
  • Rotation is two steps, not one. The pipeline updating the Secret is not the consumer adopting it — an env-consumer stays frozen until it's rolled. A green status can sit above a workload on a stale credential.
