Module 01 · Workloads I

Pods, Deployments
& ReplicaSets

What a Pod is, how its lifecycle works, how the three probes decide “alive” and “ready,” and how graceful shutdown keeps a rollout from dropping in-flight work.

The Pod is the unit you operate — everything else is about getting Pods to run, stay healthy, and shut down cleanly.

Objectives

By the end of this module you can

  • Describe the Pod lifecycle — phases, container states, and how restartPolicy drives restarts
  • Distinguish the three probes — liveness, readiness, startup — by what each decides and what failing it does
  • Trace the Deployment → ReplicaSet → Pod owner chain and explain declarative reconciliation
  • Diagnose a CrashLoopBackOff and separate a real crash from a liveness probe killing a healthy container
  • Configure graceful shutdown so in-flight work drains instead of being killed mid-flight
  • Explain why the Pod, not the container, is the unit of scheduling
Why it matters

What goes wrong in practice

Liveness misfire

A liveness probe points at a path the app doesn’t serve. The kubelet restarts a healthy container into a crash loop.

Readiness on the wrong port

Every replica is quietly pulled from rotation. The Pods look fine; the Service has nowhere to route.

Grace period too short

terminationGracePeriodSeconds is shorter than the drain, so every rollout sheds a few live calls.

The probes and the shutdown sequence are the controls that keep a routine deploy invisible to callers.

Mental model

A Running Pod is not a healthy Pod

The phase is coarse. The detail lives in container state and the conditions — PodScheduled, Initialized, Ready. Probes are the inputs that flip Ready and trigger restarts.

  • A Pod can be Running and 0/1 READY for an hour — readiness fails
  • A Pod can be Running with 47 restarts — liveness keeps killing it

The Running phase holds while liveness fails (kubelet restarts the container → CrashLoopBackOff) or readiness fails (Ready=False, pulled from endpoints).

Terminal phases need restartPolicy: Never or OnFailure (Jobs). With Always (Deployments) the container restarts instead and the Pod stays Running.

A Deployment is a contract: keep N copies of this Pod template running. The Deployment owns a ReplicaSet; the ReplicaSet keeps exactly N Pods alive.

Declarative reconciliation

The control loop runs continuously

read spec

→

close the gap, then repeat
  • Delete a Pod and the ReplicaSet creates a replacement within seconds
  • Change the template and the Deployment spins a new ReplicaSet and shifts replicas over — a rolling update
  • When a Pod can’t be created, the failure event lands on the ReplicaSet, not on a Pod that doesn’t exist

Editing a live Pod is almost always wrong — the ReplicaSet replaces it and your change is gone. Edit the Deployment and let it roll.

How the Pod lives

When a container exits, restartPolicy decides

Always — default

Restart on any exit, success or failure. The only value a Deployment allows.

OnFailure

Restart only on a non-zero exit. Used by Jobs.

Never

Never restart; the Pod settles into Succeeded or Failed.

Set per Pod, applies to every container in it. Restarts back off exponentially — 10s, 20s, 40s … capped at 5 minutes. A container stuck in that cycle reports CrashLoopBackOff.

Container restarts

CrashLoopBackOff is not the crash

It is the kubelet waiting between restart attempts. The crash reason is one level down, in the container’s last state.

# in Containers:, read the Last State block — Reason, Exit Code kubectl describe pod <pod> -n <ns> # what the dead container logged before it died kubectl logs <pod> -n <ns> --previous

--previous is the key flag. The current container may have just started and its logs are empty; --previous reads the terminated one that actually failed.

The distinction that matters most

Liveness restarts; readiness gates traffic

Liveness restarts the container

If the cause isn’t fixable by a restart — a dependency is down — liveness turns a degraded service into a crash loop.

Default to no liveness probe, or a conservative one. It should only mean “this process is wedged and only a restart will help.”

Readiness removes it from rotation

It drops the Pod from endpoints but leaves the process running, so it can recover and rejoin.

Lost a database connection? Fail readiness, keep the process, and let the Service route elsewhere until it’s back.

For slow boots use a startupProbe rather than inflating initialDelaySeconds on liveness — that is what startup probes are for.

A Service routes only to Pods whose Ready condition is true. A failed readiness probe drops the Pod from the EndpointSlice even though the Pod is still Running. kubectl get endpoints <svc> is the tell.

How the Pod dies

Graceful termination is an ordered sequence

delete issueddirectly, or a rollout / scale-down replacing the Pod
marked Terminatingdropped from Endpoints — new traffic stops arriving
preStop hook runsif defined — e.g. a short sleep, before SIGTERM
SIGTERM → PID 1app drains in-flight work, then exits
SIGKILL (forced)grace period expired; container killed, Pod object removed

preStop hook

A command or HTTP call the kubelet runs before SIGTERM. The classic use is a short sleep so load balancers finish removing the Pod before it starts refusing connections.

terminationGracePeriodSeconds

The total budget, default 30s. Both preStop and SIGTERM handling spend from it.

The failure mode

The budget has to cover the whole drain

terminationGracePeriodSeconds is a fixed budget. A graceful shutdown only finishes if that budget covers the app’s real drain time.

When the budget is shorter than the drain, the kubelet sends SIGKILL mid-drain and in-flight work is lost — every time the Pod is replaced, on every rollout and scale-down.

Size the grace period to exceed the measured drain. The fix is a larger budget, not a shorter drain.

SHARP EDGES

  • The grace clock covers the whole sequence, preStop included
  • If preStop is still running at expiry, the kubelet grants one ~2s extension — don’t rely on it
  • SIGTERM goes to PID 1. If the app runs under sh -c, the shell may not forward it — use tini or exec-form CMD
Why the Pod is the atom

The Pod is the unit of scheduling, not the container

Containers in a Pod are co-scheduled onto one node and share its network namespace (one IP; they reach each other on localhost), IPC, and volumes.

Init container6

Runs to completion, in order, before the app containers start. A Pod stuck Init:0/1 has an init container that hasn’t finished.

Sidecar container7

Runs alongside the app for the Pod’s whole life — a proxy, log shipper, or config reloader.

Ephemeral container

Injected into a running Pod with kubectl debug — no probes, no restarts. For distroless or crashing Pods.

Going deeper

Native sidecars

An init container with restartPolicy: Always (GA in v1.33). The kubelet ties its lifecycle to the main containers, giving three guarantees an ordinary container can’t.

Starts first

Becomes ready before the main containers start, so the app comes up into a working dependency.

Stops last

Kept alive until the main containers exit, then terminated in reverse order.

Bounded by the Pod

Terminates when the main container exits, so it never holds the Pod open past the app.

Use one for a helper that must live as long as the app — a proxy, log shipper, or config reloader — instead of an ordinary container.

Recap

What to carry forward

  • A Running Pod is not a healthy Pod. Phase is the headline; container state, conditions, and probes are the detail.
  • Liveness restarts — use it sparingly, a wrong one self-inflicts a crash loop. Readiness gates traffic — pulls from endpoints, no restart. Startup protects slow boots and suppresses the other two until it passes.
  • CrashLoopBackOff is the kubelet backing off between restarts, not the failure itself. The reason is in lastState.terminated and logs --previous.
  • You write Deployments; controllers reconcile them into Pods continuously. Edit the Deployment, not the Pod.
  • Graceful shutdown is preStop then SIGTERM, all inside terminationGracePeriodSeconds. If the budget is smaller than the drain, work dies on every rollout.
Production thinking

Questions to consider

  • A liveness probe restarts a container on failure. Name a failure where restarting makes the incident worse, and decide whether that workload should have a liveness probe at all.
  • Your readiness probe checks a downstream dependency that has a 30-second blip. What happens to every replica’s Ready state at once, and what does that do to the Service?
  • You’re sizing terminationGracePeriodSeconds for a workload that holds long-lived sessions — a media leg, a websocket. How do you find the right number, and what’s the cost of guessing too high versus too low?
