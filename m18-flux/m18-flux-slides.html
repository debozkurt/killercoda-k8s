Flux — GitOps Delivery

Git holds the desired state; a controller in the cluster makes it true and keeps it true. Flux fetches a source, reconciles it into live objects, and corrects drift every interval.

A Flux failure is rarely a crashing Pod — it's a stalled reconcile. The workload looks fine or looks stale, and the real signal is in Flux's own objects.

What you'll walk away with

  • Explain GitOps — declarative state in git, continuously reconciled by an in-cluster agent — and how Flux implements it as controllers and CRDs
  • Separate a source (GitRepository) from a consumer (Kustomization, HelmRelease), and read each object's Ready condition top-down to find a stall
  • Trace the reconcile loop: source artifact → server-side apply → live objects, on an interval you can force with flux reconcile
  • Reason about drift correction — why a manual kubectl edit on a managed object is reverted — and when suspend turns that off
  • Order releases with dependsOn, and read why a dependent is stuck waiting
  • Drive the fleet with the flux CLI: get sources, get kustomizations, reconcile, suspend/resume, logs, events

GitOps is continuous reconciliation,
not a one-shot deploy

Four principles: the desired state is declarative, versioned and immutable (git history), pulled automatically by an agent, and continuously reconciled. The last two are what separate it from a CI job that runs kubectl apply.

A CI pipeline pushes once

It applies when it happens to run. Edit the cluster afterward and the pipeline neither knows nor cares until the next push — drift lives until the next deploy.

A GitOps agent pulls on a loop

It pulls the declared state every interval and re-asserts it, dragging the cluster back toward git. Drift has a bounded lifetime — one reconcile interval.

The shift is from a deploy that happens to the cluster to a loop that continuously holds the cluster equal to git.

Flux is a set of controllers,
each owning one CRD family

There is no central "Flux daemon" to restart. Each controller writes status on its own objects and coordinates only through the Kubernetes API — so the whole system is debuggable with kubectl get and flux get.

flux-system

kustomize-controllerbuild + apply

coordinate only through the Kubernetes API — status on each object, no shared bus, no central daemon

flux install lays these controllers into the flux-system namespace; each then reconciles its own kind on its own interval.

A fetch failure freezes the artifact — nothing crashes

When the ref is wrong or the server is unreachable, the GitRepository goes Ready: False with the git error verbatim, its artifact freezes at the last good revision, and every consumer keeps reconciling that stale revision — reporting it's waiting on the source. A green consumer on a red source means the cluster is running yesterday's truth, which is why the source is the first object you read.

A Kustomization builds a path
from a source and applies it

The Flux CRD (kustomize-controller) — distinct from the kustomization.yaml file it may build. It points at a source, builds a path inside the artifact, and applies with server-side apply.

The object, field by field

sourceRefwhich GitRepository to read
patha directory inside the artifact to build
prunegarbage-collect what's removed from git
waitblock on applied objects reporting healthy

The path is the field that bites

If it doesn't exist or isn't a buildable kustomization, the build fails and the object goes Ready: False before anything is applied — the cluster is untouched and there's no Pod to inspect.

flux build kustomization and flux diff kustomization reproduce and preview the build without touching the cluster.

Drift correction is the guarantee
and the surprise

Because a Kustomization re-applies the declared manifests every interval, a Flux-managed field cannot durably hold an out-of-band edit.

Drift is reverted

Scale a managed Deployment out of band and Flux resets it to git's replica count within one interval. The cluster cannot durably disagree with the declared state.

Prune garbage-collects

With prune: true, a manifest removed from git is deleted from the cluster; Flux tracks an inventory of what it applied. Without it, removed resources linger as orphans that no longer appear in git.

The property that makes GitOps trustworthy is the one that surprises operators mid-incident: your kubectl edit fix vanishes because Flux owns that field. Fix it in git, or suspend first — don't fight the controller.

suspend freezes reconciliation —
and hides in plain sight

spec.suspend: true (or flux suspend) stops the controller from touching an object: no drift correction, no new applies, no pruning. flux resume turns it back on and reconciles immediately.

A real operational tool

Suspend a Kustomization before a manual intervention so Flux won't fight you, or to freeze a subsystem during an incident while you work upstream.

The hazard: it looks healthy

A suspended object reports its last state, which was Ready: True, so get output looks fine at a glance. Only the explicit Suspended marker distinguishes it.

The classic outage: a fix merged, CI green, dashboards green — and nothing lands, because a consumer was suspended during last week's incident and never resumed. When a commit doesn't take and the source is fine, check for a suspended consumer first.

A HelmRelease drives Helm
from an object, not a laptop

helm-controller runs the same install/upgrade/rollback model as helm — but driven by a HelmRelease object, declared in git and reconciled like everything else.

The chart comes from a source, and the entire release is declared in one object — so there is no laptop state to drift from.

  • The chart is a HelmRepository, an OCIRepository, or a chart directory inside a GitRepository
  • Values live in spec.values (or a referenced ConfigMap / Secret)
  • Remediation can auto-retry or roll back a failed release

The object, field by field

chart./charts/x from a source ref
targetNamespacewhere the release installs
valuesthe release's inputs, in git
remediationretry / rollback on failure

Remediation closes the "green status hides a stuck rollout" trap: a HelmRelease reports Ready: False when the release genuinely didn't come up.

dependsOn orders releases —
and references the same kind only

A HelmRelease's dependsOn lists other HelmReleases; a Kustomization's lists other Kustomizations. The dependent holds until every listed object is Ready before it reconciles.

The sharp edge: a name that will never be ready

A typo or a stale rename leaves the dependent pointing at a name (or the wrong kind) that will never be Ready — which reads identically to a genuinely-blocked release, both stalling with a dependency ... is not ready message. Confirm the named dependency actually exists, as the right kind, and is Ready.

Waiting is working as designed: Flux would rather hold than install into a half-built world.

Three places the pipeline stalls —
and nothing crashes

In every case the workload looks fine or looks stale; the real signal is in Flux's objects, not the Pod.

Source

The GitRepository can't fetch — bad ref or URL. The artifact freezes; every consumer runs last-known-good and reports it's blocked on the source.

Reconcile

A Kustomization is suspended. Drift isn't corrected and new commits aren't applied, while get output looks healthy.

Ordering

A HelmRelease lists a dependsOn that isn't Ready — failing, suspended, or misnamed. The release waits and never installs.

Source, reconcile, ordering — one layer each. Name the layer and the fix is already narrowed.

The diagnostic order is fixed:
source, then consumer, then object

Read the sourceflux get sources git — Ready, and revision matches git HEAD
Read the consumerflux get kustomizations / helmreleases — Ready, and not Suspended
Only now, the objectthe managed Deployment or release — reached last, not first

Flux's objects carry the diagnosis

Each layer's Ready condition either clears it or names the failure. Don't stare at a Deployment Flux isn't even touching — climb the two Flux layers above it first.

Driving the loop with the flux CLI

# read the pipeline top-down — source, then consumers flux get sources git flux get kustomizations flux get helmreleases # force a reconcile now, pulling the latest source first flux reconcile kustomization apps --with-source # freeze / unfreeze one object's reconciliation flux suspend kustomization apps flux resume kustomization apps # the controller's own logs and an object's events flux logs --kind Kustomization --name apps flux events --for Kustomization/apps

reconcile --with-source forces the source to fetch before the consumer applies — the fastest way to answer "is the cluster current with git?"

What to carry forward

  • GitOps is continuous reconciliation, not a one-shot deploy. Git is the declared truth and Flux re-asserts it every interval, so drift lasts one interval, not until the next push.
  • Flux splits sources from consumers. A fetch failure freezes the artifact and stalls every consumer on the last good revision — read the source's Ready first, then the consumer, then the managed object.
  • Drift correction is the guarantee and the surprise. A managed field can't durably hold an out-of-band edit — fix in git, or suspend before you intervene.
  • suspend freezes reconciliation and hides in plain sight. A suspended object reports its last-healthy state; when a commit doesn't take and the source is fine, check for a suspended consumer.
  • dependsOn orders releases by waiting for Ready. A dependent stuck "not ready" is often pointing at a dependency that's failing, suspended, or misnamed — verify the named object exists and is Ready.
