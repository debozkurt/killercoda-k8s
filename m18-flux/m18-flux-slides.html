Flux:
fetch, build, apply, health

Git holds the desired state. Controllers in the cluster fetch it and make the cluster match it, on a loop.

A failure stops one stage and leaves the later stages on the last good result. Read the Flux objects in pipeline order, and compare revisions.

GitOps pulls on a loop;
a CI job pushes once

Push: CI runs kubectl apply

The job applies once, when it runs.

A later hand change stays until the next deploy, and the job does not know about it.

Pull: an agent in the cluster

The agent reads git every interval and makes the cluster match it.

Drift lasts at most one interval.

OpenGitOps principles: declarative, versioned and immutable, pulled automatically, continuously reconciled.

The kustomize-controller and the helm-controller run build, apply and health. Each stage records its result on a Flux object.

A source stores an artifact;
the revision names the commit

apiVersion: source.toolkit.fluxcd.io/v1 kind: GitRepository metadata: name: polyphone-config namespace: flux-system spec: interval: 1m url: http://gitea.../polyphone-config.git ref: branch: main
$ flux get sources git NAME REVISION READY polyphone-config main@sha1:42b1aaba True MESSAGE stored artifact for revision 'main@sha1:42b1aaba'
  • A source only fetches. It never applies anything.
  • Consumers (Kustomization, HelmRelease) read the artifact; they never clone git.

A fetch failure has two cases,
and they look different

No artifact was ever stored

e.g. a branch that the repo never had.

The Kustomization reports Source artifact not found. The HelmRelease reports that its HelmChart has no artifact.

The workloads are absent.

An earlier artifact exists

e.g. an expired credential after a good fetch.

Consumers keep applying the old artifact and stay Ready True. Only the source is red.

The new commit never arrives.

Consumers check whether an artifact exists, not whether the source is Ready. Compare the source revision with git, and each consumer's revision with the source.

One pass of a Kustomization

Buildthe path with Kustomize. A missing path fails with kustomization path not found; kustomize-controller applies and deletes nothing.
Applyevery built object with server-side apply, forcing ownership of the fields in the manifest.
Prune(prune: true): delete inventory objects that the new build no longer contains.
Health(wait: true): wait up to timeout for every applied object to become healthy.

Apply and prune together form the apply stage. A failure stops the pass at that step, and a failed build leaves the objects from the last good build running.

A build failure: the source has the commit,
the consumer trails it

$ flux get sources git polyphone-config main@sha1:84dcaf2b True stored artifact ... $ flux get kustomizations apps main@sha1:565e580f False kustomization path not found: stat /tmp/kustomization-2020937857/apps: no such file or directory
  • The revisions differ: the source holds the new commit, and apps last applied the old one.
  • e.g. a repo restructure moved the directory, and nobody updated spec.path.
  • The old workload keeps serving, so no Pod-level alert fires.

A Kustomization reverts a hand change
on the next pass

$ kubectl scale deploy dialplan --replicas=5 $ flux reconcile kustomization apps ✔ applied revision main@sha1:42b1aaba... $ kubectl get deploy dialplan dialplan 2/2 2 2
# managedFields after kubectl scale manager: kustomize-controller operation: Apply manager: kubectl operation: Update subresource: scale
  • The controller applies the git manifest with force, so it takes back every field the manifest declares.
  • The controller leaves alone a field that git does not declare.
  • An HPA fights Flux when the manifest sets replicas. Remove the field when an HPA owns it.

A HelmRelease keeps a hand change;
drift detection is off by default

$ kubectl scale deployment voicemail --replicas=3 $ flux reconcile helmrelease voicemail ✔ applied revision 0.1.0 $ kubectl get deploy voicemail voicemail 3/3 3 3

disabled (default)Drift stays until the next upgrade

A health failure: applied,
but the applied revision stays old

$ flux get kustomizations apps main@sha1:66caf5fd False health check failed after 1m0s: timeout waiting for: [Deployment/app-services/dialplan status: 'InProgress'] $ kubectl describe kustomization apps -n flux-system Last Applied Revision: main@sha1:66caf5fd... Last Attempted Revision: main@sha1:1df556f3...
  • The new objects are live: old Pods serve, the new Pod is in ImagePullBackOff.
  • lastAppliedRevision moves only when a whole pass succeeds, health check included.
  • Between retries the condition reads Ready Unknown, Reconciliation in progress.

When git holds the bad change,
the fix that lasts is a commit

kubectl set image

The rollout completes. On the next pass the controller applies the bad image from git again.

The hand fix lasts about one interval.

Revert in git

git revert --no-edit HEAD git push flux reconcile kustomization apps --with-source

Confirm with revisions: the newest commit, the source revision and the applied revision are the same hash.

A suspended object keeps
its last green condition

$ flux get kustomizations NAME REVISION SUSPENDED READY MESSAGE apps main@sha1:f3fe863c True True Applied revision: main@sha1:f3fe863c $ flux reconcile kustomization apps ✗ resource is suspended
  • Suspended: no new revision, no drift correction, no prune.
  • Suspend before a deliberate hand change; put the change in git; then flux resume.
  • When a commit does not land and the source is current, read SUSPENDED first.

The controller checks dependsOn
at the start of every pass

The dependency is red

dependency 'flux-system/message-store' is not ready

Fix the dependency.

The dependency does not exist

unable to get 'flux-system/message-cache' dependency: helmreleases.helm.toolkit.fluxcd.io "message-cache" not found

Fix the reference.

  • Both carry the reason DependencyNotReady: read the message. The controller retries every 30 seconds.
  • Same kind only: a HelmRelease lists HelmReleases, a Kustomization lists Kustomizations.
  • A closed gate later blocks upgrades and drift correction. It never uninstalls.

flux check tests the Kubernetes version
before the controllers

$ flux check ► checking prerequisites ✗ flux 2.9.6 <2.10.0 (new CLI version is available, please upgrade) ✗ Kubernetes version v1.30.10 does not match >=1.33.0-0 ► checking controllers ✔ helm-controller: deployment ready ✔ kustomize-controller: deployment ready ✔ source-controller: deployment ready ✗ check failed
  • Each Flux release supports a range of Kubernetes minor versions; the project supports the latest three.
  • Controllers can run outside the supported range. The version failure is a cluster upgrade to plan.

Recap

  • Flux is a pull loop with four stages: fetch, build, apply and health. A failure leaves the later stages on the last good result.
  • Compare revisions, not colors. A consumer stays green on an old artifact, and a suspended consumer keeps its last green condition.
  • A Kustomization reverts any hand change to a field that git declares. When git holds the bad change, fix it with a commit.
  • suspend stops every pass for one object. Lift it when the change is in git.
  • The controller checks dependsOn on every pass, and the message tells a missing dependency from a red one.
