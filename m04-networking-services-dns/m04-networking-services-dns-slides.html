Services & DNS

Pods already have routable IPs. A Service provides stable discovery and a stable frontend for a changing backend set.

This module follows one request from DNS resolution to the application socket.

What this module establishes

  • Pods reach each other without a Service, and why a Service still exists
  • How a Service selector becomes EndpointSlices, and who writes each
  • How cluster DNS resolves a Service name, and what the record returns
  • What a ClusterIP represents, and what implements it
  • How the Service dataplane selects an endpoint and forwards to it
  • How port, targetPort, and the application listener relate
  • Where ClusterIP, NodePort, LoadBalancer, headless Services, and port-forward enter or bypass the path
  • Which failure signature belongs to which part of the path

The Pod network comes first

  • Each Pod receives its own IP. Every container in the Pod shares that IP and network namespace.
  • The CNI implementation provides Pod connectivity. Cross-node delivery depends on that implementation.
  • Pods communicate directly by Pod IP. A Service is not required for Pod-to-Pod reachability.
  • Pod IPs are ephemeral. A rollout replaces the Pod and the address is gone.

Pod IP is a current network location. A Service is a stable identity plus a backend set.

Containers share a network namespace; Pods do not

  • Containers in one Pod share one network namespace — one interface, one IP, one port space. They reach each other on localhost.
  • Reaching another Pod crosses that boundary: out the Pod's eth0, over a veth pair, through the node's namespace, in through the target's eth0.
  • Traffic transits the node's namespace — the veth peer ends live there. A Pod is never a member, and sees none of the node's interfaces.
  • The node-side hop belongs to the CNI implementation — bridge, routing, or eBPF. Same objects either way; different debugging tools.
  • Leaving the cluster differs again: outbound traffic is source-NATed to the node IP, so an external peer never sees a Pod address.

Membership decides what you can bind: a sidecar reaches its app on localhost, and two containers in one Pod cannot both listen on 8080. The one Pod that genuinely has no namespace of its own is hostNetwork: true — its IP is the node's, and it binds the node's real ports.

Why a Service exists

kind: Service metadata: name: session-broker namespace: media spec: selector: app: session-broker ports: - port: 80 targetPort: 8080
  • The Service object defines a stable frontend for a set of Pods.
  • The selector defines backend intent.
  • The Service object does not contain the current backend Pod IPs.
  • Kubernetes assigns a ClusterIP to a normal ClusterIP Service. It is stable for the lifetime of the Service.
  • The backend set is maintained separately, in another object.

The selector is intent;
the EndpointSlice is the result

  • You write the selector: which Pods should back the Service.
  • Kubernetes writes the EndpointSlice: current endpoint addresses and their conditions. Do not edit it.
  • The EndpointSlice controller runs in the control plane and reconciles selector and Pod state into EndpointSlices.
  • Service traffic normally uses endpoints considered ready for the Service, subject to Service configuration and endpoint conditions.
kubectl get endpointslice \ -l kubernetes.io/service-name=session-broker

DNS maps Service identity
to the Service frontend

# the name the client uses session-broker.media → session-broker.media.svc.cluster.local → 10.96.42.17 # the resolver config inside a Pod nameserver 10.96.0.10 search media.svc.cluster.local svc.cluster.local options ndots:5
  • CoreDNS provides cluster DNS in a typical installation. A normal Service receives a DNS record.
  • The fully qualified form is <service>.<namespace>.svc.<cluster-domain>. cluster.local is the common default, not a requirement.
  • search expands short names, so a bare Service name resolves relative to the caller's namespace.
  • Use service.namespace or the FQDN across namespaces. ndots controls when expansion is tried.

DNS identifies the Service. For a normal ClusterIP Service, DNS does not select the backend Pod.

The canonical request

messages 1–2 are discovery · 3–6 are the data plane · the EndpointSlice is control-plane state, written before any of this

A NetworkPolicy can permit or deny the traffic at message 4. Enforcement depends on the networking implementation. Policy provides no discovery and selects no endpoints.

The ClusterIP is a virtual frontend

No application process listens on the ClusterIP. The node Service dataplane implements it.

1 resolve2 ClusterIP3 select4 deliver5 socket

  • The ClusterIP is allocated to the Service. It does not correspond to a host interface with a process bound to it.
  • kube-proxy watches Service and EndpointSlice state and programs the node dataplane. It is not a userspace proxy handling each packet.
  • The kernel processes the packets once that state exists. Upstream modes are nftables and iptables.
  • Some networking implementations replace kube-proxy with another Service dataplane, for example an eBPF-based one.

Translation, connection tracking,
and Pod delivery

1 resolve2 ClusterIP3 select4 deliver5 socket

  • The dataplane selects an eligible endpoint for a new flow and redirects the destination to it.
  • Connection tracking records the flow. Reply traffic is handled consistently with that state, so the client sees answers from the address it dialled.
  • A local endpoint is delivered through the node's networking into the Pod. A remote endpoint crosses the CNI network to the destination node.
  • The exact cross-node mechanism depends on the CNI implementation.

Only the process opens a socket

1 resolve2 ClusterIP3 select4 deliver5 socket

  • port — the Service-facing port clients dial.
  • targetPort — the destination port on the selected endpoint.
  • containerPort — Pod-spec metadata. It opens nothing.
  • The application process creates the listener. Nothing else does.

The EndpointSlice can be correct while targetPort has no listener. That is the troubleshooting boundary between the backend set and the application.

Service forwarding balances flows,
not application requests

1 resolve2 ClusterIP3 select4 deliver5 socket

  • Backend selection happens for a new flow.
  • Kubernetes does not reselect a backend for each application request inside an established connection.
  • These reuse long-lived connections: HTTP keep-alive, WebSockets, HTTP/2, gRPC.
  • Native Service forwarding is flow granularity, not request granularity.

TypeTypical reachabilityWhat it adds

  • ClusterIP is intended for cluster-internal reachability, so it is normally reachable only from networks that can route into the cluster Service network.
  • NodePort is reached at <NodeIP>:<nodePort>, exposed on eligible node addresses according to node and kube-proxy configuration.
  • type: LoadBalancer requests an external implementation. The datapath depends on the provider or controller; a NodePort-based path is common, and direct-to-endpoint integrations also exist.

Headless and ExternalName
skip the forwarding path

# headless: no virtual frontend spec: clusterIP: None selector: app: media-engine DNS → endpoint addresses # ExternalName: a DNS alias spec: type: ExternalName externalName: db.vendor.example.com DNS → a CNAME
  • Headless has no Service virtual IP. DNS exposes endpoint addresses, and the client or protocol chooses one.
  • StatefulSets and client-side balancing are common uses, not the definition.
  • ExternalName returns a CNAME. No selector, no EndpointSlice-backed routing, no Service dataplane for the destination.
  • get endpointslice is empty on an ExternalName by design.

kubectl port-forward bypasses
the normal Service path

  • It does not prove cluster DNS, ClusterIP forwarding, or Service dataplane behaviour.
  • With svc/<name>, Kubernetes uses the Service to select a backing Pod for the forward. The traffic still does not traverse the ClusterIP path.
  • A working port-forward proves that one application endpoint is reachable through the port-forward path.

The model, in one piece

  • Pods already have network identities.
  • Services provide stable discovery and a stable frontend.
  • Selectors express intent. EndpointSlices represent current endpoints.
  • DNS maps Service names to the Service frontend.
  • The Service dataplane selects an endpoint for a new flow.
  • The CNI delivers the traffic to the Pod.
  • The process must listen on the target port.
