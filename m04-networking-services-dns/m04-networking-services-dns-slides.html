Services & DNS

Pod IPs change. A Service gives one set of Pods a stable name and a stable IP.

This module covers the objects that make that work, the path a request takes through them, and where a call stops on that path.

What you'll learn

  • The Pod network — every Pod holds a routable IP, so Pods already reach each other without a Service
  • The Service — one object that puts a fixed name and a fixed IP in front of a moving set of Pods
  • Five hops, five owners — name, ClusterIP, node rules, Pod network, socket — and who writes each one
  • Ways in — from a Pod, from a node, from outside, and kubectl port-forward, which skips the ClusterIP and kube-proxy
  • Locating a failure — the common stops on the path, and the signature each one leaves

Every Pod holds its own IP

Pods on different nodes already reach each other. No Service takes part in that.

  • Each Pod gets one IP, shared by its containers, and reachable from every other Pod on any node
  • The CNI plugin provides that — the kubelet calls it when a Pod starts
  • Pod IPs work, and no client can depend on one: a rollout replaces the Pod and the IP is gone

Pods already reach each other. A Service adds a stable name and load balancing. It does not add connectivity.

Anatomy of a Service

One object, four fields that matter. You write two. The cluster writes the others.

kind: Service metadata: name: session-broker spec: selector: ← you: which Pods answer app: session-broker clusterIP: 10.96.84.19 ← the apiserver assigns ports: - port: 80 ← you: what clients dial targetPort: 8080 ← you: where bytes land
  • The selector is a query, not a list — it matches whatever Pods carry those labels, whenever they appear
  • A Service is not a process, a proxy Pod, or an address on any interface

The EndpointSlice is written for you

The selector says which Pods should get traffic. This says which ones actually do.

what it isA list of addresses — Pod IP plus port — that belong to one Service
who writes itThe EndpointSlice controller, in the control plane. Never you.
written fromThe Service's selector, matched against Pods that are Ready
who reads itkube-proxy on every node, to build that node's rules
see it withkubectl get endpointslices — or get endpoints, the older view of the same thing
kubectl get endpointslice \ -l kubernetes.io/service-name=session-broker NAME ADDRESSTYPE PORTS ENDPOINTS session-broker-7k2xw IPv4 8080 10.244.1.7,10.244.2.4 # a Pod goes not-Ready — nobody edits anything kubectl get endpointslice -l kubernetes.io/service-name=session-broker session-broker-7k2xw IPv4 8080 10.244.2.4

Do not edit this object. The controller overwrites it. Change the selector or the Pods' readiness instead.

The ClusterIP is data, not a host

the client resolves the nameCoreDNS

the answer is a ClusterIPthe apiserver

  • No process holds it and no interface answers for it — it is data
  • kube-proxy compiles the Service and its EndpointSlice into kernel rules on every node
  • So there is no Service process to restart, and one node failing while others work points at that node's rules
  • With zero endpoints kube-proxy installs a reject rule, so the client is refused instead of left hanging

What the packet does inside a node

the client resolves the nameCoreDNS

the answer is a ClusterIPthe apiserver

node rules pick a backendkube-proxy

the packet reaches the Podthe Pod network

  • A veth pair carries the packet out of the Pod's network namespace into the node's
  • The node's rules rewrite the destination from ClusterIP:port to PodIP:targetPort
  • When the chosen Pod sits elsewhere, the CNI routes or encapsulates the packet to that node
  • Connection tracking remembers the rewrite and reverses it, so the reply appears to come from the ClusterIP
  • The backend is chosen once per connection, not per packet

the process accepts ityour container

  • port — what clients dial on the Service
  • targetPort — the Pod port traffic is delivered to; defaults to port
  • containerPort — documentation in the Pod spec; it opens nothing
  • The process opens the socket, on whatever port it binds

When targetPort points at a port nothing listens on, the EndpointSlice is fully populated and the connection is still refused.

A path that works proves every hop below its entry point. Use that to narrow a failure.

ClusterIP — inside the cluster only

The default. One virtual IP, load-balanced across the Ready backends, with no way in from outside.

spec: type: ClusterIP # the default; usually omitted selector: { app: session-broker } ports: - port: 80 targetPort: 8080

Use it for internal APIs, databases, and caches. It exposes the least, and it is the default.

NodePort — a port on every node

One port from 30000–32767 opens on every node. Any node accepts it, then forwards it down the same path.

spec: type: NodePort # ClusterIP, plus a port on every node selector: { app: session-broker } ports: - port: 80 targetPort: 8080 nodePort: 31380 # or let the apiserver pick one

Use it for a demo, a debug endpoint, or a cluster with no balancer to call. It is rarely production: the ports are high, firewalls between client and node often block them, and every Service needs its own port.

LoadBalancer — a balancer in front

The cloud controller provisions a real balancer, gives it a stable external address, and aims it at those node ports.

spec: type: LoadBalancer # NodePort, plus a provisioned balancer selector: { app: session-broker } ports: - port: 80 targetPort: 8080

Each Service needs its own balancer, its own address, and its own bill. An Ingress shares one entry point across many Services. With nothing to provision it, the Service stays at <pending>.

Two types opt out of proxying

Both answer in DNS, and neither takes a virtual IP, so kube-proxy has nothing to do.

# headless — no virtual IP; DNS hands back the Pods spec: clusterIP: None selector: { app: media-engine } → media-engine.media = 10.244.1.7, 10.244.2.4 # ExternalName — no selector, no backends, no proxying spec: type: ExternalName externalName: billing.vendor.example.com → billing.finance = a CNAME, and nothing else
  • Headless gives a StatefulSet's Pods individually addressable names. A database replica is reached by its own name, and a gRPC client takes the Pod list and balances requests itself
  • ExternalName gives a managed database or a vendor API a stable in-cluster name, so application config is the same in every environment. get endpoints on it is empty by design

Port-forward does not use the Service path

Your machine opens a local port. The stream travels the control plane, not the data path.

  • It touches nothing the Service uses — no cluster DNS, no ClusterIP, no kube-proxy rule
  • Given svc/<name> it uses the Service only to pick one Pod, then talks to that Pod
  • So it reaches the app while the Service is broken — which is what makes it a probe, not a test of the Service

What to carry forward

  • Every Pod holds a routable IP, so Pod-to-Pod already works. A Service exists because those IPs move.
  • A Service is a name and a virtual IP in front of a selected set of Pods. You write the selector; the apiserver writes the ClusterIP; a controller writes the EndpointSlice from Ready Pods.
  • The ClusterIP is data, compiled into every node's kernel by kube-proxy. Connection tracking reverses the rewrite on the way back.
  • port is what clients dial, targetPort is where bytes land, and containerPort opens nothing. Endpoints can be perfect while the port is dead.
  • Short names resolve only inside the caller's namespace. Qualify cross-namespace calls as <svc>.<ns>.
  • Read the signature before the code: NXDOMAIN is the name, empty endpoints is the selector or readiness, refused-with-endpoints is the port. Other stops exist; the method is the same.
