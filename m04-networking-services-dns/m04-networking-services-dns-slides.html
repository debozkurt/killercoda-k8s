A stable identity in front of churn

Pods are disposable — a rollout, a drain, an autoscaler, and their IPs are gone. The Service is the name and IP that don't move.

Clients hold the name; the platform churns the Pods. The ClusterIP is stable for the Service's life — no single Pod holds it.

One request path, three places it breaks

Each hop is owned by a different component. Read where it stopped and you know which one.

A Service finds Pods by selector;
the EndpointSlice is the proof

# the selector defines the backend set kubectl get svc session-broker -n media -o jsonpath='{.spec.selector}' {"app":"session-broker"} # the EndpointSlice is the result — Ready Pods only kubectl get endpoints session-broker -n media NAME ENDPOINTS session-broker 10.244.1.7:80,10.244.2.4:80

get svc proves the Service exists; get endpoints proves it has somewhere to send traffic. A failed readiness probe pulls a Pod from the slice without killing it — readiness doubles as load-balancer membership.

Three port fields; only one opens a socket

port

What clients connect to — <svc>:<port>.

lives onthe Service

targetPort

The Pod port the Service forwards to. Defaults to port. This decides where traffic is delivered.

lives onthe Service

containerPort

Documentation. Advertises intent; opens nothing. The process listens on whatever it listens on.

lives onthe Pod spec

When targetPort points at a port nothing listens on, the EndpointSlice is fully populated and the connection is still refused — a perfect-looking Service that sends traffic to a dead port.

The ClusterIP is data, not a host

No process holds it; no interface answers for it. kube-proxy compiles the Service into kernel rules on every node.

One node reaches a Service and another can't? Suspect that node's kube-proxy or its rules — the Service object is identical clusterwide. Modes: iptables (default), IPVS (at scale), nftables (newer).

Zero endpoints → kube-proxy installs a reject rule, so the client's connection is refused rather than silently hung.

Names: <svc>.<ns>.svc.cluster.local

# every Pod resolves via CoreDNS — see its resolver config cat /etc/resolv.conf nameserver 10.96.0.10 search media.svc.cluster.local svc.cluster.local cluster.local options ndots:5 # short name expands via the search list; FQDN is unambiguous nslookup session-broker.media # → ClusterIP

The search domains are built from the caller's namespace. A bare session-broker from another namespace expands to session-broker.<caller-ns>.svc… → NXDOMAIN. Qualify cross-namespace calls with <svc>.<ns>.

Same refusal, two causes —
the EndpointSlice decides

A connection failure looks identical from the client. One command tells the two apart.

Empty EndpointSlice

The Service has no backends — kube-proxy rejects the traffic. A healthy-looking Service routing to nothing.

get endpoints<none> → selector / readiness

Populated EndpointSlice

Traffic reaches a Pod and is rejected — nothing listens on the delivered port.

get endpointsPod IPs listed → targetPort

The headline lies — get svc looks fine in both. Read the endpoints, not the client error. Empty vs populated is the whole diagnosis — the same instinct as Running ≠ Ready.

What to carry forward

  • A Service is a stable name and virtual IP in front of a changing set of Pods, defined by a selector and materialized — for Ready Pods only — in an EndpointSlice.
  • A healthy-looking Service can route to nothing. get svc proves it exists; get endpoints proves it has backends — check the endpoints, not just the status.
  • port is what clients hit; targetPort is the Pod port forwarded to; containerPort opens nothing. Endpoints can be perfect while the port is dead.
  • Short names resolve only inside the caller's namespace — qualify cross-namespace calls with <svc>.<ns>.
  • The differential: NXDOMAIN = name · empty endpoints = selector/readiness · refused-with-endpoints = port. The client error says it broke; the EndpointSlice and DNS answer say where.
