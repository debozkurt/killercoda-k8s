Service mesh: a second dataplane
beside every workload

A proxy next to every pod carries its traffic, so routing, retries, timeouts, circuit breaking, and mutual TLS become platform config instead of application code.

That layer adds a second dataplane with its own failure modes. A pod can be Running, Ready, and backed by healthy endpoints and still return 503 — because the truth is in the Envoy config the mesh compiled, not in kubectl get pods.

What you'll walk away with

  • What a mesh is structurally: a control plane (istiod) that compiles config, and a dataplane of Envoy sidecars it injects — a pod is "in the mesh" only if it carries one
  • How injection happens: a mutating webhook fires for pods in a namespace labeled istio-injection=enabled, so 2/2 vs 1/1 is the fastest membership check
  • Shaping L7 traffic with a VirtualService (routing, timeout, retries) and a DestinationRule (subsets, connection pool, circuit breaker) — both enforced by the caller's sidecar
  • mTLS as a two-sided contract: a PeerAuthentication sets what a server accepts; a DestinationRule's tls mode sets what a client sends
  • Debugging with istioctl: proxy-status for config sync, proxy-config to walk the listener → route → cluster → endpoint chain

L3/L4 stops at the packet;
the mesh works per request

What Kubernetes ships

NetworkPolicy at L3/L4, Ingress at the edge. Both stop at the packet.

Neither retries a failed request, enforces a per-call timeout, trips a circuit breaker on a flapping backend, or authenticates one pod to another.

What the mesh moves out of the app

Retries become a field in a VirtualService. mTLS becomes a one-line policy.

The application keeps making a plain HTTP call and never knows a proxy rewrote, secured, and load-balanced it.

Historically each service wrote that logic itself — differently, in whatever language it was built in — and got it subtly wrong. The mesh applies one implementation uniformly.

Two planes: istiod compiles config,
Envoy sidecars carry traffic

You configure the control plane declaratively; the dataplane is what actually moves packets.

The control plane never touches your traffic. Almost every mesh mystery resolves to one question: does the dataplane's compiled config match what you meant?

A pod is in the mesh
only if it carries a sidecar

Label a namespace istio-injection=enabled and every pod created afterward is intercepted by a mutating admission webhook that rewrites the spec: it adds an istio-proxy container and an istio-init init container that programs an iptables redirect.

The application is unchanged and unaware — it still binds :80 and makes ordinary calls, but the kernel now routes those through the proxy.

Injection is admission-time
and per-pod overridable

Admission-time

It applies only to pods created after the namespace is labeled. Label an existing namespace and nothing changes until the workloads roll.

Per-pod overridable

The annotation sidecar.istio.io/inject: "false" opts a workload out even in an enabled namespace.

A workload that skipped injection is not "partly in the mesh" — it is entirely outside it. No policy, retry, or mTLS applies, and it never registers with istiod, so istioctl proxy-status doesn't list it. When mesh config seems ignored, check for a sidecar first.

VirtualService routes;
DestinationRule shapes the connection

VirtualService — where does it go

Matches on host (and optionally path, headers) and routes to a destination.

carriestimeout — caps how long the caller waits
carriesretries — attempts, per-try timeout, conditions

DestinationRule — how to talk to it

Policy for reaching the host once routing has chosen it.

definessubsets, connectionPool limits
definesoutlierDetection and the client-side tls mode

Both are enforced by the caller's sidecar, on the way out. The rules for reaching a host live in the proxy of whoever is calling it — not in the host's own proxy.

A subset that selects zero pods
is a valid route with no backend

A subset is a named, label-selected group of a host's pods — usually a version. istiod compiles each subset into a separate Envoy cluster.

If a subset's labels select zero pods — a canary defined before its build ships, for example — the cluster is valid but has no endpoints. A request routed there has no healthy upstream, so Envoy returns 503. Nothing is unhealthy; the route aims at an empty set.

You see it only in the compiled config

routesproxy-config routes <caller> — which cluster the host targets
endpointsproxy-config endpoints <caller> — that cluster has no addresses

connectionPool

Caps concurrent connections and pending requests, so one slow replica can't consume the caller's resources and turn a partial outage into a total one.

Like retries and timeouts, this is caller-side resilience the application never sees — applied uniformly by the platform instead of reinvented per team.

mTLS is a two-sided contract:
the server accepts, the client sends

PeerAuthentication — server side

Sets what a workload's sidecar will accept.

STRICTonly Istio mTLS; rejects plaintext
PERMISSIVEmTLS or plaintext — the migration setting
DISABLEplaintext only

DestinationRule tls — client side

Sets what a caller sends.

ISTIO_MUTUALoriginate Istio mTLS
DISABLEsend plaintext
automatic mTLSset nothing — the mesh negotiates it

The two must agree. A STRICT server with a client set to DISABLE is a contradiction — the server resets the connection and the caller gets 503. Repair upward (raise the client to mTLS), never downward.

Before the listener: no sidecar → not in the mesh at all. After the endpoint: an mTLS mismatch → the server's sidecar resets. Same 503, a different link — the client's status code names the class, proxy-config names the spot.

One 503, three different roots
in the Envoy path

No sidecar

The workload isn't in the mesh (1/1); with mTLS required upstream, callers 503.

Repair: re-enroll and roll the Deployment to 2/2.

Empty subset

The route targets a subset that selects zero pods; the Envoy cluster has no endpoints.

Repair: route to a subset that exists.

mTLS mismatch

The client sends plaintext while the server requires mTLS; the server resets.

Repair: align the client to mTLS.

All three are the same client-visible 503 with pods reporting healthy. The client's status code names the class; istioctl names the link.

Read the compiled config with istioctl:
proxy-status, then proxy-config

# is every sidecar on istiod's latest config? istioctl proxy-status # SYNCED / STALE / NOT SENT # walk one pod's compiled Envoy config, link by link istioctl proxy-config routes <pod> -n <ns> # which cluster a host routes to istioctl proxy-config endpoints <pod> -n <ns> # is that cluster empty? istioctl proxy-config clusters <pod> -n <ns> istioctl proxy-config listeners <pod> -n <ns>

The objects you apply are intent; the compiled Envoy config is what moves packets. When they disagree, the config wins — so you read the config.

What to carry forward

  • A pod is in the mesh only if it has a sidecar. Injection is an admission-time webhook keyed on istio-injection=enabled; 2/2 means policy applies, 1/1 means none of it does. Check the container count first.
  • The control plane is intent; the dataplane is truth. When behavior and config disagree, read the compiled config with istioctl proxy-config — listener → route → cluster → endpoint.
  • Traffic management is caller-side, and subsets can be empty. The VirtualService and DestinationRule are applied by the caller's sidecar; a route to a zero-pod subset is a valid rule with no backend.
  • mTLS is a two-sided contract. PeerAuthentication (server) and the DestinationRule tls mode (client) must agree; automatic mTLS makes them agree for free. Repair upward, never downward.
