Service Mesh:
Istio sidecars, routing and mTLS

A proxy beside every workload carries its traffic. Routing, retries, timeouts and mutual TLS become platform configuration.

The mesh adds a second dataplane. Most of its failures reach the caller as the same 503, and the Envoy access log names the cause.

What NetworkPolicy and Ingress cannot do

Without a mesh

NetworkPolicy allows or drops packets at L3 and L4. Ingress routes at the edge. Each service writes its own retries, timeouts and TLS.

With a mesh

A proxy applies the same rules to every call, from configuration objects.

The webhook injects at pod creation only

  • A mutating admission webhook acts on new pods in a namespace labeled istio-injection=enabled.
  • It adds istio-init, which installs the iptables redirect, and istio-proxy, the Envoy sidecar.
  • A pod that already runs keeps no sidecar until something recreates it.
$ kubectl get pods -n media NAME READY session-broker-... 2/2 $ kubectl get pods -n signaling NAME READY sip-router-... 1/1

2/2 and a row in istioctl proxy-status mean mesh rules apply. 1/1 means no mesh rule applies.

If either label is disabled, the pod is not injected. The annotation of the same name still works, and Istio marks it deprecated in favor of the label.

The port name selects the protocol

Port named http

Istio treats the port as HTTP. One shared listener per port number routes by the Host header, and the route table carries the port number as its name.

Unnamed port

Istio tries automatic detection. Traffic that it cannot identify becomes plain TCP, and HTTP rules do not apply to it. istioctl analyze reports the unnamed port.

The appProtocol field on the Service port has the same effect as the name prefix.

The circuit breaker lives in the DestinationRule

trafficPolicy: connectionPool: tcp: maxConnections: 100 http: http1MaxPendingRequests: 64 outlierDetection: consecutive5xxErrors: 5 interval: 10s baseEjectionTime: 30s maxEjectionPercent: 50
  • outlierDetection ejects an endpoint after consecutive 5xx errors, for a base time, up to a share of the pool.
  • connectionPool caps connections and pending requests.
  • Together they stop one failing replica from tying up every caller.

A fault injection answers in the caller's sidecar

http: - route: [...] fault: abort: httpStatus: 503 percentage: { value: 50 }
  • fault.delay adds latency. fault.abort returns a chosen status for a share of requests.
  • The aborted request never leaves the caller's pod. The server's logs show only the successes.
  • Retries do not repeat an injected abort.

mTLS is a two-sided contract

Caller sidecar
DestinationRule tls.mode: what it sends
must agree→
Server sidecar
PeerAuthentication: what it accepts
PeerAuthentication modeServer accepts
STRICTIstio mTLS only
PERMISSIVEmTLS or plaintext (the default with no policy)
DISABLEplaintext only

Plaintext into a STRICT server matches no filter chain. Repair the caller side. A switch of the server to PERMISSIVE stops the error and accepts plaintext again.

Automatic mTLS, and the silent downgrade

No tls block

The caller sidecar sends mTLS to destinations with a sidecar, and plaintext to destinations without one.

Server loses its sidecar

No Envoy enforces its PeerAuthentication. Callers switch to plaintext. The hop works, unencrypted, with no error.

An explicit ISTIO_MUTUAL makes the same missing sidecar fail with 503. Automatic mTLS favors availability; an explicit mode favors a guarantee that fails visibly.

Recap

  • A pod is in the mesh only if it has a sidecar. Injection happens at creation; a namespace label does nothing for running pods.
  • The caller's sidecar applies traffic rules. The server's sidecar applies admission.
  • The objects are intent. istioctl proxy-config shows the compiled clusters and endpoints.
  • mTLS is a two-sided contract. Repair a mismatch on the caller side.
  • The access log names the link. A reset with no status means the caller has no sidecar.

Production thinking

  • A team labels its namespace for injection and reports that the mesh does nothing. What recreates the pods with sidecars, and what is the risk of doing it to every Deployment at once?
  • You must move a namespace to STRICT while some callers are still outside the mesh. Which signal shows that every caller sends mTLS, and what happens to a caller you missed?
  • A canary route sends 10% of traffic to a subset with zero ready pods. Which flag do you expect in the caller's log, and why did the VirtualService apply without an error?
