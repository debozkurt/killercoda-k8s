Configuration

Handing a container its settings — ConfigMaps and Secrets, delivered as environment variables or mounted files — and the four ways that wiring breaks.

How a Pod consumes its config decides how it fails. Read the status, the events, and — when nothing's red — the value itself.

  • Update semantics — env is frozen at start; files drift; a config edit rolls nothing on its own — and how to force one

ConfigMaps and Secrets: two objects, one shape

Both hold key/value config as a standalone object — separate from the workload that reads it.

ConfigMap

Non-confidential settings — kept out of the image so one build runs in every environment.

holdsplain key/value
consumed asenv vars or files
exampleslog level, feature flags, upstream hostnames, a whole nginx.conf

Secret

Confidential data — values base64-encoded in data, stored in etcd. Write plaintext to stringData and the API encodes it for you.

default typeOpaque (also tls, dockerconfigjson, …)
protectionbase64 is not encryption
examplesDB password, API tokens, TLS cert + key, registry pull creds

Both are namespaced and capped at 1 MiB — they live in etcd, and every kubelet that mounts one holds it in memory. They're for settings, not data blobs.

One source, two paths into the container

The path decides how a missing reference fails — and whether a later edit ever reaches the process.

Config extends the image's two bases

The image ships an ENV and a filesystem. A ConfigMap or Secret adds to each at runtime — same build, no rebuild.

as envkeys → variables, layered over the image's ENV
as fileskeys → files, mounted over the image's filesystem

Same keys either way — the mode decides where they land and how they update.

Two ways in: environment variables vs files

As environment variables

Injected into the process environment when the container starts.

syntaxenvFrom (every key) · env + valueFrom (one key)
on updatefrozen — never changes after start
good forsimple, universal scalar settings

As mounted files

Projected into a directory — one file per key, key as filename, value as contents.

syntaxa configMap/secret volume, or a projected one
on updatetracks the source (~sync period)
good forwhole files; keeps secrets off the env

A projected volume combines a ConfigMap, a Secret, downward-API fields, and a ServiceAccount token into one directory — how every Pod's short-lived token arrives.

envFrom takes every key; env takes one

# envFrom — takes EVERY key of app-config envFrom: - configMapRef: { name: app-config } # env + valueFrom — takes ONE key of the same app-config env: - name: LOG_LEVEL valueFrom: configMapKeyRef: { name: app-config, key: LOG_LEVEL } # identical shape, secretKeyRef → one key from a Secret - name: DB_PASSWORD valueFrom: secretKeyRef: { name: database-creds, key: DB_PASSWORD }

envFrom silently skips any key that isn't a valid env-var name — a key like app.properties (the dot) is dropped, the Pod starts fine, and the only trace is one InvalidEnvironmentVariableNames warning event.

The same config, mounted as files

One file per key — the key is the filename, the value is the file's exact contents. A whole config file rides in as one multi-line value.

# the ConfigMap — two keys data: LOG_LEVEL: info app.yaml: | listen: 0.0.0.0:8080 timeout: 30s
# mounted at /etc/app $ ls -l /etc/app LOG_LEVEL -> ..data/LOG_LEVEL app.yaml -> ..data/app.yaml ..data -> ..2026_07_14/ $ cat /etc/app/LOG_LEVEL info # raw value, verbatim

The kubelet writes each update to a fresh timestamped directory and flips the ..data symlink to it in one atomic rename — so the whole set swaps at once, never a half-written file. That symlink indirection is exactly what subPath steps outside of.

Env is frozen; files drift; nothing rolls

A ConfigMap or Secret edit updates etcd and restarts nothing. What reaches the container depends on the consumption path.

Environment variables

Read once, at container start. Never refreshed — the old value sticks until the Pod is replaced.

Mounted files

Kubelet refreshes the file on its sync (~1 min). But updated on disk ≠ reloaded by the app — the process must re-read it.

subPath mounts

A single-file bind mount — frozen like env, not live like a volume. What it's for, and the trap: next slide.

No controller rolls your Deployment when a config object changes. Env-consumers never see the edit; file-consumers get it on the next sync. Need one file that still updates? Mount the whole volume in a subdirectory — not subPath.

subPath: mount one file, not the whole directory

A normal volume mount replaces the target directory with the object's keys. subPath projects a single file (or subdirectory) into an existing directory — the rest of that directory stays put.

Plain mount — shadows the whole dir

volumeMounts: - name: nginx-conf mountPath: /etc/nginx # result — the ConfigMap replaces /etc/nginx /etc/nginx/ └── nginx.conf # only ConfigMap keys mime.types, conf.d/ … hidden

subPath mount — one file, rest intact

volumeMounts: - name: nginx-conf mountPath: /etc/nginx/nginx.conf subPath: nginx.conf # result — one file in, the rest survives /etc/nginx/ ├── nginx.conf # from ConfigMap ├── mime.types # image └── conf.d/ # image

The trade-off that matters here: a subPath is a one-time bind mount to a fixed inode, outside the symlink the kubelet swaps on update — so a ConfigMap/Secret edit never reaches it until the Pod is recreated. (The same feature partitions one PVC across workloads — subPath: postgres, subPath: redis — and makes per-Pod dirs via subPathExpr: $(POD_NAME).)

This rolls env consumers — it doesn't make env live. Env stays frozen per container; the hash just automates the restart. A mounted file updates in place; env only ever changes by replacing the Pod.

Base64 is encoding, not encryption

# a Secret's data is base64 — not hidden kubectl get secret database-creds -o jsonpath='{.data.DB_PASSWORD}' Y2hhbmdlbWU= # anyone with get-secret decodes it — no key, no permission echo Y2hhbmdlbWU= | base64 -d # → changeme

RBAC

Restrict get/list — but note: anyone who can create a Pod in a namespace can mount any Secret in it.

Encryption at rest

Encrypt Secret values before etcd, ideally via a KMS. Off by default.

External stores

Vault / cloud managers, sealed-secrets, sops — keep long-lived secrets out of the cluster. (M11)

How you consume decides how it fails

One source, two paths — and each path fails at a different point in the Pod’s lifecycle.

Same missing object, a different lifecycle phase — env fails during container creation, a volume before it. Different phase → different status, different event, different place to look.

A green Pod can still hold the wrong config

Every signal Kubernetes checks passes — and none of them inspects the one thing that's wrong: the value.

Green is liveness, not correctness. The platform proves the container started and stayed up — never that the value it received is the value you meant. Running, Ready, and Complete all say the same nothing about the config inside.

What to carry forward

  • Config is separated from the image and delivered at runtime by ConfigMaps and Secrets. Base64 is encoding, not encryption — RBAC, encryption-at-rest, and external stores are what protect a Secret.
  • A container consumes config two ways — environment variables or mounted files — and the choice decides both how a bad reference fails and whether an edit ever reaches the process.
  • Env vars are frozen at start; mounted files update with the source (except subPath). A config edit rolls nothing — force it with rollout restart or a config-hash annotation.
  • The differential: CreateContainerConfigError = missing env key · FailedMount = missing mounted object · stale = nothing rolled · Running-but-wrong = a value that resolved but is incorrect.
  • A green Pod can hold the wrong config. Running ≠ correct — read the value, not just the status.
