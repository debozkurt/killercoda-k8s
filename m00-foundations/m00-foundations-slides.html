Mental Model
& kubectl Fluency

How a cluster is organized, how kubectl actually works, and the four-command diagnostic loop every later module assumes.

kubectl is a thin HTTPS client over the API server. There is no magic — orient yourself first, then ask the cluster what it knows.

By the end of this module you can

  • Name the components of a cluster and what each one does
  • Trace any kubectl command back to the HTTP request it makes
  • Read any object through the universal spec / status shape
  • Apply the diagnostic loop — get → describe → events → logs — in order
  • Pivot to cluster-wide awareness when you don't know where a problem lives
  • Avoid the context and namespace mistakes that waste time or widen blast radius

Reach for the model before the commands

The most common reason SREs flounder is typing commands before holding a mental model.

  • Memorizing kubectl get pods without knowing why -A matters
  • Running describe without knowing where Events come from
  • Editing a Deployment, then surprised a controller you didn't know existed rolled a new ReplicaSet

The skill that compounds is orienting fast, asking the cluster what it knows, and reading what it tells you.

A cluster has two halves

The control plane decides what should run; the nodes run it. The API server is the only thing that talks to etcd — everything else, including kubectl, goes through it.

kubectl is a thin HTTPS client

Every command is an API call

apply is a PATCH with server-side merge; logs proxies to the kubelet; describe also fetches the object's events and owner chain and pretty-prints them.

When output looks wrong, ask what API call it made. -v=6 on any command prints the raw URLs and status codes.

Every object has the same shape

Every thing is addressed by three coordinates: kind, namespace, name. Most are namespaced; a few are cluster-scoped — Nodes, PersistentVolumes, ClusterRoles.

  • spec is yours — the desired state you write
  • status is the controllers' — the observed state they report

When something is wrong, the gap between spec and status is where the story lives. Every diagnostic command exposes part of that gap.

apiVersion: apps/v1 kind: Deployment metadata: name: portal-ui namespace: admin-portal spec: # what you want # ... status: # what controllers observe # ...

You describe outcomes, not steps. "There should be a thing that looks like this" — controllers handle the rest, continuously, on every cluster.

This is what separates Kubernetes from a config-management tool. Delete a Pod and a controller makes a new one within seconds.

When a controller fails to create something, the failure event attaches to the creator, not the missing object. A Pod that never got created has nothing to describe — climb to the ReplicaSet, or read the namespace events. The same shape holds for CronJob → Job → Pod and PVC → PV → StorageClass.

Eight verbs carry the routine work

getlist objects — what's there?
describepretty-print one object + its recent events
logsstream a container's stdout / stderr
execrun a command inside a container
applycreate or update from a manifest
editopen the live object in $EDITOR
deleteremove an object (cascades by default)
port-forwardtunnel a local port to a Pod or Service

Flags you combine endlessly: -n, -A, -l key=value, -o wide|yaml|json, --watch, -c <container>, --previous.

edit is triage; apply is declarative

edit — triage only

Opens the live object in $EDITOR and applies on save. Fast for a fix in the moment, but it diverges from the git source of truth.

apply — the declarative verb

A three-way merge against your manifest — the same operation Flux and Argo run. Change the manifest in git, then apply for anything persistent.

Read-only commands are safe anywhere. Any state-changing command needs a context check first.

Ask the cluster what it knows

kubectl api-resources

Every Kind the cluster knows — the built-ins plus anything a CRD or operator installed.

group--api-group=apps → Deployment, StatefulSet, …
scope--namespaced=false → Nodes, PVs, ClusterRoles

kubectl explain

The built-in schema docs for any resource or field — beats grepping through YAML.

fieldexplain pod.spec.containers.livenessProbe
treedeployment.spec --recursive → every nested field

Per-field descriptions depend on whether the resource author wrote docstrings — core resources are well-documented; some third-party CRDs are blank.

Pull fields out: jsonpath, custom-columns, jq

You wantReach forExample
One field-o jsonpathget deploy foo -o jsonpath='{.spec.replicas}'
A quick table-o custom-columns-o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName
Filter / transform| jq'.items[] | select(.spec.nodeName=="n1")'

Prefer label selectors → field selectors → jq, in that order: server-side and indexed beats fetching every object and filtering client-side. If you filter by something that could be a label, add the label.

The diagnostic loop, in order

get → describe → events → logs. If you internalize one thing from this module, make it this.

getwhat's there? current phase?
describewhat happened to it? events for this object's UID
eventswhat's happening in the neighborhood?
logswhat does the app itself say? --previous if it crashed

Same four commands, same order

Broken Services, scheduling failures, OOMKills, image-pull errors, PVC binding — almost every problem in later modules surrenders to this loop.

events is the most-skipped step — and often the fastest path to the answer.

When you don't know where — go wide first

# everything, everywhere — the first command when "something is broken" kubectl get pods -A # only the unhappy ones (excludes cleanly-finished pods) kubectl get pods -A --field-selector=status.phase!=Running,status.phase!=Succeeded # recent activity, cluster-wide kubectl get events -A --sort-by='.lastTimestamp' | tail -50

Why exclude Succeeded? It's a good terminal state — Job and CronJob pods that finished cleanly. Filtering only !=Running would lump completed pods in with the broken ones.

Always know which cluster you're pointed at

# which cluster am I on? kubectl config current-context # list known contexts kubectl config get-contexts # set the default namespace for this context kubectl config set-context --current --namespace=admin-portal

The most embarrassing incident in a multi-cluster shop is a state-changing command on the wrong cluster. Run current-context before any apply / patch / delete — better, keep the active context visible in your prompt.

What to carry forward

  • The control plane decides what runs; nodes run it. The API server is the only thing that talks to etcd
  • kubectl is a thin HTTPS client — every command is an API call; -v=6 shows the exact request
  • Every object is spec (what you want) / status (what is); the gap between them is the story
  • Controllers reconcile continuously — you describe outcomes, not steps
  • The loop is get → describe → events → logs; scan wide with -A first; events is the most-skipped step

Questions to consider

  • A 5,000-pod cluster returns 5,000 lines from get pods -A. How do you triage at that scale? (--field-selector, jq, dashboards)
  • The loop assumes the API server is reachable. If it's down and you're paged, what do you check first?
  • You've spent 20 minutes in prod-us-east-1 and now need to change lab-us-east-1. What workflow makes a wrong-cluster mistake impossible?
