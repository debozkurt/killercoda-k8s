Observability:
events, logs, metrics, traces

A running cluster gives you three signals. Each answers one question, and each expires.

Choose the signal before you type the command. A wrong first choice costs an hour.

Three built-in signals answer
three different questions

Events

What did the control plane do?

read withkubectl events, describe
lifetimeone hour by default

Logs

What did the process say?

read withkubectl logs
lifetimeuntil the node removes the Pod

Metrics

How much does the workload use, and how does it behave?

read withkubectl top, Prometheus
lifetimecurrent values only, or a time series

Traces are the fourth signal. You add them yourself.

All three built-in signals are ephemeral

  • Events expire after the TTL
  • Logs leave the node with the Pod
  • kubectl top keeps no history
  • A durable stack replaces them: an event exporter, a log store, a time-series database

An Event records what the control plane
did to one object

Event fields

typeNormal or Warning
reasona machine token, such as FailedMount or BackOff
objectinvolvedObject: its kind, name and namespace
countrepeats collapse into one Event, and the count rises

The scheduler, the kubelet and the controllers create Events. An Event is not a log line.

A Pod that waits in ContainerCreating has no logs. Its Events are the only signal.

kubectl events sorts by time;
get events does not

A repeated Event reads x7 over 9m in describe and kubectl events. get events hides the count unless you add -o wide.

# every namespace, only trouble kubectl events -A --types=Warning # one object, by kind and name kubectl events --for pod/web-0 # the older reader: pick a sort, select on a field kubectl get events --sort-by=.metadata.creationTimestamp kubectl get events -A --field-selector reason=BackOff

Writes to stdout

kubectl logs and a node collector both see the lines.

Writes to a file in the container

The app logs and kubectl logs stays empty. Nothing captures the file.

Know which container instance
kubectl logs returns

Container statePlain kubectl logs returns
An instance runsThe current instance, often only a startup banner
Waiting in back-off after a crashThe last terminated instance
Never startedAn error: waiting to start
--previousThe last terminated instance, in any state that has one

A plain read hides which instance you get after a restart. Use --previous to pin the one that died, and describe for its exit code.

Two fixes for an app that logs to a file

Log to stdout

The default choice. A node-level collector already ships stdout, so the app needs nothing else.

Streaming sidecar

For an app you cannot change. A second container shares a volume, runs tail -F on the file and prints it to its own stdout.

costone container and some memory per Pod

Since Kubernetes v1.29 a sidecar can be an init container with restartPolicy: Always. It starts before the app and stops after it. The feature is stable in v1.33.

The kubelet rotates logs; the node removes them with the Pod

Kubelet defaults

file sizecontainerLogMaxSize: 10Mi
files keptcontainerLogMaxFiles: 5
read limitkubectl logs returns at most 10MiB

Ship logs before the Pod is gone. Afterward nothing remains to read.

A node-level collector is a DaemonSet with one agent per node. It reads every container's log file, labels each line and forwards it to a store.

"Metrics" names two separate pipelines

Resource Metrics API

metrics-server collects CPU and memory from each kubelet and serves them on metrics.k8s.io.

read bykubectl top and the HPA
holdsCPU and memory, present values only
on failkubectl top errors; the HPA reads unknown

Application metrics

A workload publishes numbers about itself at an HTTP endpoint. Prometheus pulls them on an interval.

read byPrometheus, then dashboards and alerts
holdsany number the app defines, as a time series
on failgraphs go flat while kubectl top still works

The exposition format and four metric types

# HELP calls_active Calls in progress. # TYPE calls_active gauge calls_active 42 # HELP calls_total Calls handled. # TYPE calls_total counter calls_total 18734

Keep label values bounded. Every distinct value creates a new time series.

Prometheus reads no annotation by default;
its scrape configuration decides

Annotation convention

The prometheus.io/scrape, port and path annotations are a community convention. They work only if the scrape configuration reads them.

discoversPods; one target per declared container port
wrong portthe scraper calls a port nothing serves

ServiceMonitor

A Prometheus Operator resource. It selects Services by label and names the Service port to scrape.

discoversthe endpoints behind each selected Service
no endpointsthe scraper finds nothing to call

A scrape target fails in two silent ways

FailureCausePrometheus shows
DOWNDiscovery works. The scrape fails: wrong port, wrong path, refused connection.A target with up equal to 0

An alert on up == 0 catches DOWN only. An absent target has no series to evaluate. Check the Service endpoints before the port.

Recap

  • Three signals, three questions. Choose the signal before you type.
  • All three are ephemeral. A durable stack exists to replace them.
  • A container that never started has no logs. Its Events name the cause.
  • The logging contract is stdout and stderr. --previous pins the instance that died.
  • A scrape fails as DOWN or absent. Check the endpoints, then the port.

Production thinking

  • A failure happens at 02:00 and heals by 02:20. At 09:00 the Pod is gone and its Events are past the TTL. Which signal would have told the story, and what do you stand up so the next review is not a guess?
  • An alert on up == 0 stays quiet while a workload's dashboards are blank. Which state produces this, and which expression catches it?
  • One vendored component writes only to a file. What do you add for that Pod, what does it cost, and why is it the exception?
