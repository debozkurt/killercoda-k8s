Observability

Three signals a running cluster already gives you — events, logs, metrics — and a fourth you add, traces.

Each answers one kind of question, and all three built-in signals are ephemeral. The skill is reading the right one fast — reach for the wrong signal and you burn an hour.

What you'll walk away with

  • Separate the three built-in signals by the question each answers — events (what the control plane did), logs (what the process said), metrics (how much it's using / how it behaves) — and reach for the right one first
  • Read an Event as a structured object — type, reason, involvedObject, count — and survey the stream with --field-selector and --sort-by
  • Retrieve logs under pressure: --previous for a container that already crashed, -c for the right container, --since / --tail / -f to scope the firehose
  • Read the container logging contract — stdout/stderr only — and its two fixes: log to stdout, or a streaming sidecar
  • Tell the two metrics pipelines apart — the Resource Metrics API (kubectl top, HPA) versus application metrics (Prometheus scrape) — and diagnose a scrape target that's down
  • Place traces (OpenTelemetry) in the picture: what a span is, and the cross-service latency question logs and metrics structurally can't answer

Three signals, one question each

Events, logs, and metrics ship with the cluster; traces you add. Each answers exactly one kind of question — match the question to the signal before you start typing.

All three built-in signals are ephemeral

Events

Garbage-collected after a TTL (~1h). A failure that recovered two hours ago has no events left.

Logs

Files on the node, rotated in place. Delete the Pod and they go with it.

Metrics (kubectl top)

Point-in-time only. No history is kept at all.

That impermanence is the whole reason a production platform runs a durable layer on top — a log store fed by node collectors, a metrics time-series database fed by scrapes, a tracing backend fed by spans. kubectl reads the live, expiring signal at 3am; the stack answers "what happened last Tuesday."

Events — the control plane narrating itself

An Event is not a log line. Your app doesn't write it; the scheduler, kubelet, and controllers emit one whenever they act on an object. When a Pod is Pending and has no logs yet, the event stream is the only signal that exists.

typeNormal (routine lifecycle) or Warning (trouble) — triage reads Warnings first
reasonthe stable machine token (Unhealthy) — the best --field-selector key
involvedObjectwhat it's about (pod/reg-proxy-0) — the key describe matches to a UID
countx47 means it fired 47 times, aggregated into one row — a climbing count is an active fire

describe reads one object;
get events surveys the stream

kubectl describe <kind> <name>

The events for one object, matched by involvedObject to its UID. Reach for it when you already know the suspect.

kubectl get events

Surveys the whole stream, shaped with selectors. Reach for it when you don't yet know where the problem lives.

kubectl get events -n signaling --sort-by=.lastTimestamp # oldest→newest; read the bottom kubectl get events -A --field-selector type=Warning # only the trouble, cluster-wide

Events are namespaced (reach for -A when you don't know where it lives) and get events is unsorted by default — always add --sort-by=.lastTimestamp or you'll misread the order.

The logging contract — stdout and stderr only

The kubelet redirects a container's stdout/stderr to a file on the node, and kubectl logs streams that file back. Nothing else is captured.

App logs to stdout/stderr

kubectl logs sees it, and the node-level collector ships it. This is the twelve-factor convention — and the whole contract.

App logs to a file in the container

kubectl logs is empty on a Running Pod. The app is logging fine to /var/log/app/app.log; you just can't see it.

Fix it by making the app log to stdout, or — when you can't change the app — by adding a streaming sidecar.

The logs flags that earn their keep

--previous / -pthe logs of the prior, terminated instance — why the last one died. After a restart, plain kubectl logs shows the fresh start (often clean and misleading). The single most important logs flag at 3am.
-c / --all-containersa multi-container Pod makes logs ambiguous. A 1/2 Pod means one of two containers is down — read that one.
--since / --tailscope the firehose to a window (--since=15m) or a line count (--tail=100).
-ffollow (stream) the log live.
kubectl logs <pod> -c <container> --previous # why the dead instance died kubectl logs <pod> --since=15m --tail=100 -f

Two ways to get logs off the node

Node-level collector a DaemonSet

One agent per node (Fluent Bit, Vector) tails every container's stdout/stderr files, tags each line with Pod and namespace, and forwards to a store.

The default: zero-config for the app as long as it logs to stdout, one agent covers every Pod on the node.

Streaming sidecar

When an app insists on writing to a file, add a second container that shares a volume and does tail -F to its stdout, so the file's lines flow to stdout and the collector picks them up.

Costs a container and some memory per Pod — the fallback, not the default.

Logs are as ephemeral as the Pod. Anything you want after the Pod is gone has to be shipped off the node while it's still there.

"Metrics" is two separate pipelines

Confusing them is the most common metrics mistake, so pin the distinction first.

Resource Metrics API

metrics-server scrapes each kubelet for live CPU and memory per Pod and Node, served on metrics.k8s.io. Powers kubectl top and the HPA.

CPU/memory only, right now only, no history. No metrics-server → top errors and the HPA reads <unknown>.

Application metrics

Anything richer — calls/sec, queue depth, error ratio, p99 latency — the workload publishes about itself. The ecosystem standard is Prometheus.

Everything the Resource Metrics API is not. A different pipeline, a different failure mode.

kubectl top nodes # per-node CPU/memory vs. capacity kubectl top pods -A --sort-by=memory

Prometheus pulls; the workload exposes and waits

Each workload exposes an HTTP endpoint (by convention /metrics) in a plain-text exposition format, and Prometheus periodically scrapes it. The workload never pushes.

# HELP sip_calls_active Currently active calls. # TYPE sip_calls_active gauge sip_calls_active 42 # HELP sip_calls_total Calls since start. # TYPE sip_calls_total counter sip_calls_total 18734

The four metric types

counteronly goes up — a total; you rate() it
gaugegoes up and down — a level (active calls, memory)
histogrambuckets observations — latency distributions, for percentiles
summarya client-side percentile

A scrape target down looks nothing like a sick app

prometheus.io/* annotations

The lightweight convention: scrape, port, and path annotations on the Pod tell Prometheus what to pull.

ServiceMonitor

The production way: a Prometheus Operator resource — "scrape every Pod behind this Service, on the port named metrics."

If the declared port doesn't match the port serving /metrics, the scrape is refused, the target shows DOWN, and every graph goes flat — while the app is healthy and kubectl top still works. A metrics gap with a green top is a pipeline-2 scrape problem, not a sick app.

Every distinct label value is its own time series. A label like call_id with millions of values — high cardinality — can bury the database. Keep labels bounded.

Traces answer what metrics and logs can't

Metrics aggregate (p99 across all calls); logs are per-process (what this container said). Neither answers: for this one slow call, which of the services it touched ate the 900ms?

The building blocks

spanone timed operation — one service handling one request
tracethe tree of spans for one request, stitched by a propagated trace ID (traceparent)
OpenTelemetrythe vendor-neutral standard — SDKs, the OTLP format, the Collector

When metrics say "slow" and logs say "each service looks fine," the missing signal is a trace across the call path. Read the trace and the slow hop is the long bar.

What to carry forward

  • Three signals, three questions. Events = what the control plane did; logs = what the process said; metrics = how much it's using / how it behaves. Match the question before you type.
  • All three built-in signals are ephemeral — events expire, logs die with the Pod, kubectl top keeps no history. That impermanence is why a durable stack exists.
  • Events are structured objects, not text — read type, reason, involvedObject, count; a climbing count is an active fire.
  • The logging contract is stdout/stderr only — fix a file-logging app with stdout or a streaming sidecar; --previous reads a container that already died.
  • Metrics are two pipelines — a gap with a healthy kubectl top is a scrape problem, not a sick app.
