Policy as Code

A policy engine — Kyverno or OPA Gatekeeper — runs your organization's rules as admission webhooks: rejecting non-compliant objects, rewriting them to a safe default, and refusing images you didn't sanction.

One more gate on every write to the API server. After RBAC says yes, admission asks the question authorization can't: is this a good object?

What you'll walk away with

  • Where a policy engine plugs in — as admission webhooks, mutating first then validating, after RBAC and before the object is stored
  • How to read a Kyverno ClusterPolicy: the match, the rule type, and the failureAction
  • The three rule types worked here — validate (reject), mutate (rewrite), verifyImages (check signatures)
  • Reading a rejection: the admission webhook denied signature, and where it lands
  • Kyverno versus OPA Gatekeeper — YAML rules versus Rego
  • The engine's own failure modes: autogen and failurePolicy

RBAC answers who;
policy answers is this a good object

Authorization decides whether an identity may make a call. It cannot judge the object that call carries — and the identity is allowed to create Pods.

A Pod with no limits, a :latest tag, a hostPath into the node, an image from an unvetted registry — none is an authorization question. They're policy questions, and the place to enforce a rule on an object's content is admission.

RBAC — M10

May this identity make this call? Verb, resource, scope.

By the time the engine runs, RBAC has already said yes. It inspects the object and decides whether this specific YAML is acceptable — rejecting or fixing it.

Kyverno registers its webhooks dynamically, only for the kinds and namespaces some policy actually matches — so the engine isn't in the path of everything, and never a single point of failure for the whole API.

Admission has an order: mutate first, then validate

Mutating webhooks run first, so a default a mutate rule injects is already present when a validate rule checks for it. Validating webhooks only accept or reject.

Read a rule the way you read a Role

match

Which objects the rule governs — kinds and namespaces, narrowed by an optional exclude. Wrong match, and the rule silently never fires.

rule type

Exactly one action: validate (check, maybe reject), mutate (rewrite), or verifyImages (check signatures).

failureAction

For a validate rule: Enforce blocks a violation, Audit admits it and records a report.

A ClusterPolicy is cluster-scoped, a Policy is namespaced; each holds a list of rules. The policy reads like the objects it governs — the point of expressing rules as YAML.

Validation rejects the non-compliant

A validate rule is the workhorse: a match that selects objects and a check they must satisfy. The readable default is a pattern — a partial object the target must match, with '?*' meaning "any non-empty value."

The denial names everything you need to find the rule: the webhook, the policy, the rule, and your message — exactly as an RBAC Forbidden named the identity, verb, and resource.

# Pod in tenant-apps, no resource limits kubectl apply -f pod.yaml Error from server: admission webhook "validate.kyverno.svc-fail" denied the request: ... blocked due to policies: require-resource-limits: require-limits: 'CPU and memory limits are required.'

Autogen decides where a rejection surfaces

A rule matching Pod makes Kyverno auto-generate sibling rules for pod controllers, so the same check guards the Deployment. One annotation flips which of two very different failures you see.

Autogen on default

The violating Deployment is rejected the instant you kubectl apply it. It's never created; the error shows up directly in kubectl or CI.

Autogen off

The Deployment is admitted, but its ReplicaSet can't create the Pod. Stuck at 0/N, no Pods to describe — the denial rides a FailedCreate event on the ReplicaSet.

The 0/N with nothing to describe is the PodSecurity signature from M10 — the one to recognize when a rollout stalls with no Pending Pod.

Enforce blocks; Audit records — the safe-rollout tool

Land as Auditthe rule admits everything, records each violation in a PolicyReport
Read the reportswhat Enforce would reject, before it does
Flip to Enforceonce the fleet complies, turn violations into hard rejections

Audit

Admits the object, writes a PolicyReport pass/fail per resource. The audit trail and the dry run.

Enforce

A violation becomes a hard denied the request. The enforce-vs-audit split PodSecurity gave you, generalized to any rule.

Mutation rewrites the object on its way in

A mutate rule supplies defaults authors can't forget — an owner label, an injected sidecar, a set field. The consequence that defines it: the stored object is not the one you submitted.

kubectl get pod -o yaml shows a label no one wrote. That's the feature — safe defaults enforced centrally — and the trap: when a live field doesn't match the manifest on disk, a mutate rule is the suspect.

# the rule, applied at admission mutate: patchStrategicMerge: metadata: labels: +(owner): platform # +() = add only if absent # the live Pod carries the label — # the submitted YAML never did

Mutation fires only at admission — never on running Pods

A mutate rule runs on create and update, the moments an object crosses the webhook. It does nothing to Pods already running. So a missing injected default has two causes that look identical from the Pod:

The rule didn't match

Wrong kinds, a typo'd namespace — the Pod was never a candidate. Fix: correct the match.

The Pod predates the policy

The rule is correct, but the Pod was admitted before it existed. Fix: trigger fresh admission with kubectl rollout restart.

Fixing the policy alone never retro-fixes running Pods. New Pods pass the webhook and get mutated; old ones stay as they were admitted.

Image admission: what is allowed to run here

The supply-chain gate, at three levels — cheapest to strongest — each answering is this image allowed before it's ever pulled onto a node.

Tag discipline

Forbid the mutable :latest (and bare tags). latest means "whatever was pushed last," so the running image can change with no manifest change. Force a pinned version.

Registry allow-list

Require every image from an approved registry, e.g. registry.polyphone.example/*. A typo'd or malicious public image is rejected at admission, not pulled.

Signature verification

The strongest: verifyImages proves the image was signed by a key you trust (cosign) before it runs, and can pin it to its digest.

Allow-list says "from our registry" — anyone who can push passes. A signature says "our pipeline signed this" — a compromised registry push still fails.

Neither is "correct." Both are admission webhooks, both split enforce-vs-audit, both surface the same denied the request. Learn one and you can read the other.

The engine has its own blast radius: failurePolicy

One webhook setting decides what happens when the engine itself is unreachable — the sharpest failure, because it's the engine, not your workload.

failurePolicy: Fail fail closed

Secure — an unreachable webhook denies. But a down engine blocks every deploy in scope until it recovers.

failurePolicy: Ignore fail open

Deploys keep flowing — unpoliced. Your security posture is off for the window the engine is down.

The pick isn't the same for every webhook. A validating image-signature check leans Fail; a mutating label-injection rule can afford Ignore. Know which your cluster runs.

What to carry forward

  • A policy engine is admission-as-code — mutating and validating webhooks judging an object's content. admission webhook denied is a policy event, not a workload bug; the message names the fix.
  • Validate rejects or audits — land as Audit, read the PolicyReports, then flip to Enforce.
  • Autogen decides where a rejection surfaces — at apply, or as a 0/N with nothing to describe.
  • Mutation happens only at admission — the stored object differs from the submitted one; re-admit with rollout restart, never a retro-fix.
  • Image admission is the supply-chain gate — pin tags, allow-list registries, verify signatures at the one place you can still say no cheaply.
  • The engine has a blast radius — failurePolicy decides whether a down engine fails closed or open.
