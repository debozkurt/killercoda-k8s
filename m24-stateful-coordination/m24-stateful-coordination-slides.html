Stateful coordination
identity, discovery, leadership

How a set of Pods stops being an interchangeable herd and becomes a coordinated cluster — and the three ways that coordination breaks while every Pod still looks healthy.

When a coordinated workload misbehaves, the Pods usually look fine. The diagnosis lives in the coordination objects — the StatefulSet, the Service, the Lease — not in kubectl logs.

Most Pods are interchangeable;
some cannot be

Stateless herd

A Deployment behind a Service. Any replica answers, a dead Pod is replaced by an equivalent one with a new name and an empty filesystem, and one VIP hides which replica you reached.

This is why stateless services scale and heal so easily.

Coordinated cluster

Members keep a stable identity, address each other directly, come up in a known order, and agree on one leader for work only one may do.

A replicated cache, a database's replicas, a router that writes an authoritative table.

Two members both writing the authoritative table is a split-brain incident, not a scaling event. That guarantee is what coordination buys.

Three questions, three objects

A coordinated workload stands on three primitives. When it breaks, ask these in order — each has one object that answers it, and none is the Pod's logs.

Identity

Which member is this, and does its state survive a restart?

readthe StatefulSet and its PVCs

Discovery

How does a peer reach one specific member, not a load-balanced VIP?

readthe governing Service

Leadership

Which single member does the work that only one may do at a time?

readthe Lease and its RBAC

A StatefulSet pins identity —
and storage — to an ordinal

StatefulSet · session-cache
session-cache-0data-session-cache-0
session-cache-1data-session-cache-1
session-cache-2data-session-cache-2
volumeClaimTemplates — one PVC per ordinal, bound for the life of the identity

The ordinal <name>-N is sticky: a deleted session-cache-1 is replaced by another session-cache-1, not a random new member.

The replacement re-mounts the same PVC. State follows the identity, not the Pod — a member can restart or rejoin as itself.

OrderedReady: one member at a time

Create ordinal 0then wait until it is Running and Ready
Create ordinal 1only after 0 is Ready
Create ordinal 2only after 1 is Ready — scale-down reverses this

OrderedReady default

Act on one ordinal at a time, each waiting for the previous to be Ready. Needed when member 0 must bootstrap before 1 can join.

Parallel

Act on all Pods at once — faster, but only safe when members do not depend on startup order.

The set is only as available as its lowest unready ordinal.

An unready low ordinal
halts every higher one

# three replicas declared kubectl get statefulset session-cache NAME READY AGE session-cache 0/3 6m # but only one Pod exists kubectl get pod -l app=session-cache NAME READY STATUS session-cache-0 0/1 Running

Not a scheduling problem

Ordinal 0 is Running but never Ready — a broken readiness probe, an unschedulable Pod, a failing init. So -1 and -2 were never created. There are no Pending Pods to describe.

Diagnose the first unready ordinal. Then delete the wedged Pod — OrderedReady will not reroll a template onto a Pod that was never Ready.

A headless Service
publishes per-Pod DNS

A normal Service allocates one VIP and hides which replica you reached. For coordination you need the opposite: reach session-cache-1 specifically.

clusterIP: None

No virtual IP. DNS resolves the Service name to the set of Pod IPs, and publishes a stable per-Pod name for each ordinal.

per-pod name<pod>.<svc>.<ns>.svc.cluster.local
wired bythe StatefulSet's spec.serviceName
# resolves to exactly one member's IP session-cache-0.session-cache.media .svc.cluster.local

Bootstrap chicken-and-egg — peers must find each other before any is Ready? Set publishNotReadyAddresses: true.

Per-Pod DNS is a property
of a headless Service

Headless

clusterIP: None. DNS returns the Pod IPs and a per-Pod name for each member — a peer can address one specific ordinal.

Ordinary VIP

A clusterIP is assigned. The per-Pod records vanish; the Service name now resolves to one load-balancing IP that hides members. The Pods are untouched and healthy — only discovery breaks.

clusterIP is immutable. You cannot kubectl edit a VIP Service back to headless — you delete and recreate it.

A Lease is a distributed lock

Leadership decides which single member does work only one may do at a time. The primitive is a Lease, a small object in the coordination.k8s.io group.

The control plane runs on it: the scheduler and controller-manager run several replicas, but the active one is simply whoever holds the Lease named for the component. Your own singletons use the identical mechanism.

The spec is the whole protocol

holderIdentitywho holds the lock; every other replica reads this and stays passive
renewTimewhen the holder last proved it was alive
leaseDurationSecondshow long the lock stays valid without a renewal
acquireTimewhen the current holder first took the lock

Take over

A live leader bumps renewTime every few seconds. A renewTime that stops advancing is a leader that has died or stalled.

Correctness invariant: leaseDuration > renewDeadline > retryPeriod. Invert the first two and a healthy leader can be declared dead while it still leads — two leaders.

Taking the lock needs permission

Both Pods healthy, nothing leads

Acquiring and renewing a Lease means writing it. The election client acts as its Pod's ServiceAccount, which must hold get, create, and update on leases.

Miss any verb and the client is forbidden from the lock: no Lease is ever held, the singleton work never runs — while both Pods sit Running.

# reproduce it in one line kubectl auth can-i update \ leases.coordination.k8s.io -n media \ --as=system:serviceaccount:media:coordinator no

A no where you need a yes is the whole diagnosis. Leadership lives in the Lease; the ability to take it lives in the Role.

A Lease coordinates;
it does not fence

A Lease is a cooperative lock. It coordinates well-behaved clients that all agree to check it before acting. It cannot stop a process that ignores it.

The zombie leader

A leader hangs past leaseDuration on a long GC pause, a challenger steals the lock, then the first wakes still believing it leads — and keeps writing. The Lease did nothing to stop it.

Fencing

Real safety needs the shared resource itself — a database, a volume — to reject writes from a stale leadership epoch, using a monotonic fencing token it checks.

Kubernetes leader election gives you fast, cooperative failover, not fencing. If two writers would corrupt data, the protection has to live in the resource.

The differential:
identity, discovery, leadership

Walk the three questions in order. Each failure branch maps to exactly one object to read — the Pod's status tells you it's stuck; the coordination object tells you why.

Recap

  • StatefulSets trade interchangeability for identity. Sticky ordinals and a per-member PVC via volumeClaimTemplates pin state to the identity, not the Pod.
  • OrderedReady makes a set only as available as its lowest unready ordinal. Missing higher ordinals were never created — diagnose the first unready one.
  • Per-Pod DNS is a property of a headless Service. clusterIP: None publishes per-Pod names; a VIP hides members, and clusterIP is immutable.
  • A Lease is a lock, and taking it needs permission. A leaderless singleton with healthy Pods is almost always missing get/create/update on leases.
  • A Lease coordinates, it does not fence. Protection against a zombie leader lives in the shared resource, not the Lease.
