Kustomize —
bases & overlays

One base, many environments, no templating language. Kustomize composes plain YAML with more YAML — and its failures land in three separate layers.

Every Kustomize problem is a build, an apply, or a runtime failure — and each has a different first command. Name the layer and you have most of the fix.

What you'll walk away with

  • Compose an environment from a shared base plus environment-specific overlays, and read any kustomization.yaml
  • Render locally with kubectl kustomize and apply with kubectl apply -k — and know why rendering first is the discipline
  • Patch two ways — strategic-merge and JSON 6902 — and understand how a patch finds the resource it targets
  • Generate ConfigMaps and Secrets, and reason about the name-suffix hash and the reference rewriting it drives
  • Apply transformers — namespace, labels, images, namePrefix — without the immutable-selector trap
  • Reuse cross-cutting slices with components
  • Locate any failure to build, apply, or runtime — each has a different first command

Kustomize renders; it never runs

kubectl kustomize <dir> is a pure function — a directory of YAML in, one stream of YAML out, no cluster touched. apply -k is that same function with an apply stapled on the end.

The cluster never sees the kustomization — only the rendered objects, which look exactly like hand-written manifests. Nothing in the cluster knows Kustomize exists.

That one fact organizes every failure you will debug: the problem is in the render, in the apply, or in what the render produced at runtime.

Two commands, one function

kustomizekubectl kustomize — build, print, touch nothing
apply -kbuild, then apply the result
the clustersees plain objects, never the kustomization

Because rendering is separate from applying, render first, every time. kubectl kustomize shows you exactly what the cluster will get before it gets it.

One base is the source of truth;
overlays are reviewable diffs

A base captures what every environment shares. Each overlay points its resources: at that base, then layers on only its departures.

# base/kustomization.yaml — the common core resources: - deployment.yaml - service.yaml namespace: edge configMapGenerator: - name: edge-relay-config literals: [LOG_LEVEL=info]
# overlays/prod/kustomization.yaml — the diff resources: - ../../base images: - {name: nginx, newTag: "1.27"} patches: - path: replicas-patch.yaml

resources: does double duty — raw manifest files and other kustomizations, which is how composition happens. A fix to the base reaches every environment on the next build. A wrong relative path fails the build: accumulating resources ... no such file.

A transformer touches everything;
a patch touches what it targets

Because a patch changes specific resources, it must identify which — and if it can't, Kustomize fails the build rather than silently doing nothing.

Strategic-merge

A partial resource. Matched by apiVersion/kind/name, then merged — it understands list-merge keys and reads like the resource. The default for shaping fields.

missfailed to find unique target for patch

JSON 6902

An operation list against explicit paths — /spec/replicas — on a named target:. Positional: containers/0 is by index. For add/remove/replace where merge semantics get in the way.

traitprecise and brittle — reorder the list, break the index

A mismatched target is a build failure — nothing reaches the cluster. Reconcile the two names: either the patch is stale, or the base was renamed.

A generator ties a config object's name
to its contents

configMapGenerator builds a ConfigMap and appends a hash of its data to the name — edge-relay-config-4f9dk2. Different content, different name.

A hand-written ConfigMap has a fixed name; edit its data and running Pods keep their old values, because no Pod template changed to trigger a rollout.

A generator ties the name to the content, so any edit becomes a new name, a reference change, a Pod-template change — a rollout. Config change becomes rollout, automatically.

secretGenerator works identically but base64-encodes — base64 is not encryption. disableNameSuffixHash: true gives a stable name, at the cost of the automatic rollout.

Reference rewriting binds
only on a name match

For the hash to reach a Deployment, Kustomize rewrites references — but only where the reference's name equals the generator's declared name.

A Deployment whose envFrom names edge-relay-config gets rewritten to the hashed name. One that names edge-relay-conf does not — Kustomize never recognizes it as a reference to this generator.

The name match is the load-bearing detail. Get it wrong and the render is internally inconsistent while still being valid YAML.

A valid apply that can't start

The render holds a hashed ConfigMap and a Deployment pointing at a plain name that doesn't exist. Valid YAML, clean apply, and a Pod stuck in CreateContainerConfigError.

This is the runtime layer — build and apply both succeeded. First move: kubectl kustomize and compare the generated name to the reference.

Labels that reach the selector
collide with immutability

commonLabels writes onto metadata, Pod templates, and every selector. The modern labels: transformer leaves selectors alone unless you set includeSelectors: true.

A Deployment's selector is immutable after creation — it's the identity link between the Deployment and the ReplicaSets and Pods it owns.

On a fresh namespace, commonLabels is harmless; the selector is being set for the first time. Promote that same overlay over an already-running Deployment and the API server rejects it.

The apply rejection

spec.selector ... field is immutable — the build was fine, the render valid. The object already in the cluster is what made the apply illegal.

This is the apply layer. Keep labels off the selector — labels: with includeSelectors: false — for anything already running; reserve selector-touching labels for greenfield resources.

A base can't carry patches;
a component can

A component — kind: Component — is a reusable slice of patches, resources, and generators that an overlay opts into via components:.

Base what everyone builds on

Raw resources plus the transforms common to every environment. It renders on its own.

reach for itwhen the same resources recur across overlays

Component a capability you turn on

An optional slice some environments enable — a regional-affinity pin, a debug sidecar, a monitoring annotation set. Prod enables it, lab skips it, from one definition.

reach for itwhen the same change recurs across overlays

Extract a component when the same change is copy-pasted across overlays — but not too early. A premature abstraction is its own cost.

What to carry forward

  • Kustomize renders; it never runs. kubectl kustomize is a pure function; apply -k is that plus an apply. Render before you apply.
  • One base is the source of truth; overlays are reviewable diffs. No templating language — YAML transformed by YAML.
  • A generator ties a ConfigMap's name to its contents and rewrites references by name match. Break the match and you get a valid apply that can't start.
  • Failures live in three layers — build, apply, runtime. An empty cluster means read the build; an immutable-field rejection means diff live-vs-render; a broken Pod means the normal loop.
  • Transformers that reach into selectors collide with immutability. Keep labels off the selector for anything already running.
