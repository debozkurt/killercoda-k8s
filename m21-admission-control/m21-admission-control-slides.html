Admission control:
webhooks in the write path

Two configuration objects splice your own HTTPS callbacks into the API server's write path — one rewrites objects, one accepts or rejects them — after RBAC, before anything is stored.

Read the error before you touch anything. failed calling webhook is infrastructure — the server was unreachable or untrusted. admission webhook denied the request is policy — it was reached, and said no.

What you'll walk away with

  • Place a webhook in the request pipeline — registered by a MutatingWebhookConfiguration or ValidatingWebhookConfiguration, and called during admission
  • Read a webhook configuration the way you read a Role — its clientConfig, rules, selectors, and failurePolicy
  • Internalize the order — all mutating webhooks, then schema re-validation, then all validating webhooks
  • Reason about failurePolicy as a blast-radius choice — Fail fails closed, Ignore fails open
  • Recognize the TLS contract — a webhook is HTTPS, so its caBundle and the cert's SAN must line up or every call fails
  • Scope a webhook to exactly what it governs — and tell a raw webhook from ValidatingAdmissionPolicy

Webhooks live in the third gate

Every write crosses three gates in order: authentication asks who, authorization asks may they, admission asks is this object allowed. By the time a webhook runs, RBAC has already said yes — it inspects the object itself.

A webhook can only rewrite or reject the object in front of it. It never re-decides identity or permissions — those gates already passed.

Admission is a chain,
and the order is fixed

For a write, the API server calls every mutating webhook, re-checks the object against the schema, then calls every validating webhook. Only if all of them allow it does the object reach etcd.

A positive namespaceSelector fails safe — a namespace without the label is simply never intercepted.

The TLS contract:
two checks before any policy runs

A webhook is an HTTPS endpoint, so the API server verifies its serving certificate like any TLS client. Both checks happen before a single byte of policy logic runs.

SAN must match the dialed name

The cert's SAN must include <name>.<namespace>.svc — the name the API server dials.

errorx509: certificate is valid for …, not admission-guard.admission.svc
look atthe cert's SAN vs the Service DNS name

caBundle must match the signer

The caBundle must be the CA that signed the serving cert — usually broken by a certificate rotation.

errorx509: certificate signed by unknown authority
look atthe config's caBundle vs the served cert; the CA injector

Either way the request is treated as a failed call, and failurePolicy decides its fate. A webhook that worked yesterday and x509-rejects everything today is a cert/caBundle mismatch until proven otherwise.

A broken mutation surfaces
as a validating denial

All mutating webhooks run before any validating one, so a validating rule can require a field a mutating webhook injects. e.g. mutation adds env=tenant; validation requires env. That ordering is a contract you can build on — and it couples the two.

The trap: if the mutating webhook stops firing — wrong operations, a selector that no longer matches, a down backend under Ignore — the label is never injected, and the validating webhook rejects the object for a missing field the author never had to set. The error points at validation; the fault is upstream in mutation.

failurePolicy is a blast-radius choice,
not a default to ignore

The load-bearing question is what happens when the webhook doesn't answer — a crashed backend, a network partition, a TLS mismatch, a timeout past timeoutSeconds.

Fail — fails closed

An unreachable webhook is treated as a denial. The gate holds even when the enforcer is down.

safe fora security control you must never bypass
costa down backend blocks every write it matches

Ignore — fails open

An unreachable webhook is treated as an allow. Writes keep flowing when the enforcer is down.

safe foravailability — a convenience not worth blocking a deploy
costpolicy silently stops enforcing, with no error

There is no universally right answer — only a tradeoff that interacts with scope. A hard security rule on tenant Pods is reasonably Fail because it is scoped to tenant namespaces.

The combination that wedges a cluster

failurePolicy: Fail plus rules that match Pods in every namespace plus an unreachable backend. Now the API server can't create Pods anywhere — including the webhook's own backend, which can never come back.

Scope tightly

Use rules and namespaceSelector so the webhook only sees what it governs.

Exclude the control plane

Always exempt kube-system so the cluster can heal itself. Not optional.

Short timeoutSeconds

A slow webhook degrades instead of hanging every write in scope.

This is the canonical "a webhook took down the cluster" incident. The defenses are structural — you build them into the configuration, not into the backend's uptime.

You may not need a webhook at all

ValidatingAdmissionPolicy runs a CEL expression inside the API server — no server, no Service, no serving cert, no caBundle to keep in sync.

# the whole check, evaluated in-process kind: ValidatingAdmissionPolicy spec: matchConstraints: resourceRules: - resources: ["pods"] operations: ["CREATE"] validations: - expression: "'env' in object.metadata.labels" message: "Pod must carry an 'env' label"

What it removes

The check runs inside the API server, so there is no backend to be unreachable — it can't fail-closed-wedge the cluster on a dead server.

What it can't do

CEL expresses validation, not arbitrary logic, external lookups, or signature checks. Those still need a webhook.

What to carry forward

  • A webhook is your code in the write path, registered by one object. Read the MutatingWebhookConfiguration or ValidatingWebhookConfiguration first — it says what to call, what to intercept, and what to do on failure.
  • Order is fixed: all mutating, then all validating. Validation sees the mutated object, so a broken mutation surfaces as a validating denial for a missing field — fix the upstream mutation.
  • failurePolicy is a blast-radius choice. Fail fails closed; Ignore fails open. Scope tightly, exclude kube-system, set a short timeout.
  • Read the error to split infrastructure from policy. failed calling webhook means unreachable or untrusted; denied the request means reached and refused.
  • You may not need a webhook. ValidatingAdmissionPolicy runs CEL in-process — reach for it when CEL suffices, keep webhooks for logic, external data, and signatures.
