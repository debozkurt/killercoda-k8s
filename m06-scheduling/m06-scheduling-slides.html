Scheduling:
which node runs each Pod

Requests, limits, QoS, taints, affinity and spread: the fields the scheduler reads, and the signature each leaves when a Pod does not run.

A Pending Pod starts no container and writes no log. One FailedScheduling event names the reason each node refused it.

What you'll walk away with

  • The scheduler's three moves: filter, score, bind, and the order the filters run
  • Requests and limits: the scheduler fits the request, and the kernel enforces the limit
  • QoS classes: how Kubernetes derives them, and what they do and do not decide under node pressure
  • Taints and tolerations: nodes that repel Pods, and the exception a Pod carries
  • Affinity and spread: steering Pods onto labeled nodes, spreading replicas, and how a hard rule leaves replicas Pending
  • The Pending differential: one message entry per filter, plus the runtime OOMKilled counterpart

The scheduler filters, scores, then binds

kube-scheduler "selects an optimal node to run newly created or not yet scheduled (unscheduled) pods".

  • No feasible node: the Pod stays Pending, and the scheduler records FailedScheduling.
  • Scheduling fails at the filter, never at the score.
  • After the bind, the kubelet on that node starts the containers.

Common node filtering checks

These are common reasons a node becomes infeasible. The table groups them by purpose, not execution order.

CheckWhat the node must satisfyWhen it matters
TaintsThe Pod tolerates the node's blocking taints.The node has NoSchedule or NoExecute taints.
Node selectionThe node matches required selectors and node affinity.The Pod or scheduler profile adds placement requirements.
ResourcesThe node has enough available CPU and memory for the Pod's requests.The Pod requests resources.
Pod placementThe placement satisfies required anti-affinity and hard spread constraints.The Pod defines required rules.

For each node, filter plugins run in the configured order and stop after the first rejection. Nodes may be checked concurrently.

The FailedScheduling event
is the diagnosis

kubectl describe pod <pod> -n <ns> ... Warning FailedScheduling 0/2 nodes are available: 1 Insufficient memory, 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }. preemption: 0/2 nodes are available: ...
  • 0/2: no evaluated node passed every required filter.
  • Each entry groups nodes rejected for the same reason. The text order does not show plugin order.
  • The preemption: clause says whether evicting a lower-priority Pod would help. Stop reading before it.

A kubeadm control-plane node carries a NoSchedule taint, so on a small cluster every message has an entry for it. Read the entry for the nodes you expected the Pod to use.

Two numbers per resource,
and a different reader for each

spec: containers: - name: app resources: requests: { cpu: 25m, memory: 32Mi } # read by the scheduler, before placement limits: { cpu: 100m, memory: 64Mi } # enforced by the node, while it runs
  • The scheduler sums a Pod's requests. It never reads limits or live usage.
  • A limit with no request: Kubernetes copies the limit into the request.
  • describe pod prints both blocks as Limits: and Requests:.

A request is a reservation
in the node's ledger

Allocatable is Capacity minus what the node reserves for the kubelet, the operating system and eviction. The scheduler compares requests with what is left.

# example: a node whose CPU requests are nearly booked kubectl describe node <worker> Capacity: cpu: 2 memory: 4Gi Allocatable: cpu: 2 memory: 3.6Gi ... Allocated resources: Resource Requests Limits cpu 1850m (92%) 3200m (160%) memory 1.1Gi (30%) 2.3Gi (64%)
  • The node above refuses a Pod that requests 200m CPU, even while its CPU sits nearly idle.
  • Limits may add up to more than 100%. The scheduler does not check them.

Requests are what you fit;
limits are what kill you

Request too large

No node has that much free Allocatable, so the scheduler places the Pod nowhere.

symptomPending, Insufficient memory
fixright-size the request, or add capacity

Memory limit too small

The Pod schedules and starts. The kernel's OOM killer kills it for going over its limit.

symptomOOMKilled, exit 137, CrashLoopBackOff
fixraise the limit above the working set
  • The kernel throttles CPU over the limit. The container runs slower and keeps running.
  • Memory limits "are enforced reactively": the kernel kills when it reclaims memory.

Kubernetes derives a QoS class
from requests and limits

ClassRule
Guaranteedevery container sets CPU and memory requests and limits, and each limit equals its request
Burstablenot Guaranteed, and at least one container sets a CPU or memory request or limit
BestEffortno container sets any CPU or memory request or limit
  • The API server sets it at creation, in status.qosClass. describe pod prints QoS Class:.
  • The class does not change for the life of the Pod, even under in-place resize.

OOMKill, eviction, preemption:
three killers, three owners

OOMKill

The kernel kills one container over its own memory limit. The Pod stays on its node and restarts in place.

readLast State: OOMKilled

Eviction

The kubelet terminates whole Pods when its node runs low. The Pod stays listed as Failed, and its controller replaces it.

readreason Evicted

Preemption

The scheduler deletes a lower-priority Pod so that a higher-priority Pending Pod fits. QoS plays no part.

readevent Preempted

An OOMKill leaves a climbing restart count on the same Pod. Eviction and preemption end the Pod, and a replacement appears.

A taint repels;
a toleration is the exception

"Taints are the opposite -- they allow a node to repel a set of pods." A taint is a key=value:effect mark on a node.

EffectScheduler, for new Pods without a tolerationRunning Pods without a toleration
NoScheduledoes not place themstay
PreferNoScheduleavoids the node, but places them rather than leave them Pendingstay
NoExecutedoes not place themevicted, after tolerationSeconds if set
  • "Tolerations allow scheduling but don't guarantee scheduling." A toleration is permission, not attraction.
  • To reserve a pool: taint it to keep others off, and give the workload a node affinity to go there.

Kubernetes adds its own
taints and tolerations

kubectl describe nodes | grep -E '^Name:|^Taints:' Name: controlplane Taints: node-role.kubernetes.io/control-plane:NoSchedule Name: node01 Taints: <none> kubectl describe pod <any-pod> | grep -A2 Tolerations Tolerations: node.kubernetes.io/not-ready:NoExecute op=Exists for 300s node.kubernetes.io/unreachable:NoExecute op=Exists for 300s
  • The node controller taints a failed node not-ready or unreachable, with NoExecute. Its Pods stay bound for 300s. Then the cluster evicts them, and their controllers create replacements.
  • DaemonSet Pods tolerate both with no time limit. kubectl cordon adds unschedulable:NoSchedule.

nodeSelector and node affinity
steer a Pod onto labeled nodes

spec: nodeSelector: disktype: ssd # hard: every label must match affinity: nodeAffinity: preferredDuringScheduling...: - weight: 50 # soft: weighted, never blocks preference: matchExpressions: - key: topology.kubernetes.io/zone operator: In values: [us-east-1a]
  • required... is a hard filter. No match: didn't match Pod's node affinity/selector.
  • IgnoredDuringExecution: "if the node labels change after Kubernetes schedules the Pod, the Pod continues to run."

Anti-affinity and topology spread
keep replicas apart

A topologyKey names the domain: kubernetes.io/hostname for one node, topology.kubernetes.io/zone for one zone.

Pod anti-affinity

Keeps a Pod away from Pods that match a label selector. required on hostname puts every replica on its own node.

Pendingdidn't match pod anti-affinity rules

Topology spread

Limits the skew between domains. whenUnsatisfiable picks the response.

hardDoNotSchedule, the default
softScheduleAnyway

A hard rule needs at least as many schedulable domains as it demands. A drain or a zone loss leaves the surplus replicas Pending.

What to carry forward

  • Filter, score, bind. A Pod that no node can take stays Pending, and its FailedScheduling event lists each node's first failed filter. Read it first.
  • Requests are what you fit, and limits are what kill you. Too large a request means Pending. Too small a memory limit means OOMKilled.
  • QoS estimates who suffers first, and requests decide it. The kubelet evicts Pods that use more than they request, then by priority.
  • Taints repel, and a toleration is permission, not attraction. NoSchedule leaves running Pods. NoExecute evicts them.
  • A hard placement rule is a guarantee and a trap. It leaves replicas Pending when domains run out, and required anti-affinity also repels a Deployment's own new Pods.
