Scheduling:
how Kubernetes selects a Node

Use scheduling events and Node state to diagnose a Pending Pod.

Focus: requests and limits, QoS, taints and tolerations, node selection, affinity, and topology spread.

Objectives

  • Explain how the scheduler filters, scores, and binds a Pod.
  • Use kubectl describe pod to read a FailedScheduling event.
  • Explain the difference between a resource request and a resource limit.
  • Explain how requests and limits determine a Pod's QoS class.
  • Diagnose scheduling failures caused by resources, taints, node selection, affinity, and topology constraints.

The scheduler filters, scores, and binds

  • Filter: remove Nodes that cannot run the Pod.
  • Score: rank the Nodes that passed filtering.
  • Bind: assign the selected Node to the Pod.
  • If no Node passes filtering, the Pod remains Pending.

Common scheduling filters

These checks are grouped by purpose. This table is not an execution order.

CheckRequirement
ResourcesThe Node has enough available resources for the Pod's requests.
TaintsThe Pod tolerates each blocking taint on the Node.
Node selectionThe Node matches required selectors and node affinity.
Pod placementThe placement satisfies required pod affinity, anti-affinity, and topology spread constraints.

Filter plugins run in their configured order. A Node stops at its first failed filter. Different Nodes can be evaluated concurrently. Scheduler configuration can change the enabled plugins and their order.

Start with FailedScheduling

kubectl describe pod <pod> -n <namespace> ... Warning FailedScheduling 0/2 nodes are available: 1 Insufficient memory, 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }. preemption: 0/2 nodes are available: ...
  • 0/2 means that no evaluated Node passed all required filters.
  • Each entry groups Nodes that failed for the same reported reason.
  • The event text does not show filter execution order.
  • Read the initial filter failures before the preemption: result.

Request = scheduling
Limit = runtime

Request

The scheduler uses the request to determine whether the Pod fits on a Node.

CPU500m
memory1Gi

Limit

The Node runtime enforces the limit after the container starts.

CPUCPU use is throttled above the limit.
memoryExceeding the limit can cause an OOM kill.

The scheduler uses requests. Low current CPU or memory use does not make a Node schedulable when its requested capacity is full.

A request must fit in Node Allocatable

Node Allocatable CPU: 2000m Existing Pod requests: -1850m ------- Available for requests: 150m New Pod request: 200m does not fit
  • The scheduler compares Pod requests with the Node's available Allocatable resources.
  • The Pod remains Pending with Insufficient cpu.
  • The result is the same if current CPU use is low.

Use kubectl describe node <node> to inspect Allocatable and Allocated resources.

Requests and limits determine QoS

Kubernetes assigns each Pod a Quality of Service class from its CPU and memory requests and limits.

ClassCPU and memory configuration
GuaranteedEvery container has requests and limits for CPU and memory. Each request equals its limit.
BurstableThe Pod is not Guaranteed, and at least one CPU or memory request or limit is set.
BestEffortNo CPU or memory request or limit is set.
  • QoS class affects Pod selection during node-pressure eviction.
  • QoS class does not determine whether the scheduler can fit the Pod on a Node.
  • Read it with kubectl get pod <pod> -o jsonpath='{.status.qosClass}'.

Taints restrict Nodes;
tolerations allow a Pod to pass

Taint effectPod without a matching toleration
NoScheduleThe scheduler does not place the Pod on the Node. Existing Pods remain.
PreferNoScheduleThe scheduler tries to avoid the Node. This is a preference, not a hard filter.
NoExecuteThe scheduler does not place the Pod. Existing Pods without a matching toleration are evicted.
kubectl describe node <node> | grep -A2 Taints kubectl describe pod <pod> | grep -A5 Tolerations

A toleration permits placement on a tainted Node. It does not select that Node.

Node selection uses Node labels

spec: nodeSelector: disktype: ssd affinity: nodeAffinity: preferredDuringScheduling...: - weight: 50 preference: ...
  • nodeSelector is a hard requirement.
  • requiredDuringScheduling... node affinity is a hard requirement.
  • preferredDuringScheduling... node affinity affects scoring. It does not block scheduling.
  • Required rules that match no Node leave the Pod Pending.

Check Node labels with kubectl get nodes --show-labels.

Pod placement can depend on other Pods

A topology domain is a set of Nodes that share the same value for a topology label.

Pod affinity and anti-affinity

Pod affinity places Pods near matching Pods. Pod anti-affinity places Pods away from matching Pods.

hardrequiredDuringScheduling...
softpreferredDuringScheduling...

Topology spread

Topology spread constraints control how matching Pods are distributed across Nodes, zones, or other topology domains.

hardDoNotSchedule
softScheduleAnyway

A hard placement constraint can leave replicas Pending when no valid topology domain is available.

Scheduling: key rules

  • The scheduler filters Nodes, scores feasible Nodes, and binds the Pod to the selected Node.
  • A resource request is used for scheduling. A resource limit is enforced at runtime.
  • CPU and memory requests and limits determine the Pod's QoS class.
  • Taints, required node selection, affinity, and hard topology rules can make a Node infeasible.
  • For a Pending Pod, read FailedScheduling first. Then inspect the relevant Pod and Node configuration.
