Scheduling

How the scheduler decides which node runs each Pod — requests, limits, QoS, taints, and affinity — and the handful of ways a Pod ends up Pending forever or killed the moment it starts.

A Pending Pod starts no container and writes no log. The answer isn't in the Pod — it's in one event that names, node by node, why the scheduler rejected each.

What you'll walk away with

  • The scheduler's job — filter the nodes a Pod can run on, score the survivors, bind to the best; read the FailedScheduling event when the filter empties
  • Requests vs limits — what the scheduler fits against a node, versus what the kubelet and kernel enforce at runtime
  • QoS class — Guaranteed, Burstable, BestEffort, and who gets OOM-killed or evicted first under pressure
  • Taints and tolerations — keeping Pods off nodes, and the untolerated taint that keeps them off by accident
  • Affinity and spread — steering placement, spreading replicas for HA, and how a hard rule wedges a Deployment
  • The Pending differential — one FailedScheduling signature per cause

The scheduler filters, scores, then binds

It watches for Pods with no spec.nodeName and, for each, runs every node through two moves before writing the assignment.

An empty filter result means Pending — no node survived. Scheduling fails at the filter, not the score; the kubelet on the bound node takes it from there.

One filter cascade;
each “no” is a distinct Pending reason

Every node runs the gauntlet. When none survives, the FailedScheduling event lists the first filter each node failed — and that list is the differential.

The FailedScheduling event is the diagnosis

# a Pending Pod's story lives in its events, not its (absent) logs kubectl describe pod <pod> -n <ns> ... Events: Warning FailedScheduling 0/2 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 1 Insufficient memory.

On a cluster with a tainted control-plane, every message carries the control-plane taint line — expected noise. Read past it to what the worker line says; that's the actionable cause.

Requests are what you fit;
limits are what kills you

Two numbers per resource. The scheduler reads one; the node enforces the other.

request — a reservation

Summed and fit against a node's Allocatable (capacity minus what the kubelet and OS reserve). The only resource number scheduling uses.

too bigPending — a scheduling failure
fixright-size the request, or add capacity

limit — a runtime ceiling

Enforced by the node while the container runs. Ignored by the scheduler entirely — a node can be overcommitted on limits and still accept Pods.

too smallOOMKilled — a runtime failure
fixthe memory limit, or actual usage

Same resource, opposite symptom, opposite fix. Pending → look at requests and node headroom. A running Pod dead with exit 137 → look at the memory limit.

Over its CPU limit a container throttles;
over its memory limit it is killed

The two resources enforce the same ceiling in opposite ways, because memory can't be handed back.

CPU over-limit

Throttled — the kernel's CFS quota hands the container fewer time slices. It runs slower; it does not die.

mechanismCFS quota
symptomadded latency, not a crash

Memory over-limit

Killed — memory can't be throttled, so the kernel OOM killer terminates the process.

signatureOOMKilled, exit 137 (128 + SIGKILL)
symptomrestart, then CrashLoopBackOff

QoS class falls out of requests and limits
and sets the kill order

Guaranteed

Every container's CPU and memory limit equals its request. It gets exactly what it reserved.

evictedlast

Burstable

At least one request or limit set, but not Guaranteed — the common case, requests below limits.

evictedin the middle

BestEffort

No requests or limits anywhere. Uses whatever is spare, guaranteed nothing.

evictedfirst

Under node-pressure eviction the kubelet reclaims memory in exactly this order — BestEffort, then Burstable, then Guaranteed — and within a class, those most over their requests go first. “Just don't set limits” makes a Pod the first casualty of any tight node.

OOMKill, eviction, preemption —
three killers, three owners

Conflating them sends you to the wrong fix. Each is a different component acting on a different scope.

OOMKill

The kernel, on one container that touched its own memory limit. Local and synchronous: the process dies, the container restarts in place.

reasonOOMKilled

Eviction

The kubelet, when the whole node crosses a memory or disk threshold. Picks victims by QoS class; the Pod is deleted and rescheduled if controller-owned.

reasonEvicted

Preemption

The scheduler, deleting a lower-PriorityClass Pod to fit a higher-priority Pending one. Driven by PriorityClass, never QoS.

reasonPreempted

The tell: OOMKill leaves the Pod in place with a climbing restart count; eviction and preemption make it disappear from its node.

Taints repel; a toleration is the exception

A taint is a key=value:effect mark on a node that repels every Pod lacking a matching toleration. Three effects, ascending severity.

NoSchedule

No new Pod is placed here unless it tolerates the taint. Pods already running are left alone.

scopenew Pods only

PreferNoSchedule

Soft. The scheduler avoids the node if it can, but uses it rather than leave a Pod Pending.

scopebest-effort avoid

NoExecute

Strongest. Blocks new Pods and evicts running ones that don't tolerate it; a toleration may carry tolerationSeconds for a grace period.

scopenew and running

This is why tainting a live node NoSchedule surprises people — the existing Pods stay. Kubernetes taints automatically too: not-ready / unreachable (NoExecute) empty a failed node; cordon adds unschedulable:NoSchedule.

nodeSelector and node affinity
steer a Pod onto labeled nodes

Both attract a Pod to nodes carrying particular labels — the difference is expressiveness and whether the rule is hard.

nodeSelector

The blunt form: an exact key: value match, always hard-required. No matching node, no schedule.

formexact match, hard

node affinity

The expressive form, with two flavors that recur across every affinity type.

requireda hard filter — no match, Pending
preferredsoft, weighted — won't leave you Pending

Point a required node affinity — or a nodeSelector — at a label no node carries and the Pod is Pending with didn't match Pod's node affinity/selector.

Spread replicas for HA —
and the wedge it hides

Both place replicas apart so one node's loss can't take the service. In their hard form, both also refuse to schedule.

Pod anti-affinity

“Don't put two of these in the same topology.” required on kubernetes.io/hostname forces every replica onto a distinct node.

domaintopologyKey — per-node, per-zone

Topology spread

Bounds how uneven replicas may get: a maxSkew across a topologyKey, with a hard or soft response.

hardDoNotSchedule — the default
softScheduleAnyway

The trap: a required / DoNotSchedule rule wedges the moment the schedulable domain count drops below what it needs. A drain or a zone loss turns “highly available” into “won't scale up,” surplus replicas Pending.

What to carry forward

  • The scheduler filters, then scores. A Pod that fits no node stays Pending, and one FailedScheduling event names, per node, the first filter it failed — that list is the differential.
  • Requests are what you fit; limits are what kills you. Scheduling sums requests against Allocatable and ignores limits. Too-big request → Pending; too-small memory limit → OOMKilled.
  • QoS falls out of requests and limits and sets the kill order — Guaranteed survives longest, BestEffort dies first. It drives kubelet eviction, not scheduler preemption.
  • Taints repel; tolerations are the exception. NoSchedule blocks new Pods but leaves running ones; NoExecute evicts. Read past the control-plane taint line to the worker's reason.
  • required affinity and DoNotSchedule spread are HA and a trap in one — they wedge the moment schedulable domains drop below what they need. Prefer soft forms unless you have the domains.
