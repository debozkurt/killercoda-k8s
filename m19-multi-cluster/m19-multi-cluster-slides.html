Multi-cluster Fleet

One repo describes many nearly-identical clusters. Each cluster's desired state is composed from shared layers — a base, its region, its own overlay — and rendered on demand.

At fleet scale a failure is not a crash. It is valid YAML that applies cleanly, runs, and is simply wrong for one cluster. The fix is always the same shape: render the cluster, find the surprising value, trace it to the layer that set it.

What you'll walk away with

  • Structure a fleet repo as base → region → cluster layers, and read any cluster's kustomization.yaml as a path through that stack
  • Render one cluster with kubectl kustomize clusters/<cluster> and trace every field to the layer that set it
  • Reason about cluster variables — region, tier, capacity, image — and know which layer owns each
  • Apply composition order: when two layers set the same field, the later one wins
  • Move a change through promotion — lab, then stage, then prod — and see that the layer you edit is the blast radius
  • Locate a fleet misconfiguration to its owning layer, because at fleet scale "the value is wrong" has three distinct root causes

The unit of operation is the fleet,
not the cluster

A fleet is the set of clusters you run as one thing. Differentiated, not independent — the same workloads and contracts, departing only where they genuinely must.

Two axes carry all the variation:

  • Where a cluster runs — its region
  • How ripe its tier is — lab, stage, prod

The source of truth is no longer any one API server. It is a git repo that describes the whole fleet at once.

Same base, different arguments

region axisus-east-1, eu-central-1, …
tier axislab → stage → prod
sharedworkloads, contracts, defaults

A fleet repo is a tree of kustomizations

fleet/ base/ # what every cluster runs regions/ us-east-1/ # region-scoped: REGION, capacity eu-central-1/ clusters/ lab-us-east-1/ # a leaf: composes its region, stage-us-east-1/ # pins tier + image + replicas prod-us-east-1/ prod-eu-central-1/ # composes eu-central-1 instead

Each cluster overlay's resources: names its region overlay; the region's names the base. So clusters/prod-us-east-1 reads as a path: base → region → this leaf.

The only copied text is the small leaf that says "I am prod, in us-east-1, on this image." One base, and the differences at the edges.

Every cluster is the same base folded with different arguments. The cluster's API server never learns Kustomize exists — a GitOps controller renders the path and applies the result.

Every cluster variable has one owning layer

A cluster variable is any value that makes one cluster or region differ from the identical majority. The rule that keeps a fleet legible: each variable has exactly one owning layer.

One home per value means "where do I change this?" has one answer — and a rendering trace has one place to land.

VariableOwning layer
fleet defaultsbase
REGION, capacityregion overlay
tier, replicas, imagecluster overlay

A new region overlay is almost always born by copying its nearest sibling — which is exactly how its REGION ends up stale. The clone still names the sibling, the render is valid, the apply succeeds, and the workload reports the wrong region.

Composition is ordered;
the last layer to set a field wins

Layers accumulate base-first, then region, then cluster. When more than one sets the same field, the one later in the stack — the more specific layer — wins.

Reading the final render is never enough. You have to know which layer put each value there, because that is where you fix it.

e.g. tracing MAX_SESSIONS

base500 — the fleet floor
region8000 merged on — wins over base
clustersilent — 8000 survives to the render

The render is the microscope

# render exactly what one cluster receives — touches no cluster kubectl kustomize clusters/prod-us-east-1 # attribute a surprising value: grep the whole path, last hit wins grep -rn MAX_SESSIONS base regions/us-east-1 clusters/prod-us-east-1

When a value is wrong, render the cluster, find it, then walk up the path. Grep each layer for the key and take the last layer that sets it — that is the entire trace algorithm.

If the render disagrees with the layer you thought owned the value, a later layer is shadowing it — and that later layer is your bug.

The layer you edit is the blast radius

Edit the base

Reserved for what the whole fleet must take at once, on purpose — a security floor, a dropped-capability fix, a corrected default.

radiusevery cluster

Edit a region overlay

The geographic blast radius — placement, regional capacity, REGION.

radiusone region

Edit a cluster overlay

The narrowest change you can make — tier, replicas, the image under test.

radiusone cluster

The same one-line change is a fleet-wide rollout or a single-cluster tweak, depending only on the file it lands in.

Promotion advances a pin, in order

lab

→
stage

→
prod
customers

A change moves through tiers in sequence, gating at each. In a layered fleet that is not a copy into every cluster — it is advancing a pin from one tier's overlay to the next. Between promotions the tiers legitimately run different images; that is the gate working, not drift.

Pin it in the base

Lab, stage, and prod all take it in one commit. The gate is bypassed and an untested change lands in front of customers.

Pin it in the wrong tier

Promote prod's overlay instead of stage's, and prod overshoots the gate while stage never advances — exactly backwards from what you intended.

"The value is wrong" has three root causes

One symptom every time — a value is wrong for one cluster. Three different layers at fault, three different fixes. The render tells you which.

Stale in the owning layer

The right layer owns the value, but its copy is out of date — a cloned overlay whose variable was never updated.

fixupdate it in that layer

Shadowed by a later layer

The owning layer is correct, but a more-specific layer overrides it — a leftover per-cluster pin winning over the new standard.

fixremove the shadow

Right value, wrong layer

The change is correct but landed where the blast radius is wrong — a promotion pinned in prod instead of stage.

fixmove it to the owning layer

Field guide: symptom, cause, where to look

SymptomLikely causeWhere to look
Runs fine, reports the wrong value A cluster var is stale in its owning layer kubectl kustomize <cluster> | grep <VAR> vs the layer's literal
A layer you edited doesn't change the render A later, more-specific layer sets the field and wins Grep the whole path base→region→cluster; last hit wins
A tier you promoted didn't change The pin was added to a different tier's overlay Diff the two rendered tiers
A change reached every tier at once It was committed to the base, not a tier overlay The base kustomization — a per-tier value doesn't belong there
Two regions diverge on a shared value The value lives in each region instead of the base Move it down to the base; keep only differences in regions

Recap

  • A fleet repo is a function evaluated once per cluster. kubectl kustomize clusters/<cluster> folds base → region → cluster into the exact manifests that cluster receives.
  • Composition is ordered; the last layer to set a field wins. Trace each surprising value up its path and take the last layer that set it.
  • Every cluster variable has one owning layer. One home per value keeps "where do I fix this?" answerable.
  • The layer you edit is the blast radius. Promotion is advancing a pin lab → stage → prod, never editing the base for a per-tier change.
  • "The value is wrong" has three root causes — stale, shadowed, or wrong-layer — each fixed in a different place. The render tells you which.
