PKI & TLS

How a workload gets a cryptographic identity, and uses it to talk securely. A certificate binds a public key to a set of names; TLS checks it on every connection.

Every TLS failure is one of three questions — was the cert issued, does its identity match, is its signer trusted. Name the layer and you have halved the fix.

What you'll walk away with

  • Read the cert-manager issuance chain — Issuer → Certificate → CertificateRequest → a kubernetes.io/tls Secret
  • Stand up an internal CA, and say why a private CA — not a public one — secures east-west traffic
  • Read a leaf cert's identity — its SANs — and recognize a hostname-verification failure on sight
  • Explain trust: why a client accepts or rejects a server by which CA signed it, and how ca.crt reaches the clients that need it
  • Set up mutual TLS between two workloads and read each way it breaks
  • Place ACME — the Let's Encrypt protocol — and why it is for public certs, not internal ones

Every TLS failure is one of three questions

A certificate answers "who are you?" with a signature you can check without asking anyone. Three separable properties make that work — and each fails on its own.

Issuance

Does a signed cert exist? Someone holding a CA key had to sign the workload's public key.

Identity

Does the cert claim the right name? A cert for one service proves nothing about another.

Trust

Does the verifier believe the signer? A cert is only as good as your trust in its CA.

All three look identical from outside — "the call didn't connect" — but have different fixes. Name the failing layer before you touch anything.

cert-manager turns a certificate
into a declarative object

Before, getting a cert into a Pod meant a human running openssl and pasting the result into a Secret — every 90 days. cert-manager is an operator: CRDs plus a controller that issues and auto-renews.

  • An Issuer declares how certs get signed — the backend
  • A Certificate declares what you want — names, duration, the Secret to write
  • The controller creates a CertificateRequest — a CSR as an object — which the issuer signs

One Secret, three keys —
the deliverable and the trust anchor

cert-manager reconciles a Certificate into a kubernetes.io/tls Secret. This is what a workload mounts.

kubernetes.io/tls Secret
tls.crtthe leaf cert · public
tls.keyprivate key · never leaves
ca.crtthe issuing CA · public
the server mounts it to serve TLS · a client needs only ca.crt to verify

The Secret is the deliverable; ca.crt is the trust anchor. Issuance produces the first, trust distribution the second — keep the two jobs separate.

Missing cert = missing Secret = stuck Pod

A Certificate that won't issue never writes its Secret. A Pod mounting that Secret sits ContainerCreating with a FailedMount event.

Two symptoms, one root cause. Read the Certificate, not the Pod.

Identity is the SAN list,
not the Common Name

TLS checks the name you dialed against the cert's Subject Alternative Names. Modern clients ignore the legacy Common Name entirely.

# decode a leaf cert, read its SANs kubectl get secret config-api-tls \ -o jsonpath='{.data.tls\.crt}' \ | base64 -d | openssl x509 -noout -text \ | grep -A1 'Subject Alternative Name'

The handshake error

no alternative certificate subject name matches target host name — trusted, freshly issued, still rejected because the dialed name is not in the SANs.

A service's cert must list every name a client uses to reach it — the short form and the FQDN. Miss one and some callers fail while others succeed.

Trust is what the client holds,
distributed apart from the cert

A client trusts a fixed set of CAs — for the public web, the roots baked into the OS. An internal CA no OS has heard of is trusted by nobody by default.

  • ca.crt is public — no private key — so it is safe to hand to every workload
  • Give the client the CA's public cert so it can complete the chain; point its verifier at it with --cacert
  • Mount the wrong CA and a flawless server is rejected

The trust error

unable to get local issuer certificate — not "the cert is bad", but "I don't recognize who signed it."

Never answer this with curl -k or insecureSkipVerify — that turns authenticated TLS into plaintext-equivalent.

Mutual TLS: both ends present
and verify a certificate

Server TLS authenticates one direction — the server accepts anyone. mTLS closes the loop: the server also requires a client cert and verifies it against a CA.

Client
presents tls.crt / key
verifies the server
both verify↔
Server
presents tls.crt / key

# --cert/--key present the caller's identity; --cacert is its trust anchor curl --cert /etc/tls/id/tls.crt --key /etc/tls/id/tls.key \ --cacert /etc/tls/trust/ca.crt \ https://config-api.media.svc.cluster.local/

mTLS multiplies the failure surface — either side's cert can be un-issued, mis-named, or untrusted — but adds no new kinds of failure. It is issuance, identity, trust, from two vantage points.

ACME issues public certs
by proving you control the domain

A private CA fits internal traffic — you own both ends. A cert a customer's browser hits must be signed by a CA the browser already trusts, such as Let's Encrypt.

HTTP-01

Serve a random token at /.well-known/acme-challenge/ — proves you control the web server behind the name.

DNS-01

Publish a TXT record — proves you control the domain's DNS, and can issue wildcards.

Internal traffic → private CA (instant, free, you own trust). Public traffic → ACME (a real CA, but you must prove domain control). An ACME issuer will never sign a cluster-internal name.

Certificates expire;
renewal is a loop, not a reminder

A cert nobody renews is an outage with a timer on it — it worked yesterday and now throws certificate has expired.

What to carry forward

  • Every TLS failure is issuance, identity, or trust. Was it signed, does it claim the right name, does the verifier trust the signer — name the layer first.
  • cert-manager makes certs a reconcile loop. When it stalls, read from the Certificate down to its CertificateRequest for the real reason.
  • A missing cert is a missing Secret is a stuck Pod. Diagnose the cert, not the Pod it blocks.
  • Identity is SANs, not CN. The cert must list every name its clients dial.
  • Trust is the client's CA, distributed separately. ca.crt is public and safe to spread; never fix a trust error by disabling verification.
